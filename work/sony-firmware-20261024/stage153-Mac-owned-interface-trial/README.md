## 预期调用范围和真实限制

候选先在IORegistry缓存中过滤唯一的 `054C:0DA1 / ILME-FX3 / locationID=0x02100000`，在创建任何设备user client前核对。用缓存的USB序列号生成每轮HMAC标签；不请求USB字符串，也不输出原序列号。标签只用于本轮前后同一标识的比较，不证明7.02程序指纹或机身健康。

Disk Arbitration读取相机子树中IOMedia的卷元数据，不读取素材；任何已挂载卷或未知媒体记录都会阻止主动步骤。候选不会自动卸载相机卷，也没有排除重新自动挂载的完整系统锁定机制。

此后预期流程为：创建目标设备user client；再次核对缓存连接与挂载；**显式USBDeviceOpenSeize**；capture选项；关闭/非Seize重开；再次确认同一连接且MSC驱动不再占用；打开接口0并核对两个512字节bulk端点81/02；释放接口；一次release选项归还设备；关闭自身对象；仅用缓存反复观察同轮HMAC、媒体及驱动关联。前后注册表ID允许因归还而变化，主动步骤期间变化则拒绝。

Apple SDK特别说明：

1. Seize只会尝试让既有客户端关闭；对方可以拒绝，不能认为root必定能够接管。
2. capture选项不终止Mass Storage Class接口驱动。因此，capture返回0后仍有MSC驱动时，本候选停止，绝不直接继续claim。
3. 本候选归还时使用SDK的release选项，不使用libusb的零选项归还实现。两条实现不能混为一谈；实际Mac驱动行为尚未验证。

SDK原件路径、字节哈希、检查的标记及行号在构建回执中。旧152所述libusb源码行为仍为该版本的源码事实；本轮补充Mass Storage例外与新候选的不同调用路径，没有改写旧封存材料。IOKit内部可能产生的总线活动并未测量，不能将“没有显式DeviceRequest/ResetDevice”解释为零总线活动或绝不发生USB断开。

## 33项离线检查证明了什么

[测试](test_owner_core.py) 只加载自写 [fixture DSO](owner_fixture.c)，不链接IOKit或libusb。共享的真实C流程经过故障注入，覆盖工作边界、capture/reopen/claim失败、三项清理失败、缓存始终不可用、错误端点、缺失/变化标签、挂载与注册表代次变化、capture后MSC驱动仍在、无需capture的分支、时钟倒退、迟到返回、无效配置以及两个真实入口拒绝对照。C与ctypes的5种结构大小相符。

流程不自动重试capture、claim或归还；工作期限已过仍执行单次清理。清理错误即使后续缓存看似正常也保留UNKNOWN。成功的缓存比较也只用于本次接管试验的主机观察，不能证明真实驱动恢复、相机线程退出、认证、录像或救砖。

见 [33项回执](run-owner-fixtures/results.json)。这些检查没有执行 `owner_iokit.c` 的系统调用，不证明实际IOKit深层失败路径、所有资源释放或当前macOS兼容性。

审查中修正了一个实际流程问题：失败的初始snapshot可能填过部分字段，原版本仍可能用它作比较基线。现在只有成功的完整初始观察才能成为基线；原失败版本、对应源码和两个DSO保存在 `attempt-partial-baseline-review`。另有SDK头文件非UTF8导致回执生成失败的构建保存在 `attempt-SDK-header-decoding`；修正读取编码后生成正式回执。没有删除原材料。

## 为什么尚不能上机

原生调用次数受限，时间限额仍是协作式的；同步IOKit或Disk Arbitration调用可能卡住。本阶段没有完成隔离工作进程、共享结果/在途阶段观察、单次凭据、停止请求和异常退出监管。不能沿用描述符采集器“超时就终止”的做法，因为退出进程本身不证明接管已经归还。

还需对前后挂载状态、缓存序列号标签、真实接口独占及驱动回归的判据进行独立复核。首次物理执行会涉及新的user client、显式Seize、capture/release和驱动状态变化，需要具体方案对应的新增授权及管理员验证；当前单次描述符权限已消耗，不能复用。**本轮没有请求或取得这些权限，也没有执行sudo、卸载卷、接管或归还操作。**

下一步完成监管组件及故障注入，再形成可审阅的一次性接管/归还方案。之后才可能用实机核查Mac路径；它仍不等于服务认证、同机完整备份恢复或HEVC主录验收。H.265具体补丁/原片和原16项验收缺口继续保留。
