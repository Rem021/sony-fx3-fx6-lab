## AP 请求字段与消费边界

原 appFw `0x20f158c` 构造10B，前四个 little-endian u16：

| 偏移 | 值 | 已证明的含义 |
|---|---|---|
| +0 | 0x200d | 原包头字段，未恢复私有枚举名 |
| +2 | 0x032d | command |
| +4 | 10 | 请求字节数 |
| +6 | 0x8001 | 原包头字段，不擅自命名 flag 位 |
| +8 | 两字节存储 | 先清零；输入 u32==1 时只把第一字节置1；本轮为0 |

它在 `0x20f1608` 调 `0x20ef604`，输入长度10、输出长度12。通用 helper 申请新请求、复制10B、把 source 设为自有动态队列后发送。发送返回0才进入原 `timeout=-1` 接收路径。收到后不检查 recv rc、消息长度或头部，**直接复制12B到输出缓冲，再以自己的动态 qid 释放响应，随后走原临时队列生命周期清理**。

具体消费者只读取响应 `+8` 的 u32（`0x20f160c`），经 `0x20edd1c` 映射后写到调用者输出（`0x20f1614`）。因此10B echo会让原复制长度超出请求；12B随意填零虽可能映射成成功，也不是合法完成证据。当前 helper 的宽松消费不能作为伪造响应的依据。

## 原 CP 的新证据

CP 是平坦 ARM32 镜像，本轮选中代码为 **Thumb**；基址 `0x108000`，换算一律为 `file_offset=(VA & ~1)-0x108000`。例如完成函数 VA `0x5dc82a` 对应文件 `0x4d482a`，不是把 VA 直接当偏移。脚本对每个断言保存该换算与指令。

### 原完成函数

`0x5dc82a` 入口把 incoming R1保存到R5。随后构造12B：

```text
u16 {0x200d, 0x132d, 12, 0x8001}
u32 payload = incoming R1              // body +8
```

`0x5dc86a` 写的是R5，**不是固定 `0x00580000`**。`0x5dc870` 调 `0x1abecc` 送出这个完成包。

`0x1abecc` 从上下文/事务索引取出目标，申请新回复、把source设为 `0x92840747`、复制指定12B，再发送；发送返回0后不在该路径释放，发送失败才走释放调用。目标来自原上下文的路由FIFO读取，不是可直接把任意 source 复制进来的无状态 echo。平坦镜像中 `0x4b6fa4/0x4b68d8/0x4b70a0` 的 alloc/send/free 名称属于接口模式推断；其数值调用边、分支和新申请/复制行为已逐条绑定。完整FIFO取消/并发所有权仍待专门研究。

### 两条完成来源与请求处理

完成函数只有两处本轮已定位的直接BL调用：

- **即时错误：** `0x1a9324 → 0x1af1b0` 调 handler。非零结果保存在R5，`0x1a9344` 把它交给完成函数；结果0则先不发完成，转公共请求清理。
- **下游完成事件：** `0x1a994e` 从事件 `+8` 读u32状态、事务索引设为 `0xbb`，`0x1a9954` 调同一个完成函数。

内部请求分派有精确跳表证明：`0x1a8a24` 从包装对象 `+0` 取内部索引、`+0xc` 取消息；TBH基址 `0x1a8a4a`，索引 `0xbb-0x1e` 的表项在 `0x1a8b84`（文件 `0xa0b84`），u16值 `0x46d`，计算 `0x1a8a4a+2*0x46d=0x1a9324`。**这没有冒充外部 command=0x032d 到索引0xbb的 ingress 查表边；该边仍未知。** 完成头和调用边证明它是对应完成构造/内部处理链，但未证明完整外部派发入口。

`0x1af1b0` 读取原请求 `+8` 的第一字节。0/1分别传0/1；其它值仅打印错误后仍读取并传递原字节，**这里没有可恢复出的“非法参数必返某个固定错误码”契约**。它构造下游12B包 `{0x2004,0x0304,12,1}` 和该payload，调用 `0x5ec356`，目的 `0x9058003f`，返回路由标识 `0x928407b9`。

子发送返回非零时 `0x1af248` 令返回值为 `0xffffffff`；上面的即时错误路径会把它装入0x132d完成包。子发送成功时 handler本地返回0，**没有在这条路径伪造完成状态**；后续完成走另一个事件入口。公共请求路径最后在 `0x1a90a4..0x1a90b6` 交还原请求给释放例程。这个所有权顺序不允许 hook 同时释放请求再保留指针做迟到回复。

## AP 状态映射与上层是否检查

`0x20edd1c` 是数字枚举转换。下表为本轮原指令分支重建，**不是原函数执行结果，也未恢复 enum 名称**；脚本JSON保留更多明确输入值。

| raw response+8 | AP映射 |
|---|---|
| 0、0x00580000 | 0 |
| 1 / 2 / 0xffffffff | 0x6d / 0x6e / 0x6f |
| 4 | 0x8b |
| 0x0058e001..0x0058e008 | 分别0x80..0x87 |
| 0x0058e009 / 0x0058e00a / 0x0058efff | 0 / 0x89 / 0x8a |
| 0x00590001..0x00590005 | 分别0x70..0x74 |
| 0x005a0001..0x005a0007 | 分别0x78..0x7e |
| 0x005affff | 0x7f |

默认分支可返回2；不能为这些数值贴上未经证实的 `unsupported/invalid` 名称。尤其真实 CP 的子发送失败 `-1` 在 AP 会映射成 `0x6f`，而不是成功0。只有复现了对应真实失败条件，才能讨论传播该错误；不能因为虚拟服务缺失就自行挑一个数值回复。

`20d00e8` 之前的wrapper原样传递输出。`init_hdmi` 在 `0x1cd8100/104` **检查映射后的输出是否非零**：零才继续下一项HDMI调用；非零会记录日志、等待100000µs、调用 `0x2167780` 后提前返回。该固定原件的 `0x2167780` 就是一条RET，并非本轮证明的abort。外层 `cold_boot::run` 从 `0x1cd86a8` 继续读取对象+0x10并调用后续函数，没有检查 `init_hdmi` 的返回状态。因此错误在本地被检查并短路该HDMI后续项，随后由外层继续，不是全层级向上传递失败，也不是完全没检查。

## 冻结决定

本轮新增节点足以证明原完成包的构造来源、可变状态、子发送失败路径、AP消费/释放和错误处理。仍未闭合：

1. 外部 `0x032d` ingress →内部索引0xbb的精确查表/校验边。
2. 子服务 `0x9058003f` 真正操作、完成条件及状态产生者。

因此**不实现回复、不回echo、不固定0x580000，不将当前等待误标为已解决**。当前native线程池修复及其真实新阻塞可单独交付，后续若恢复这个服务需依据上述原消费者和真实失败状态，保留事务路由与消息所有权。

正式交付仅此报告、JSON与自写脚本；无固件、ELF、KO、CPIO、缓存或大段固件内容。未改shared source、供体或VM候选，未新跑VM或Git/sync。通用 ABI解释复用已查阅的Arm规则；Sony私有字段完全来自本机固定原件，官方OSS/产品规格不用于倒推应答word。
