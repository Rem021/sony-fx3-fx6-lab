# FX3 原 CP 启动描述块、页表生产链与 DMM 指针门槛（2026-10-29）

**已从官方 CP 原镜像找到完整 380 字节启动描述块，并用原启动指令在明确的 RAM 环境中生成页表；此前缺失的页表来源得到补充。仍无可正常刷入 FX3 的完整 FX5／VENICE 菜单和色彩链替换固件。** 本轮没有缓存／RAW 像素、完整供体 ISP、实机映射或目标修改包准入证据。

开始前复核外盘 UUID `F9404A58-A1C4-409F-8E78-9A6B7EEB3F7B`，逐项回读[上一阶段](../loader-host-20261029/README.md) 109 个封存文件。只读核对另一 agent 的 stage192：仍为本地进程／假设备检查，原生08未运行，真实备份、冷启动和独立恢复未验。本轮不运行或修改其设备／恢复工具，不占用设备。

## 页表输入原来位于 CP 原镜像内

原输入仍为 `cpapp-b.bin`，15,980,568 字节，SHA-256：

`c90d00d807874a5309dc1b65b203287e83608ceee513cc57b53409333fb6bcba`

原 MMU 结构初始化 `0x553d48` 读取的配置基址由 `MOVW #0x8000`／`MOVT #0x12` 形成，即 **`0x00128000`**。按已核对的 `CP VA = 文件偏移 + 0x108000`，该描述块就在文件偏移 **`0x20000`**，不是尚未恢复的高地址 RAM。380 个字节的 SHA 为：

`543e6e57aa6ebb26257a96e3a28c59068cbd5eb9fef26c67ed8684c7fc05f50b`

这也避免了把 `0x128000` 与 `0x1280000` 混淆。来源是实际原件、原地址构造和原读取指令，不是根据预期手填的启动结构。

| 描述块偏移 | 原值 | 本轮直接关联 |
| --- | --- | --- |
| `0x0` | `0x553c94` | 启动段末尾读取后跳转的入口值；本轮不执行该入口 |
| `0x158`／`0x15c` | `0x4000`／`0x14e8000` | 一级表大小／地址 |
| `0x164`／`0x168` | `0x8000`／`0x14ec000` | 二级表区容量／地址 |
| `0x16c` | `0x128000` | 原启动段参与地址计算的值 |
| `0x170` | `0xedf000` | 与上项相加，得到启动元数据地址 `0x1007000` |

原启动段把该描述块复制到 `0x108da0`；原文件中的目标 380 字节均为零，guest 中通过原 `0x108a04` 复制后与原描述块完全相同。一级表 4,096 项／16 KiB 和原查询的索引形式也与 [Arm 官方短描述符说明](https://developer.arm.com/community/arm-community-blogs/b/tools-software-ides-blog/posts/developing-jython-scripts-for-ds-5-translation-table-decoder)相符；实际尺寸、地址和结果仍以原字节／原指令为依据，不据此推定具体 DRAM 芯片或实机当前状态。

## 严格路径与明确环境输入分开

`bootstrap_guest.py` 共记录五组原指令实验。只有隔离 Unicorn RAM，不加载内核、写寄存器或连接相机。

1. **完整原入口 `0x108398`**：到 `0x10897c` 读取 `0x3e42001` 前停止。没有给启动轮询提供成功状态。
2. **独立的轮询后代码片段 `0x1083a4`**：不声称真实轮询已通过，使用明确的独立栈；原复制和地址计算执行，得到 `L1=0x14e8000`、`L2=0x14ec000`，到 `0x1089ec` 读取另一个硬件标志 `0x3e42000` 前停止。
3. **声明后一个标志为 0 的片段**：原启动指令执行 66,848 条、7,299 次非栈 RAM 写入，生成表和启动元数据，停在 `0x108728` 的 CPU 设置调用前。没有执行 CPU／TTBR／TLB 设置，不能称作完成启动。
4. **使用上一项状态进入原 `0x553d48`**：初始根结构与表管理数据由原指令写出，执行 1,122 条指令后，停在 `0x5541e4` 的 `DSB SY` 前。完整 MMU 初始化尚未返回。
5. **声明后一个标志为 1 的片段**：仅到标志消费之后、表生成之前 `0x108434` 停止。这个分支没有被作为用户机身标志的推断，也没有扩展到特殊地址访问。

两个硬件标志是不同输入。即使声明第二个标志为 0，真正的启动轮询字节仍然未知且停止；附加三组负向检查确认这一点，以及未知标志、原镜像外的 BSS 都不能被当作原代码继续执行。

## 原生产结果，而非填入一个成功的 MMU 回复

在明确的标志0片段中，原生成结果为：

```
L1 = 0x14e8000，16,384 字节，4,096 项
L2 = 0x14ec000，描述块容量 32,768 字节
实际生成的 L2 字节 = 6,144（六个 1 KiB 区域）
启动元数据 @0x1007000：
  0x14e8000  0x14ec000  0x6  0x153c000  0x1414000  0x108d94
```

只导出了原指令已经初始化的 L1、L2 区域和元数据。二级表区其余 **26,624 字节**没有导出或当作“恢复的零字节”。guest 对原镜像以外 RAM 的未初始化读取会停止；没有拿 AP WBI 的缺页补造 CP 数据。

进入原软件 MMU 初始化后，`0x14007c8` 的前几项确实由原指令获得 L1／L2 地址和容量 `0x20`。这接上了[此前备份参数调查](../dmm-backup-20261029/README.md)已定位的查询根。它仍是首次同步屏障之前的部分初始化状态，不代表正常冷启动／Tomco 配置完成后的最终映射。

## 原属性查询和指针检查的局部结果

在上述**首次屏障之前的同一软件表快照**上，独立调用原 `0x54bbd0 → 0x554ebc` 属性查询和原 `0x53894c` 指针检查。输入是候选地址或负例，属性结果全部由原函数读取原生成的表得出，没有代填映射或属性返回值。

| 查询地址 | 原查询返回 | 输出属性字 | 原指针检查返回 |
| --- | --- | --- | --- |
| DMM 候选 `0x09a08e00` | `0` | `0` | `0x09a08e00` |
| CP 原镜像地址 `0x128000` | `0` | `0xf` | `0` |
| 零地址 `0` | `-26` | `0` | `0` |

原指针检查消费属性中的 `0x4` 掩码；上述负例说明不是统一返回候选地址。正例仅证明这个明确的表快照可以通过该局部谓词。**没有在 `0x09a08e00` 放入 `DmmCfg.bin`、读取实际配置、完成 DMM 分配或取得真实像素。** 也没有证明真实启动的标志值、轮询、屏障／TLB 效果、后续映射和备份段选择。

## 失败保留与完整目标

首轮自写 guest 在切换 CPU 模式前设置了栈，模式切换后银行寄存器导致第一条 push 到未映射地址，未到预期硬件边界。该失败记录保留于 `attempts/banked-stack-initialization.json`；已改为先设置模式、再设置该模式的 SP／LR，才得到上述结果。它是夹具初始化错误，不是索尼固件或机身故障证据。

本轮补上了真实嵌入描述块、原表生产和原属性读取之间的局部链。下一步应接完整软件 MMU 初始化／后续映射与正常配置装入，再连接 DMM 单位槽／extent 分配。不能把当前的初始表谓词通过扩大为正常缓存或 RAW 读取成功。

完整 FX5 私有系统／菜单、VENICE type3/type4 明文和完整传感器／ISP 色彩链、FX3 主录绑定、目标修改整包准入、正常启动及独立恢复均未通过。公开供体检索本轮未取得新内层读取入口；亚太 FX5 下载页直接读取失败也没有被当成全网不存在包的证明。持续目标保持 active，不输出修改固件，实际刷机不执行。
