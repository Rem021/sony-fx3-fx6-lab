# FX3 原软件 MMU 后续、区域表与未缓存配置链（2026-10-29）

**仍没有可正常刷入 FX3 的整套 FX5／VENICE 功能或色彩链固件。** 本轮补上了原页表清理、原区域重建和 `memcfg` 数值解析之间的局部链，也确认上一阶段候选指针通过只是中间状态。没有得到候选区的 `DmmCfg.bin`、缓存像素或 RAW，更没有完整供体 ISP、修改整包准入或实机启动结果。

重启后先等到[上一阶段](../cp-bootstrap-20261029/README.md)已运行的封存任务退出，再独立回读全部 27 个文件，SHA 全部一致、入口索引只有一项；没有重复执行封存。外盘 UUID 为 `F9404A58-A1C4-409F-8E78-9A6B7EEB3F7B`，项目为现有非 Git 的 Mac 研究目录。只读核对另一 agent 的 stage193：其原生09未发布／未运行，实际备份、冷启动和独立恢复仍未验；本轮未运行或修改其工具，未占用设备。

## 中间状态不能代表最后结果

CP 原件仍为 15,980,568 字节的 `cpapp-b.bin`，SHA-256：

`c90d00d807874a5309dc1b65b203287e83608ceee513cc57b53409333fb6bcba`

在明确声明第二个可选标志为0、从轮询后片段起步的 RAM 环境内，原 `0x553d48` 软件初始化执行到返回。记录到 116,936 条原指令、4,806 次非栈 RAM 写入、28 次原清理调用和28次 `DSB SY`。相对启动表，一级表有 4,065 项发生变化；候选地址 `0x09a08e00` 的项变成零，原查询返回 `-26`，原指针检查返回零。

这里允许原 `DSB SY` 指令在 Unicorn 中执行，仅用于追踪软件表的后续写入。模型没有物理缓存、页表遍历观察者或 TLB，因此不证明真实同步完成。其他 CPU／硬件操作继续停止；没有提供 CPU 寄存器返回值。[Arm 官方架构说明](https://documentation-service.arm.com/static/5f8daeb7f86e16515cdb8c4e)也要求把软件表更新与实际 TLB／屏障生效区分开。

## 原区域表重新建立映射

原 `0x54ad18` 完整入口先在 `0x555d34` 的 CPU 信息读取前停止。为了独立审查其后软件效果，使用两个明确分开的原代码片段：

- `0x54ad3c → 0x54ae54`：原代码初始化三组空闲节点，停在互斥量初始化调用之前。
- `0x54ae5c → 0x54b3b4`：独立的互斥量调用后区域片段，使用原节点与表数据；停在后续缓存辅助函数之前。没有给略过的互斥量／事件提供成功返回，也不声称完整入口完成。

原 `0x569f74` 返回表地址 `0xd22a84`、数量19；原 `0x54b21c` 证明步长为 `0x14` 字节。380 字节的表和19个原名称均已保存，不能把它误按16字节记录拆开。原表的 `Rsv_C1` 项为：

```
0x04000000  0xc4000000  0x0  <原名称指针>  0x04000000
```

这个片段产生15次原 `0x554610` 映射调用，覆盖上述保留区；候选地址重新获得属性 `0xc`，仍被原指针检查拒绝。其后另一个原表提供者 `0x569f8c` 实际返回零指针和零项；没有为了继续而填入额外表。

## 原 memcfg 解析值与严格调用边界

从已封存的原 `tomco.txt` 取出唯一这一行作为明确输入：

```
memcfg=0x7000000@0x09000000:uc
```

原值解析片段 `0x546b2c → 0x546c9c` 计算出的原调用参数是地址 `0x09000000`、长度 `0x07000000`、属性 `0x20`。数值、单位、地址和 `uc` 属性的转换都由原指令完成；不是宿主直接把结果写入页表。只使用这一行的值解析片段，没有运行整份 TOMCO 装载或它的其他回调。

严格进入原 `0x54b4b8` 属性设置函数，在 `0x556204` 读取尚未知的缓存几何字段 `0x1400728` 前停止。没有补造硬件状态使它通过。

另开一个软件实验，明确将属性参数改为 `0x20000020`。原包装器解释其中 `0x20000000` 为关闭 CPU 维护分支，剥离后仍以 `0x20` 修改表。这个实验按原包装器的现有参数语义运行，没有修改原指令或提供 MMU 查询成功值；但它是**明确不同于 TOMCO 原调用的参数**，只能说明软件表效果，不能算原正常路径完成或安全跳过硬件维护的方法。

| 软件阶段 | 候选的 L1 原始项 | 原属性查询 | 原指针检查 |
| --- | --- | --- | --- |
| 上阶段首次屏障前 | `0x09a10c12` | 成功，属性0 | 接受候选 |
| 软件初始化返回后 | `0` | `-26` | 拒绝 |
| 原区域片段后 | `0x09a1041e` | 成功，属性 `0xc` | 拒绝 |
| 明确关闭 CPU 维护的属性投影 | `0x09a11412` | 成功，属性 `0x20` | 接受候选 |

原查询还核对了区间端点和负例：投影后 `0x0fffffff` 属性为 `0x20`，而区间外紧邻的 `0x10000000` 保持 `0xc`、指针仍被拒绝；零地址仍返回 `-26`，原镜像地址 `0x128000` 的属性仍为 `0xf`、同样被该指针谓词拒绝。不是统一返回“接受”。

## 失败和剩余目标

区域实验首轮触发旧夹具过窄的源镜像写入保护：原 `0x54ad58` 写全局 `0xff430c`。失败保留在 `attempts/region-global-write-guard.json`；仅增加原后续代码实际使用的 `0xff4308..0xff4360` 数据根写入范围，其他源代码／外部地址保护保留。另一次只读列目录使用了不存在的 `original-files` 名称，随后通过文件清单找到已有 `tomco.txt`；没有数据改动，也不算固件故障。

本轮明确了原默认缓存区、TOMCO 未缓存请求和原指针谓词之间的关系，修正了“最初表可接受就代表后续也可接受”的可能误读。下一步应查正常缓存维护初始化、TOMCO 实际装载与配置内容进入候选区的生产者，再接 DMM 槽和 extent 分配。现有候选区没有被放入配置文件或像素，RAM 表项接受不等于真实数据可读。
