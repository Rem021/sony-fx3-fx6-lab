**原上层待处理字节清零时，后端更新标志和已复制参数仍可存在。** 本轮把原QoS消费接到独立的上层待处理片段，并完成此前停止在入口的`1a085c`已有句柄分支。这些结果进一步约束恢复/卸载条件，仍不证明硬件完成。

只在Mac上离线运行；未操作相机、Windows或UU，没有改官方文件、C原型、设备权限或生成可刷固件。16项完整目标保留。

## 本轮先修正了观察方式

新增尾部参数路径最初出现重复入口、栈偏移和未映射读取。没有修改原指令、寄存器结果或返回地址来绕过它。对同一原程序和输入进行四组观察器对照：

| 观察方式 | 本机结果 |
| --- | --- |
| 无观察钩子 | 正常返回，SP恢复 |
| 仅代码跟踪 | 正常返回，SP恢复，目标入口记录1次 |
| 内存读写钩子 | 返回异常，SP偏移 |
| 代码及内存读写钩子 | 同样异常，目标入口记录2次 |

这是当前Unicorn 2.1.4环境下的本地对照，不能据此认定Sony程序有栈缺陷，也没有证明所有平台/路径存在相同问题。[上游FAQ](https://github.com/unicorn-engine/unicorn/blob/master/docs/FAQ.md)说明了钩子与PC同步的关系，但未确认本次现象的具体根因。

正式运行采用代码白名单跟踪、无效访问停点及完整内存前后核对，**不安装内存读写钩子，也不声称采集了逐次内存访问轨迹**。代码映射始终只读可执行；完整映像、输入页、句柄页、上下文页、4KiB输出及活动栈窗口外的字节都核对。保留每阶段2万条观察上限与1秒CPU观察时限，没有手动修PC、跳指令、补内存结果或运行时返回值。

历史MIPS带内存钩子的动态记录保留；跨入新路径或用其判断指令次数/顺序前，需要按修正观察方式复核。本轮已重新覆盖目标消费与292字节转交结果；没有以这个局部对照推翻所有历史静态、A64或MIPS结果，也不将未重跑的范围标记重新通过。

## 待处理字节清零的实际范围

使用stage78原代码生成并保存的64字节QoS前缀、明确的流状态和已有句柄RAM输入：

1. 原`18fdb4/18faa0`消费16M或20M目标，设置流状态`+1`的待处理字节。
2. 独立进入原上层`190888`片段。它实际调用`19bda4`，后者在同一执行阶段复制292字节参数并正常返回到`1908c0`，没有宿主提供返回值。
3. 原`1908cc`清除流状态`+1`，随后在外层尾声之前停止，避免为未运行的整个调用者伪造栈帧。

此时待处理字节为0，而后端对象`+28`的`40`更新位仍为1，目的缓冲中的16M/20M字仍保持。这个字节不能单独作为硬件确认、缓冲已消费、恢复完成或可卸载代码的凭据。

关闭更新位的两类对照不调用参数更新例程。无句柄的20M对照进入原分配路径，在未知GP状态读取前停止，待处理字节保持1；未执行分配失败后的断言/清理或完整错误返回。

## 8008／240000继续去了哪里

原`18fad0`把查询来源的数值组装成8字节参数：`80a90300 481f0000`。在明确提供已有句柄的条件下，完整原`1a085c`把它复制到后端缓冲`+7d0..+7d7`，设置后端对象`+28`的`20000000`更新位，再沿原尾声返回。

这条路径的上层待处理字节仍为0，说明它和后端两个更新位不能混为同一状态。无句柄对照在另一个GP相对读取之前停止，未补分配器或线程状态。

数学关系仍为`240000/8008 = 30000/1001`；本轮确认继续传递的原字节，未证明字段正式单位、实际帧率或精确30.000支持。后端缓冲里还有本轮未分类的声明旧值，不能当作语义完整、可提交硬件的有效请求。
