# FX3：普通应用协作者与原 NIN 线程的有界联合执行

2026-10-27。**在声明的离线夹具下，三轮错误的前4B摘要都被原校验器拒绝，但原NIN仍发出相同的最终6/1回复，再调用普通应用的完成回调。该回调忽略传入结果，写内部状态2并请求资源。** 因而最终协议回复不能独自证明摘要被接受、资源申请成功、实际进入服务模式或认证线程已经退出。

本轮没有修改阶段145的MSC摘要提供者，没有发送USB包或操作相机。完整1080p29.97 HEVC MAIN、同机健康备份恢复、独立救援及全部16项验收要求保持。

## 原协作者的真实绑定

[normal_cooperator.py](normal_cooperator.py) 使用固定的原 `libObj.so` 和 `libsencore.so`。前者由阶段148从官方镜像提取、SHA为 `c4681d209a7fe2ed63752be3b0be89ab7b7ce400679c00068c8c6e47d39f83ae`；后者SHA为 `a2907111c4a22314dcb12c25889e0e3142764c6a4a910a746e43908f76e7c410`。固定读取器和父阶段清单先校验。

原RTTI、虚表重定位和 `.init_array` 构造共同对应如下对象，不能用服务模式的 `WorkerThreadManager` 虚表替代：

| 项目 | 原 libObj VA / 行为 |
|---|---|
| 类型 | `Senser::SenUsbIf`，继承 `NinCooperator` |
| 原构造入口 | `.init_array` 中的 `57fec` |
| 全局对象 / 虚表地址点 | `2ce108` / `252340` |
| receive / send getter | `e9f18` / `e9f24`，分别返回原 `e9ed8` / `e9ef8` |
| 实际收发封装 | 从事件回调保存的 `2ce100` 取函数表，调用表的第0/1项；并不在这些封装里计算摘要 |
| Hasp登记虚方法 | `e9f30` 只有ret；仅限此对象的此虚方法，不能推断整条认证过程不写历史 |
| 完成回调 | `ea6b0` 覆盖传入的结果参数，清对象标志、设内部状态2，再经 `ea660` 调用 `MWF::RsrcAcsr::Acquire` |

静态报告保存15个原Obj函数、11个原core函数和对应原字节SHA，见 [normal-cooperator-static.json](normal-cooperator-static.json)。局部函数由原 `.eh_frame` FDE界定。原NIN在 `bf2c` 调用对象完成回调后，才在 `bf64/bf68` 检查失败轮状态是否需要回到接收循环。

## 联合guest的范围

[run_normal_checkpoint.py](run_normal_checkpoint.py) 将两份原ELF分别映射进Unicorn，执行原构造器、原事件回调、原动态查找/线程创建封装、原getter/收发封装、原NinThread及原摘要与包编码函数。只应用明确列出的本地RELATIVE重定位，执行范围和写入范围均受检查；原代码在执行后逐字节保持。

以下均为CPU夹具或桥，未调用对应主机/相机能力：

- 回调的事件1、初始内部状态1、传输函数表、接口上下文和资源对象。它们不证明当前机身选择了这份注册或当前MSC映射。
- dlopen/dlsym、pthread创建/取消状态、mutex及atexit；线程创建只返回夹具token，随后在同一guest中调用实际选定的入口，不创建真实线程或加载Sony DSO。
- 七次516B接收及七次发送。挑战由声明的确定性RAND桥产生，包头盐为0；不是实际USB抓包。
- EVP SHA-256、C内存函数、日志函数及资源申请。EVP接收原代码构成的1024B输入，原memcmp实际决定比较结果；资源返回值为明确夹具。

每例均停在原NIN的 `bf30`，即完成回调已返回、原 `tlog_file_exist` 尚未调用的位置。没有继续执行历史文件尾部、模式文件、取消/等待或真正线程退出。暂停点的原NIN栈帧、入口上方保护区、原代码不变及所有guest写边界通过检查。

首次执行在原Obj局部日志helper `ea070` 被封闭执行守卫拒绝，原源码和失败原因保存在 `attempt-local-logging-guard`。随后将两项已审查的局部日志helper显式加入CPU日志桥，没有放开不受限的原代码执行；当前五例通过。

## 五个结果

| 声明输入 | 原摘要比较 | 原完成回调实参 | 协议回复 | 内部资源请求 |
|---|---|---|---|---|
| 完整512B挑战+对应轮材料，图案0/1 | 每例三次成功，原轮号1/2/3 | 3 | 8/4/8/4/8/4/6，最终首字节1 | 各一次，返回0夹具 |
| 公开MSC前4B摘要，两种数据图案 | 每例三次失败，返回-2，原轮号反复为1 | -1 | 同上 | 各一次，返回0夹具 |
| 前4B摘要，资源申请返回-5夹具 | 同样三次失败 | -1 | 同上 | 仍尝试一次，返回错误；内部状态仍为2 |

见 [执行回执](run-original-checkpoint/results.json)。五例共590次原函数进入；每例两条原收发封装各进入七次。**资源返回0、写内部状态2或6/1回复均不能替代物理模式和成功完成证据。** 图案0/1是测试数据编号，不是实际USB或机身模式。

这说明，在已连接的原普通协作者路径中，“前4B摘要得到最终回复”未必意味着存在独立的前4B摘要验证器。不能据此宣布真实MSC算法已验证；实际注册、对象代次、模式、驱动和物理USB仍需独立确认。

下一步追资源申请的异步完成回调与普通应用的停止/恢复链，明确哪个事件能证明机身切换完成，及失败认证线程如何结束。阶段147借用句柄收发层仍没有完整owner/驱动归还/进程寿命实现。当前无可安全刷入的文件，未改变或消耗新的设备授权。
