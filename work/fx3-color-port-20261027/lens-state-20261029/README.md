# FX3 原 AP／CP 镜头状态链与机型、地区、版本检查

2026-10-29。**已定位 CP 侧 `Lens FirmUpdate` 接收循环，并把原 AP 请求与原 CP 回复代码通过内存消息通道接通。** 在明确的合成镜头状态下，原两端会完成头部、机型、地区和版本检查；匹配时仍停在下一项机身状态服务，未证明真实入口放行、实际加载或刷入。完整 FX5／VENICE 色彩替换固件仍未完成。

接续[完整旧格式内存流与镜头类别门槛](../legacy-stream-20261029/README.md)。本轮没有相机、USB、机身文件、真实 IPC、原生目标库、mount、脚本、更新数据或刷写操作。

## 从 AP 调用定位到 CP 接收器

在原 AP 分区的 532 个 AArch64 ELF 中扫描三个精确服务 ID，记录 172 处 MOV-wide 构造候选。`0x912503d0` 出现在 UFP、原 `LensCommunicator::GetMountedLensInfo` 及版本查询库中。内核 ET_REL 地址明确按节内偏移记录，未充当机身 VA。

CP／AV 普通字节搜索没有匹配该服务值，但这不代表服务不存在。进一步扫描 Thumb／ARM MOVW＋MOVT，CP 中命中两个相关位置；按已核对的 `file + 0x108000` 映射，定位到 CP 接收循环 `0x391b54`，调用 `0x38dddc` 处理器和 `0x38e144` 回复分派。源字符串明确标记 `Lens FirmUpdate`。原接收器检查消息头的发送组后才进入处理器，不把该组值检查称为密码认证。

原回复长度表按 command 0–4 分别为 20／12／40／8／8 字节。本轮只允许 0、1、3；实际更新数据 command 2 被 guest 入口拒绝。[AP 定位](service-location-results.json)、[CP 指令构造](peer-constant-results.json)、[原片段与数据表](lens-contract-results.json)

## 两端原逻辑怎样接通

AP 原镜头准备流程从原头部读取器开始，依次发出 command 3、1、0。内存通道将实际请求字节交给独立 Thumb guest，执行原 CP 接收循环、发送组检查、处理器、状态／类型 getter、数据字段组装、回复长度表、头部访问与回复发送包装；再把这些**由原 CP 指令生成的回复字节**交回原 AP 比较代码。

OSAL 分配、收发、释放和 memcpy 是严格内存适配器，不是真实服务。CP 的 kind 2、状态字节、元数据、AP 发送 ID 和媒体路径都是明确的合成输入，不是当前机身或镜头读回。`ready`／`error` 等夹具名仅描述所查分支的作用，未恢复全部物理枚举语义。没有把底层硬件 getter 替换成“返回成功”；所选 CP 路径执行原 getter 读取这些声明的 RAM 字段，不访问 MMIO。

| 两端合成输入条件 | 原 AP 结果 |
|---|---|
| 机型／地区匹配，输入版本更新 | 元数据检查返回 1，停在下一项动态机身服务请求前 |
| 机型不匹配 | 内部 `0x140`，原转换后返回 7 |
| 地区不匹配 | 内部 `0x141`，原转换后返回 6 |
| 版本相同 | 内部 `0x142`，原转换后返回 5 |
| 版本相同，特定 CP 状态布尔字段为 1 | 原 command 1 回复使 AP 在原 `0x3020` 设置版本跳过标志；检查推进到下一项服务 |
| CP ready 夹具为 0 | 原回复中有效身份字段为零，AP 机型比较失败并返回 7 |
| 发送组与 CP 原接收检查不匹配 | CP 不处理请求、不产生回复；AP 在内存无回复边界停止，不伪造超时或成功 |

匹配案例停在 `osal_dynamic_id` 入口（action `0x2a`、category `0x92`），没有为下一项服务构造成功回复。数据表、线程入口、处理器、回复组装和 AP 错误转换均取自原件；但通道、物理状态和 OSAL 环境仍是模拟，因此不能称为真实镜头准备已成功。[七组两端检查](ap-cp-bridge-results.json)、[四组 CP 回复／发送组检查](cp-peer-guest-results.json)

## 缓存比较不能代替重新查询

另八组检查单独执行原 UFP `0x1dbc..0x1f64` 比较窗口。其缓存分支要求同一机型和地区，输入版本更高才返回 1；版本跳过只省略版本比较，仍拒绝机型不匹配。

正常镜头准备会设置 live-query 标志。该分支先清零原缓存，再请求服务；本轮单独检查此分支时在 OSAL allocation 前停止，未提供手工回复。这也是为何不能用预填匹配缓存宣称真实链通过。两端检查则由原 CP 代码实际生成回复，保留合成 CP 状态的边界。[缓存与重新查询八组结果](cached-metadata-results.json)

## 公开服务执行研究的适用边界

联网复核了 [A7C II 服务／preload 作者研究](https://github.com/YuuLuo/a7c2-service-preload)：其报告范围为 ILCE-7CM2 2.01 的临时子进程执行，并明确把修改固件准入列为另一问题，不能据此认定 FX3 已可刷入。

[A7 IV 特性研究](https://github.com/leogenot/sony-a7iv-feature-research)也区分了持久设置、共享功能代码与产品菜单条件，不能替代本机完整固件移植。两份网页本轮只读核查；提交 API 取回失败，未声称锁定其最新提交或发布日期，也未执行网页中的设备操作。[联网复核边界](public-route-review.json)
