# FX3 7.02：44字节消息、分配空间与4字节尾标记

2026-10-27。**原内核分配代码为本轮44字节条件请求128字节块，并在对齐后的数据末尾写入`0x77777777`。在明确声明的这类存储中，原MPR复制48字节得到“44字节消息＋4字节尾标记”，未越过块边界。** 这为阶段111的长度差异提供了原代码解释；实际机身采用的客户端、分配结果、用户映射和消息寿命仍未验收。

本轮只有Mac离线文件读取与Unicorn guest指令执行，没有Windows、UU、设备接口、ioctl、内核装载或相机写入。正式结果：[allocation-tail-results.json](run-native-client-branches-20261027/allocation-tail-results.json)。16组分配几何、2组拒绝条件、4组用户ioctl参数和2组MPR注册参数；另有2组独立发送／回调／复制链，合计70个有界阶段。

## 分配规则来自原模块

沿用阶段47提取的原 `osal_uipc.ko`，SHA-256 `6aa0f5c8c72f5f6cf9aa9c905fc3f3f75b8bea0dfebaf13deb632b0de088eb38`。这里只将未重定位的`.text`映射到guest，执行不依赖外部重定位的局部算术／声明内存片段；客户端查询、池引用、池分配和日志均停止。没有装载或初始化真实模块。

原 `osal_valloc_msg_wait` 调到内部`.text+0x3248`例程。本轮从其原入口到客户端查询前停止，再分别声明客户端模式，执行原大小计算。令有效数据长度为L：

- 数据长度先向上对齐到4字节，记为A。
- 消息头占24字节，尾标记占4字节；本轮所用`0x80c70047`还走额外预留40字节的分支。
- 分配请求是 `align64(A + 24 + 4 + 40)`；不含额外40字节的正值ID对照为 `align64(A + 24 + 4)`。

这些关系由原`0x32b4..0x32c0`、`0x34b8..0x34ec`等指令产生。本轮的池块是下一阶段明确声明的输入，**不是伪造池分配成功返回**。

| 声明ID／长度 | 原块大小请求 | 数据距块起点 | 原元数据长度 | 尾标记距数据起点 |
| --- | ---: | ---: | ---: | ---: |
| `0x80c70047`／44 | 128 | 64 | 44 | 44 |
| `0x80c70047`／45 | 128 | 64 | 45 | 48 |
| `0x80c70047`／48 | 128 | 64 | 48 | 48 |
| 不走额外40字节分支的声明ID／44 | 128 | 24 | 44 | 44 |

原后段还写入长度、消息头标记、引用计数、来源初始值与返回数据指针；声明客户端计数由0增到1，通过原指令恢复保存寄存器并返回。44字节条件下，数据指针到块尾还有64字节，48字节复制落在这个声明范围内。

客户端模式覆盖`flags0/pool0`、`flags0/非空pool`和`flags8/非空pool`，分别在相应池入口前停止。另一组`flags8/pool0`走配置拒绝日志分支，未执行分配或消息头生成。**这些是声明配置，不是实机当前客户端状态。** 45字节是对齐控制，不能据此允许其它消息角色读取未知填充。

## 原发送、回调入口和48字节复制

两组44字节联接实验使用阶段111原指令生成的错误回复作为消息数据：

1. 以声明的Dataflow字段及分配指针进入原发送后段。原libc仅复制44字节，原用户OSAL写来源字段；尾标记保持`0x77777777`，随后停止于发送之前。
2. 原用户回调worker在取消设置、ioctl前分别停止。独立声明通知记录后，原代码直接取出回调指针、上下文和消息指针，没有复制或补齐消息，停止在间接调用之前。
3. 另一独立阶段运行原MPR锁后48字节复制，源数据仍在同一个声明128字节块中。结果逐字等于44字节消息和4个`0x77`，来源及尾标记不变，再停止于期待状态清除之前。

各段之间没有实际队列、ioctl输出、用户映射、线程通知或互斥锁。回调地址按已声明的MPR guest装载基址计算，不能据此确认实机ASLR或注册状态。原函数没有被替换成返回成功的适配器。

## 注册及用户态到内核的边界

原 `Codec::Init` 的参数片段将ID`0x80c70047`、`CallbackFromAvbbc`原符号和上下文0交给OSAL注册调用。其日志／锁／线程建立和注册均未执行。

原用户OSAL的分配和注册封装能够生成各自的ioctl参数记录：分配仍请求44字节，注册仍传递声明的回调地址及上下文。执行在ioctl之前停止，使用的FD字段来自ELF初始存储，不是打开的设备句柄。[Linux ioctl接口说明](https://man7.org/linux/man-pages/man2/ioctl.2.html)也明确操作码与参数语义依赖具体驱动；本轮没有把通用接口说明当作Sony驱动的映射保证。

因此目前可解释的是**原分配分支的容量和尾标记**，仍需追实际ioctl处理／指针转换、客户端池初始化、用户可读范围及释放代次。不能仅见到4个`0x77`就认定任意指针可读，或任意44字节消息都能套用48字节复制。
