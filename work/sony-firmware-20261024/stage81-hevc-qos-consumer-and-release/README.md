# FX3：HEVC专属目标消费与更新位清理

**本轮把QoS目标字追到了HEVC的GOP消费分支。** 在明确的离线对象输入上，原代码把已有缓冲中的20M目标字写入GOP对象`+c8`；关闭任一层更新标志都跳过目标更新。它没有清除后端标志或归还缓冲，不能当作硬件完成。

相机、Windows和UU未操作，官方文件和C原型未改。全部16项主录及恢复验收要求保持，当前没有可安全刷入的版本。

## 确认为HEVC的依据

选定的`d9204/d9454/d949c`片段位于引用原源码路径`enc/HEVC/gop_ctrl_hevc.cxx`的函数内；`d9364/d936c`的原高低地址构造指向该字符串。另一个相似分支引用`enc/AVC/gop_ctrl_avc.cxx`，本轮没有将其作为HEVC证据。

当前MAIN是否实际绑定到这个对象、完整GOP构造和回调流程仍未验证。源码归属与局部调用不是实机当前对象身份。

## 已有参数如何进入GOP

复用stage80正式结果中的上下文及输出字节作为声明输入，使用其修正后的代码跟踪与完整内存前后检查；不安装全局内存读写钩子。新GOP对象和初始16M字段是本轮明确的试验输入，不是机身快照。

原路径先用`19bff4`检查后端`40`位，再由`19bd44`取得已有缓冲`+1c`。参数内部`+f4`的bit29也必须开启；原`d949c..d94c8`才把目标字复制到GOP`+c8`。

| 输入 | 原GOP目标字段结果 |
| --- | --- |
| 原生成16M，两个标志均开 | 保持16M，实际执行目标复制 |
| 原生成20M，两个标志均开 | 由声明初值16M变为20M |
| 20M字保留，仅后端`40`位关闭 | 不更新，仍16M |
| 20M字保留，仅参数bit29关闭 | 不更新，仍16M |
| 仅尾部参数更新，后端`40`位未开 | 不更新目标 |

两种旧值A5/C3的结果一致。所有对象其它字节、源参数缓冲和后端标志均保持。执行在其它HEVC字段处理之前停止；没有为了避开未知字段而更改它们，也没有运行完整控制器、编码提交或码流生产。

尾部参数的原谓词/指针getter另行完整执行，返回已有缓冲`+7d0`及原8字节`80a90300 481f0000`，不清除更新标志。指针取得成功不等于消费者完成；实际单位、29.97成片与精确30.000仍未验收。

## 标志清零仍不等于缓冲释放

另做原清理包装器`19bfd8`和`1a0a64`的独立对照，均进入公共`1a0cfc`：

- 使用上一轮试验状态中的其它剩余位时，清除`40`后直接返回，句柄和缓冲保持。
- 明确声明标志为`20000040`时，先清`40`仍保留尾参数位和句柄；再清最后的`20000000`，原代码先写标志0，随后进入释放路径。本轮在读取未知GP状态之前停止，句柄仍在，原缓冲未变。
- 明确的空句柄对照中，清最后一位后正常返回；该输入本来就没有可归还句柄，不能作为真实释放成功的证据。

`20000040`组合只用于隔离清理条件，不证明这组状态在真实完整启动中自然产生。未执行原释放正文、线程状态、引用归还、回执或硬件完成。

因此，外层pending清零、更新位清零和实际句柄/消费者退出是不同证据。恢复/卸载方案仍须绑定真实缓冲归属与所有消费者完成，不能靠某个布尔值或指针getter判定。
