# FX3：原 MPR Open 字段到 HEVC_MP4 / HD42010 的来源

**在声明的类型6、质量6、帧率3输入下，原 MPR 构造函数分段生成1920×1080、色度0、位深1等字段；关联的原格式查询生成主录类别15。原 av-cam 转换器据此识别 `HEVC_MP4 / 29_97 / CHROMA_420 / BIT_DEPTH_10`，质量名称为 `FH`。** 这补上原 MPR 参数生产者到接收侧标量解释的来源，但没有补上阶段105的正常 MAIN 上游来源、完整资源选择、实际 Open 或16Mbps成片。

2026-10-27，仅 Mac 离线。地址/偏移使用十六进制；表中数量和类型值使用十进制。相机、Windows、UU未操作，原固件未修改。全部16项验收和stage75不可部署原型保持。

## 原类型表及主录、代理类别

原 `g_videoParamComb` 位于 `libmpr.so+2cb108`，大小312字节、每行24字节。原 `GetCodecInfoForCodec`（`cd40c`）通过本库符号重定位读取这张原表；不是宿主新建表。

本轮显式建立同一ELF的局部符号重定位模型，以原序言、独立日志后正文、独立日志后原返回段核对查询。声明类型5/6/7/8时，选择字0得到15、选择字1得到18；类型1分别得到5和17。原 Enqueue Open 代码将主、代理字段分别以选择字0/1传给该查询，并把返回值写入请求；消费侧又将对应值用作 `Codec::EncOpen` 的 FileFormat 参数。这些调用点和字段位置为静态来源，未执行完整队列传递或绑定真实编码实例。

查询在本轮客体中实际读取原表字节。局部GOT重定位是显式客体输入，未执行真实动态加载器、全局构造或相机启动。类别相同不能证明是同一通道、编码器或资源。

## 原 Open 构造字段

原 `SetEncOpenParam`（`d13f8`）读取 `execEncOpen_t+764/+768/+76c` 的类型、质量、帧率，结合原类型表和原纯转换函数写入98字节 Open 参数区。原 Enqueue Open 的静态复制/写入位置与这几个输入偏移对应，但本轮输入结构仍为声明数据，未由真实 MovieRecInfo、缓冲分配和队列生产。

原构造器、其局部纯helper、原函数返回均实际执行。原日志调用停在 `c8c70` 前；每次后续入口都作为**独立、显式承接当前寄存器和内存的输入实验**。日志效果没有执行，没有伪造其返回或宣称整条函数连续运行。保存帧及全部独立返回的保存寄存器核对通过。

随后还独立执行原 `Codec::EncOpen` 的音频位深/质量规范化片段 `282b08..282b20`，停在未执行的全局状态操作之前。质量22保持22；没有执行其锁、消息构造、发送或硬件接口。

每项以A5/C3两种输出旧值运行，核心字段一致。列中的名称均来自原函数；`QT150M`是枚举名称，非实测速率。候选上层质量6由原函数转换为字节22，再由接收侧解释为 `FH`，不能因此声称输出16Mbps，既有质量/资源匹配问题保持。

MPR视频字节15与推流构包字节10属于本轮已读的不同生产路径。不能把推流值当作MPR构造器的预期，也不能凭数字相同或不同推断物理硬件实例。

## 表行存在不能代替完整支持

类型8的原行确有1920×1080和同一编码类别，但原色度及位深函数各自产生254。原av-cam转换器遇到254时都进入原日志getter `27d528` 前停止。本轮不提供日志返回，不把未完成的转换改称成功或生成未知名称。

这和阶段105的通用检查器反例一起说明：表行、编码类别或某个检查分支不足以证明参数组合有效。负例的两个标量消费者是独立实验，未继续向实际编码器提交。

## 完整请求与运行时缺口

输出区仍有51字节依赖A5/C3旧值。原调用者在整个 SetEncOpenParam 之前存在98字节清零调用，但本轮未执行该清零及其provider；也没有实际缓冲、物理地址、所有权、锁、状态或配置代次。声明输入中的地址为0，不能用于硬件提交。

因此，本轮原输出是**可复核字段来源**，不是完整有效 Open 包。关联格式查询和原构造结果虽然来自同一声明类型，仍未证明实际队列会把同一配置代次、实例和缓冲绑定在一起。接收侧仅执行原标量转换及名称查找，没有执行完整接收构造、资源matcher、编码器启动或SPS。

阶段105已确认此应用 MAIN 转换分支不自然产生候选类型6；该缺口没有被本轮的声明输入解决。原FH质量与目标资源/16M策略也未闭合。下一步继续核对实际编码 Open 消费者、消息头/通道/实例、状态代次及FH资源匹配，再与已有受限私有预置方案核对。

## 运行与复核

证据合计**376个有界阶段**：原参数生产及规范化280阶段在前一执行轮完成，接收侧96阶段在正式轮完成。为避免重复已通过的生产实验，正式轮复用了该轮保存的原结果；两份源码在 `def classify` 之前逐字节相同，生产源码、检查点及复用回执均复制并计入封存。未将复用结果称为正式轮重新执行。

共10组参数生产和10组接收侧核对。所有阶段均核对声明栈、scratch保护区和重定位后整个原ELF客体映像；实际执行的本库PLT解析只进入允许的原函数，helper返回由原指令完成，无成功/输出适配器。复核仍是同一代理，不是独立引擎或实机验收。

初轮宿主预期错把推流视频字节10/AVC字节4套用到MPR原构造器，实际是15/3；随后AVC名称预期应为原 `XAVCS_MP4`；负例254也不能预期正常返回。三次失败的源码与回溯均保留，正式轮按原观察修正断言和诊断边界，不修改原固件或把失败改写成通过。
