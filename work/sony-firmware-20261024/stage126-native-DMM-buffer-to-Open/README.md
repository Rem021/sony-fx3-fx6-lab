## 原代码实际执行到哪里

原 SetMemTbl（`2afb0c`）遍历人工链表，向 Model `+0x278` 的 `0x760` 字节 BufferTable 写入字段。原 Enqueue Open 的 `d6700..d67b8` 将它复制到请求前部，并以原 GetCodecInfoForCodec 填入主/代理类别及其它字段，停止在队列对象访问前。请求主核心为 `[6,6,3]`、MAIN类别15，首 `0x760` 字节与原生成表一致。

随后执行原 ExecEncOpen 序言、独立 post-log 回复48字节清零。进入独立 post-DMM/post-unlock 帧后，原调用者根据请求代理字节选分支：

| 声明模式 | 原分支与本轮结果 |
| --- | --- |
| 21 / 25，代理关闭 | 原 memset 清152字节，原 SetEncOpenParam 构建后准备 MAIN Codec::EncOpen；1920×1080、视频字节15、质量字节22、色度0、位深1，在实际 Codec Open 前停止 |
| 31 / 32，代理开启 | 按原分支到双流 Open 准备入口前停止；本轮不执行或声称双流参数构建完成 |

单流两种旧值填充得到相同的152字节输出。若干输出地址数值与原 BufferTable 字段相同，相关原构建器指令保留于审计；这种传递不是地址有效性、DMA/MMU、缓冲所有权、资源匹配、音频或编码成功的证明。质量22仍是原 FH 表示，目标16Mbps的资源/私有预置问题未由本轮解决。

早先阶段106的51个未写字节问题，在本轮**原单流调用者清零前提**下变成确定的零值；不能把这一结果反推阶段106当时已执行清零，也不代表其它调用分支或真实录制参数全部有效。
