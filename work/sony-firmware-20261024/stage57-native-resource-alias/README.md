# FX3 7.02：保持 FH／16M 身份的临时资源匹配原型

本轮新增一个已编译并实际执行的 AArch64 客体原型：**原始 FH／16Mbps 描述保持不变，仅给原资源匹配器一个临时 FF 匹配副本；原匹配器返回 MAIN 行386，原行地址计算和预置选择器选中 `0x19450`；随后受限写者发布私有16M预置，原查询和部分参数打包函数得到16,000,000。** 这解决了此前离线原型“必须先把原描述整项换成 FF”才能进入私有预置的限制。

**这仍然不是已经接入 Sony 的钩子或可刷写固件。** 真实调用位置、临时副本寿命、当前 MAIN／配置代次、共同同步域、完整 Open／Start／HAL、真实成片和恢复全部未验收。保持目标1920×1080、HEVC42010、30000/1001、约16Mbps；精确30.000fps单列。16项完整要求没有减少。

## 已执行的参数流

1. 复用原队列、空闲句柄、ID及map-node存储的声明输入，运行原 common 构造和原 queued Open 到匹配器首诊断。原代码生成 MAIN 尾部 `(1,10,25,旧值)`，common 缓存的136字节描述仍是质量4／FH。设备当前对象、完整工厂启动和真实消息运输并未执行。
2. 新编译函数 `fx3_match_view` 检查固定136字节目标描述、MAIN1／tail10／tail25、owner描述和私有控制结构。在独立客体栈上自己复制152字节，再把**副本** `+0x38` 的质量4改为6／FF。原匹配器输入和 common 描述都不改；`+0x94` 未解释的旧值原样保留。
3. 在另一个客体的明确独立后诊断入口，将原匹配器 `X19` 指向编译函数产生的副本，保留原保存帧等声明输入。原循环返回386并回到原调用者；随后独立执行原行地址／preset ID计算，得到原表行地址和 `0x19450`，在原诊断入口前停止。
4. 再从明确排除诊断／名称 helper 的独立正文入口执行原行封装及完整静态预置选择，输入仍为原 FH 描述，在真实缓冲／通道准备前停止。原指针解码给出默认 target24,498,176、trace25,999,360、CPB26,000,000。
5. 在 stage37 客体写者的本轮副本中，将资格检查收紧为**原目标 FH 描述全部136字节精确匹配**及 preset ID。编译函数自己复制原256字节预置到 common 私有区，仅修改目标系数 `+0xb0=249999`，最后发布私有指针；原查询和原率参数打包片段读到 target16,000,000，trace／CPB保持原值。

上层设置仍是此前原 `[VPC6,VQuality6,Frame3]` 的16M身份。本轮保持原资源描述和缓存字节，不会把 stage54 的人工上层质量8／raw25000当作16M修复。**完整应用到资源消息／writer 的实时传递与所有查询、缓存、封装消费者的一致性仍未打通。** 原解码数值是预置字段，不是实测平均码率或实际HEVC参数集。

## 验证范围

正式结果包含 **25段有界原执行、33次编译原型调用**。两组旧值A5／C3正例均得到386／`0x19450`／私有16M，临时副本仅第 `0x38` 字节不同，原136字节描述及152字节原输入始终保持。另一个声明对象的整个 `0xf000` 区不变，原表与原预置不变，已准备参数包在数据指针复原后仍保留原16M字节。

15组临时副本负例覆盖 FF源、1921宽度、PROXY角色、tail8c／tail90不符、未认可描述字节、owner描述变化、epoch／session不符、观察代次变化、关闭入口、已应用阶段、私有锁已持有、其他owner及输入输出重叠。均不写匹配副本或 common；锁忙时不解别人的锁。身份／代次／锁仍是本原型的输入及私有协议，不是相机实际可信来源。

编译产物为 freestanding AArch64 `ET_REL`，两个函数共2728字节文本、392字节只读数据，6个自有只读数据地址重定位，无未解析外部符号。只加载到 Unicorn 试验地址 `0x13000000`，不是相机模块、补丁入口或固件导出。写入由执行PC和范围核对：临时副本仅152字节及其质量字，写者仅控制区、256字节私有副本和选择指针，外加独立栈。

原子指令只约束使用同一协议的参与者；本原型的锁不证明 Sony 线程采用它，真实共享锁与多核行为仍待绑定。[LLVM Atomic Instructions and Concurrency Guide](https://llvm.org/docs/Atomics.html)

首次运行实际抵达预定的原通道准备入口 `0x21dd54`，但试验Guest漏登记该停止边界，因而以未批准执行停止。补登记边界并为新编译PC补齐完整写入轨迹后，重新运行通过；原 Sony 指令和 C 原型均未因此修改。失败及源副本保留在 `run-20261025/`；正式结果在 `run-bounded-stores-20261026/`。

## 复原和真实接入限制

沿用原型的生产者／参数包登记：关闭新入口后，生产者未退出或参数包仍登记时，指针复原返回 HELD。**生产者退出和包消费完成都是显式模拟通知**，不是 Sony／HAL 真实可信回调。只有这些声明依赖退出后，数据指针恢复到原静态 FF 预置，查询回到24,498,176。

这次数据指针复原后 FH 描述仍在，而原 FH 在未做匹配转换时没有预置。因而**它不是恢复到一个有效的原厂拍摄模式，更不是实机恢复或可卸载证明**。原型不释放副本、不回收代码；仍需真实关闭与回读、切回受支持模式、覆盖所有在途调用及数据引用，再证明完整回退和冷启动。引用移除与内存回收需要区分，此处仅借鉴原则，不认定 Sony 使用 RCU。[Linux RCU说明](https://docs.kernel.org/RCU/whatisRCU.html)

下一步需要找出真实资源匹配调用处的 owner／代次和同步边界，为临时副本确定实际存储与寿命，并在原 channel 准备、完整参数复制／发布／消费过程中核对这个方案。不能用本轮严格输入对照替代真机身份绑定、原生日志／锁、实际硬件接受或同机健康备份。
