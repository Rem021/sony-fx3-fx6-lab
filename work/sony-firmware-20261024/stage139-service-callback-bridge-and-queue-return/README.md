# FX3 服务回调接通与队列返回值反例

2026-10-27。**静态接通了退出请求到 FX3 内部 stop 处理器的回调路径；离线原指令仿真还确认：请求返回0可能没有排队，返回错误也可能已经排队。** 这些结果改变首次上机工具的判断和重试方式，仍不是实机退出或救砖成功。

阶段138的33个成员已逐一校验。本轮没有打开相机接口、重新枚举、切模式、认证、驱动操作或访问机身文件。新增执行仅为 Unicorn 中两个原 AArch64 函数的有界离线仿真，不是 Sony 模块在 Mac 原生环境或相机上运行。Windows/UU继续延后。

## 原回调路径已对应

静态核对18个完整原函数、3段未导出名称的原代码和13个 PLT 调用，结合重定位和两次80B结构复制：

1. 阶段138的原内核匹配退出 setup 后投递命令1，`CUsbGadgetSen` 消费时调用对象 `+f8` 回调，传底层事件3。
2. 固定原登记表八个回调均指向 `libInfraUsbCmn.so+0x18fe4`。经登记结构和 gadget 对象的80B复制，退出回调位置保持。
3. 该回调从上下文 `+18` 取得 Senser 回调表，将底层事件3转换成 Senser 事件2，附32B通道描述和零状态；第二个回调项绑定 `Usb::inactive_event_handler`。
4. 原 inactive 处理器清除通道，发布内部事件5。原事件循环在 USB 状态2时调用 stop，指定 DID13与 stop_callback。
5. USB API `+18` 槽在初始化时装入原 stop 包装器 `0x17c4c`；包装器保存24B回调记录后进入 `CUsbSvc::stop`。较晚的 stop_callback 再发布内部事件3，之后才执行阶段137已核对的 worker join。

这里依据官方包中正常提供者绑定和对象初始化流程，未测实机上的动态链接/对象/队列。没有把不同事件类型中的相同整数当作同一事件，也没有把“发起 stop”当作已经完成。原字节、结构复制及地址见 [callback-bridge-review.json](callback-bridge-review.json)。

## 原函数仿真复现了返回值不一致

运行 [run_queue_return.py](run_queue_return.py)，把原 `CUsb::request`（184B）与 `CUsb::que_push`（136B）接在一起。只将原 PLT 的 queue 调用转到原 queue 入口；日志、互斥锁和条件变量为明确声明的返回值桩。8组输入、15次原函数进入全部达到声明的结果，边界字节、SP及保存寄存器通过。

| 声明场景 | 原 request 返回 | 原队列中是否复制了64B消息 | 含义 |
|---|---:|---|---|
| 空队列或正常环绕 | 0 | 是 | 仍只证明此仿真中的排队，不证明消费者完成 |
| 队列满，包括环绕满 | 0 | 否 | queue 返回12，随后被成功 unlock 的返回值覆盖 |
| lock失败 | 5 | 否 | 尚未进入 queue |
| 排队后 unlock失败 | 5 | 是 | 不能把错误当成“动作未发生”并盲目重发 |
| 排队后条件变量 signal失败 | 0 | 是 | 成功返回不证明消费者已被唤醒 |

原 request 还会在加锁之前把输入消息 `+8` 写为消息自身地址；queue 复制64B结构，包含的指针不是深复制。实际容量、线程竞争、消息寿命和相机当前队列均未测量；上述失败输入是人工桩，**没有声称你的相机出现了队列满或锁错误**。

完整输入、调用轨迹、原函数 SHA、写入边界和已执行源码副本见 [仿真回执](run-queue-return/results.json)。这不是实现自身的镜像测试，也不采用“桩返回0”替代原 queue 执行。
