# FX3 7.02：原请求、匹配、预置选择与通道申请边界

本轮在同一个离线客体中接通了**请求队列 → 原匹配器及编译包装函数返回 → 原行参数复制 → 原预置选择 → 原通道尺寸准备**。先前stage57中排除日志后独立进入的行准备片段，现在由原调用者自然调用。目标A5／C3旧栈值、人工FF、原UHD及代理负对照共30段有界执行通过。

这仍是部分运行环境下的离线证据。日志对象“已初始化”及类别标记来自明确测试输入，再由原静音setter设置静音，日志按原分支返回。真实日志构造、完整启用日志中的时间读取与输出后端没有因此通过。没有打开相机接口、操作Windows、刷写或证明救砖。

## 接通的原路径

沿用已固定的av-cam映像、LIRO／内核导出绑定、stage58编译包装函数和唯一客体BL重定向。原文件没有改动，资源匹配使用临时FF视图，原描述仍保持FH。

在原`+0x21ed18`调用真正返回后，原调用者获得匹配行，执行两次后续诊断及名称helper，再由原`+0x21ee98`调用完整预置选择函数`+0x2261a4`，随后自然调用`+0x21dd54`准备通道。

首次在`+0x21dd54`入口暂停，随后**从同一PC、同一寄存器／栈／内存继续**。没有复制成另一个客体，没有补填行号、选择器返回或跳过诊断。继续执行原帧率查询、尺寸阈值和原静音诊断，停在`+0x22d394`通道申请函数入口，函数体未执行。

| 输入 | 原匹配行 | 原选中预置 | 实际到达 |
| --- | --- | --- | --- |
| 目标FH，旧栈A5 | 386 | ID `0x19450`，`+0x3c5798` | 通道申请入口 |
| 目标FH，旧栈C3 | 386 | 同上 | 同上 |
| 人工FF对照 | 386 | 同上 | 同上 |
| 原UHD对照 | 431 | ID `0x18da8`，`+0x3c8498` | 同上 |
| 代理FH负对照 | −1 | 无成功行 | 原无匹配行分支入口 |

四个正例分别有4次原诊断调用，负例有1次，共17次，按原静音分支返回；未生成真实日志消息。原getter、匹配诊断、行诊断和名称参数都在原调用链上执行。后续诊断的参数类型与第一次匹配诊断不同，观察器分别保存其原始寄存器和槽，不套用第一次的解码格式。

原通道尺寸诊断的参数槽显示：目标1920×1080、面积2073600、面积×内部查询帧率62208000、内部查询值30；UHD为3840×2160、8294400、497664000、60。这里的30是该查询使用的内部整数，**不是精确30.000fps或实际成片帧率证明**，29.97主录目标不变。

## 明确的停点与下一项依赖

四个正例在`+0x22d394`入口的原实参均为：

```text
X0 = 0                      通道管理对象尚未绑定
W1 = 0x61003c
W2 = 0x470
W3 = 0x806800f3
X4 = COMMON + 0x1060         原申请结果存放位置
LR = av-cam + 0x21df18      原调用者返回点
```

这个零值来自本轮部分构造／队列输入，不能称为相机空指针缺陷。没有把它替换成任意对象，也没有执行申请体或补“成功”返回。

原代码另有极短setter `+0x22c99c`，内容为`str x1,[x0,#0x10a0]; ret`。原factory尾部`+0x226e70..0x226edc`通过该setter，将factory首指针复制给6个对象（起点+0x40、步长0xe518），再给另外2个对象（起点+0x56080、步长0x269b0）。这是**静态下一步来源**：本轮未执行这段完整factory构造、setter循环或管理对象初始化。

对原始前0x300000字节的对齐BL候选扫描找到两个直接调用点`+0x226e84/+0x226eb8`，并核对其循环原字节。该扫描不是全映像可执行性、间接调用或完整所有权分析。后续应查清factory首指针、真实管理对象、原构造依赖和申请提供者，再扩大有界执行范围。

## 16Mbps衔接到哪里

在两组目标原调用链生成的预置状态上，独立调用原查询得到默认24498176。然后独立执行已编译的严格FH私有预置写入器，再独立调用同一原查询，得到16000000。私有256字节副本仅`+0xb0..0xb2`三个字节与原预置不同，原FH描述和源参数保持不变。

这些独立调用使用另一区域的客体栈和明确的control／session／epoch输入，**没有从Sony原请求调用点安装写入器hook**，也没有继续暂停中的通道申请。生产者／消费者完成、共享锁域、代次、数据回退和代码回收没有新增实证。不能将这项结果描述为自动生效的16Mbps主录。

首次尝试在复用stage57测试helper时，用匹配包装对象的长度检查了另一个写入对象的执行范围，导致宿主复核断言失败。两个对象实际独立映射；修正为各自范围后，上述对照通过。失败源码和回执保留，未改固件函数来迁就断言。

## 验证范围与交付

原映像、导入数据、单条客体BL、明确logger测试字节及两个编译对象逐项核对；原source和common描述保持。新观察器不写客体寄存器、返回值或输出。公共调用点的栈均保持16字节对齐，与[Arm AAPCS64栈约束](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst#6451universal-stack-constraints)核对（2026-10-26读取）；通用ABI要求不能代替机身实际兼容性。

完整启用日志、实际loader／MMU／代码发布和缓存同步、真实owner／代次／共享锁、Open／Start／硬件编码、音频／时间戳／长录／温度／原模式兼容、同机健康备份／回读／冷启动／独立救援仍未验收。Sony的[Save/Load Settings](https://helpguide.sony.net/ilc/2210/v1/en/contents/TP1000884354.html)只说明设置文件保存／载入及型号／版本限制，不能拿来充当上述程序与恢复验证（2026-10-26重新读取）。

本轮只做Mac离线分析，未重连UU或控制Windows；相机授权仍为缓存PnP盘点。后续Windows界面继续仅限UU虚拟屏1与原生文件传输，不切实体屏，不使用全局Alt+Tab。目标保持进行中，未释放任何持久写入。
