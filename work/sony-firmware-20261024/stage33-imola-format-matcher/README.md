# FX3 IMOLA 原参数表：FH 主录不匹配，FF 条件对照命中

本轮发现一个具体障碍：**此前目标资源描述符中的`HEVC_MP4 + FH + HD + 29_97 + 42010`，在原IMOLA参数匹配表中没有必要条件匹配项。** 执行原匹配循环的独立片段也返回-1。上阶段“可以构造描述符”不能作为资源格式已接受的证据。

同一原表确实有HD、29.97、HEVC 4:2:0 10-bit的MAIN条目。把质量改为`FF`的明确人工对照，能在一组附加输入fixture下命中原行386；这给出新的候选方向，**不是可用补丁、16Mbps或硬件录制证明**。目标、实机与恢复验收要求不变，仍不放行上机或持久写入。

2026-10-25再次核对Sony经典FX3 Ver.2+的[主录格式](https://helpguide.sony.net/ilc/2210/v1/en/contents/TP1000868279.html)与[录制设置](https://helpguide.sony.net/ilc/2210/v1/en/contents/TP1000868278.html)：公开主录菜单仍未列XAVC HS HD。本轮原程序表属于离线软件证据，不能提升为Sony公开支持或实机能力保证。

## 原匹配循环的条件对照

匹配函数会读0x88描述符以外的+0x88/+0x8c。其实际生产者与机身取值尚未闭合，本轮对它们使用两组明确的人工输入`(2,10)`与`(2,1)`，其它附加字为0。它们只用于揭示条件分支，不冒充真实图像格式或位深。

| 输入描述符 | 附加fixture `(2,10)` | 附加fixture `(2,1)` |
|---|---|---|
| 现有目标MAIN，FH | -1；检查原行3…688 | -1；同左 |
| 匹配代理格式，FH | -1 | 原行607 |
| 原UHD59.94控制，QT150M | 原行431 | -1 |
| 人工MAIN质量FF对照 | 原行386 | -1 |

目标FH的静态必要条件缺项不依赖这两个附加值；只要该描述符进入此匹配器且流类型等必要字段不变，改变附加值不能补出一行。其它描述符的命中结果则明确依赖附加条件；不能把表格中的任意一格直接推广为实机格式接受。

原匹配函数的返回值在0x21ecf4调用者中被检查：-1进入“not found CreateCh Table”分支，合法索引进入行参数分支。本轮独立执行了这个比较/分支，没有执行后续通道创建或全部错误处理。因此这里的未匹配不是被当作成功忽略，但完整资源Open最终如何回复仍未验证。

## FF 对照从哪里来

原API质量转换0x134fcc中，输入22产生资源质量4/FH；输入8与24都产生6/FF。

本轮从已有目标0x98视频包建立一个人工对照，仅把packet+0x82从22改为24。再次执行原timing、描述符构建片段后，所产生0x88描述符仅+0x38的质量字节从4改为6，其余字段与原目标相同。它能在上述`(2,10)`条件下匹配行386。

该视频包是显式反事实输入，尚未证明真实设置模型、原GetCodecQuality、平均码率、查询/剩余时间、菜单及所有消费者能一致地产生它。没有导出参数补丁、修改原固件或将这个数值直接交给相机。下一步需要辨明正确的MAIN质量选择及其与实际码率/QoS的关系，不能只换一个常数就宣布16Mbps成立。

## 资源入口与匹配器的连接范围

本轮还执行原资源接收前缀0x245dac：在已收到数据包与channel0构造字段fixture下，源0x805700f9或0x805720f9、CID0x2103/MID0x0100会经过0x249ad0的通道/MID分派，抵达0x249b1c首个诊断之前。错误CID、未识别源分别走原诊断分支。包未改变，真实注册、消息输送和源身份未验证。
