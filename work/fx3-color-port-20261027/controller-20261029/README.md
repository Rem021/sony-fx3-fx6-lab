## 从原控制器入口处理连续 TAR

使用原预置更新库 `libupdaterbody.so`、当前 AP 字符串库及 XML 原库，来源哈希与上一阶段一致。原 UpdaterBody 构造和 Execute 入口开始后，依次执行目录和对象构造、初始插件请求、原 XML 配置读取、TAR 解析、编号分组切换、原文件提取、配置收尾回调及后续键／队列／插件分派。原函数体 135 个，保存 20 个复核片段及各自原件哈希。[原指令契约](controller-contract-results.json)

输入是 5,120 字节的合成内存 TAR，普通测试文本权限 0644。输入缓冲区只在 RingBuffer 的 peek／advance 虚槽处承接指针和游标；原 `PackedFirmwareBuffer::GetCurrentBlock`、正文读取及向上补齐到 512 字节的跳过逻辑实际执行。输出目录和文件均为内存接收器，提取后的 XML 字节直接进入同一 guest 的内存 FILE 读取，再由原解析器处理。没有把配置回调直接作为宿主调用来替代控制器分派。

| 条件 | 原控制器结果 |
|---|---|
| 配置组后切换到新编号组，再处理匹配文件 | 在输入偏移 3,072 调用原配置收尾；提取三份文件后，到达输入驱动的 `system()` 请求入口 |
| 匹配文件仍属同一编号组 | 到输入偏移 4,096 才在组末读取配置；不追溯触发此前的匹配文件，最终停在 Join 入口 |
| 配置 XML 损坏且切换分组 | 原配置回调到达异常边界 `0x30002`，未处理后续触发文件 |
| 第一个 TAR 头校验损坏 | 原头解析到达异常边界 `0x30002`，未提取文件 |

有效案例中原提取结果为 27 字节普通文本、112 字节补充 XML 和 14 字节触发文本；正文、目标路径和哈希均从内存接收器回读。请求中的模块名是无执行权限测试文本所用的 `probe.txt`，没有真正执行它，也没有证明它能成功作为进程运行。[四组控制器结果](controller-guest-results.json)

## 启动条件仍是明确替身

以上连续控制器流程的构造参数为 bool 1、action mode 6，并使用合成空环境、固定时间、单线程 mutex 和内存文件系统。`/tmp_updater/UFP` 与 `/root/IAMUPDATER` 明确设为不存在；这是提供给原 stat 的夹具，不是机身读回。原标志分支因此走附件条件，没有发生真实 mount 或标志写入。

原初始插件会检查并请求绝对路径的预置 `startupdate.sh`。本轮核对原脚本字节并让内存 stat 看见它，但在 `system()` 入口提供了**明确伪造的返回状态 0／errno 0**，没有运行该脚本。只有这次启动结果得到替身；后续输入驱动的系统请求立即停止，不返回伪造成功。

这使本轮能验证启动条件满足后原 TAR 控制器的时序，不能证明实际启动准备、权限、PATH 解析、线程 Join、更新完成、恢复或外部输入准入。原 FirmwareInformation 参数使用未消费的合成存储；未运行依赖它的完成回调。

## crypter 原参数选择了什么

从 SHA-256 `f2e7d27602e3f7b236fc41dd93fccf53ba24f0793fd454e7fec171ae378beca7` 的原 UFP 库 `0x151b8` 直接读取 24 字节参数表和两个原字符串，得到 `/usr/bin/crypter.elf`、`/tmp_updater/Firm.dat` 和空终止项，没有 `chunk=full` 参数。

原 crypter SHA-256 `638eeba2fc720fa807f62fb6f1c65c72e106ed164d16747b0c56e40512c78402`。按 ELF 零初始化 BSS，在明确的零弱 gmon／JCR 绑定下执行其 DT_INIT 和唯一 init-array 函数；两者均保留 FILE_CHUNK 为 0。再执行原 main 的参数循环和虚槽调用：

| 参数夹具 | 原 main 的结果 |
|---|---|
| 原 UFP 参数表 | 请求 Initialize(0)，路径为 `/tmp_updater/Firm.dat` |
| 显式 `chunk=full` | 请求 Initialize(1) |
| 显式 `chunk=fdat` | 请求 Initialize(0) |
| 没有文件名 | 返回 1，不调用 Initialize |

这些检查在初始化虚槽前停止；manager 对象／工厂、框架初始化、格式化和 stderr 输出是显式替身。没有执行完整依赖启动、原 manager 初始化、输入文件访问或当前进程读回。原 main 对 BSS 的实际指令写入和所有替身均有记录。[四组参数结果](crypter-arguments-guest-results.json)

原 manager 的 Initialize 在正常完成时把参数写入对象 `+0x48`；原 `verifyFile` 只在该字段为 1 时进入它内部的全文件 CRC 分支，其他值在这个函数中返回真。这两处是本轮重新保存原字节的**条件性静态契约**，没有执行完整 Initialize 来证明成功。模式 0 不等于没有头部、块级或上层校验，也不是 SD 更新引擎 RSA 尾签名的绕过。[条件性契约](controller-contract-results.json)
