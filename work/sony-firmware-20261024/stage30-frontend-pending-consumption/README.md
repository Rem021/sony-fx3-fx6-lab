# FX3 前端待处理消费与共同 timing 接收端

本阶段把原前端Open待处理槽的消费接到了下一层延后事件：**前端计数归零后，原0x98视频参数仍被下游持有，处理器busy和延后计数仍为1。** 因而前端计数、局部返回值都不能单独作为编码完成或恢复安全点。

同时定位到 `SET_REC_FORMAT` 与正常Open共用的 timing 状态机句柄，后续参数协调可以沿具体接收端继续追。7个场景通过；未执行实际配置转换、任务钩子、timing处理、资源、硬件编码或恢复，完整目标保持未完成。

## 待处理槽如何被消费

原前端状态入口表0x35c868中，数值状态2的入口片段调用0x13d204，状态8调用0x13d2fc。它们都从前端+0x348的待处理计数取出请求指针，先递减计数并更新读索引，再重新提交到前端Open状态机0x13d8b0。

入口钩子中此前还有诊断调用，本轮没有跳过或stub该调用来声称完成真实状态转换。对照分两段：

1. 先实际运行原局部Open入口，在状态0的fixture下产生待处理事件。
2. 保留该段实际生成的数据，明确把第二段前提设为“配置已进入数值状态2或8”，再运行原消费函数。使真实状态转换完成的事件和钩子没有执行。

4个场景覆盖目标HD、原UHD控制、非法codec/frame在state2的消费，以及目标在state8的消费。另一个空槽对照确认该消费函数直接返回、无写入；它不是全局空闲验证。

## 前端归零，下游仍待处理

消费后的Open重新进入同一个前端状态机。动作处理中再次调用视频子事件0x13dd50时，该状态机已经busy，因此原子事件代码会：

- 将原0x98字节视频参数复制到状态机+0x290。
- 设置+0x284的待处理标志，向下游functor队列追加状态机+0x278的指针。
- 返回后继续把Open转交编码状态包装器；本轮在任务钩子之前停止。

此时目标、UHD和非法枚举的对应场景均观察到：前端待处理计数0，状态机下游计数1，busy和视频待处理flag均为1。两处前端视频副本及下游0x98副本保留原字节。没有执行下游functor、任务钩子或硬件操作。

在state8场景，下游副本完成之后，原动作又把源参数+0x88置1。因此这时源参数的该字节为1，下游副本保留此前的0。这是已核对的操作顺序，不据此判断固件缺陷或两份参数应该完全一致；不同消费者语义和后续处理仍未知。

恢复、替换或退出验证必须覆盖整个持有链：前端槽、当前动作、下游functor与副本，以及仍被引用的原参数和缓冲区。读到前端计数0，不证明它们全部退出。本轮只增加该要求的原指令依据，没有实现并发安全点、引用登记或恢复器。

## SET_REC_FORMAT和Open的共同接收端

原索引0构造绑定的 `sfmc_enc_timing_normal` 接口中：

| 请求路径 | 原接口/回调 | 后续处理器 |
|---|---|---|
| SET_REC_FORMAT | ext-ISP动作0x13bb78 → timing虚表+0x108 → 0x194ba8 | 0x19bd84 → 0x19bda0 |
| 正常Open | owner动作0x17b794 → timing虚表+0x10 → 0x193f24 | 时钟查询后0x19841c → 0x198438 |

两条回调都从timing对象+0x478取句柄。两个独立的SET_REC_FORMAT入口对照确认原接口分派，将未赋予语义的输入+c0字复制到timing+0x34，并把原参数指针交给同一句柄；在0x19bd84入口停止。真实句柄/当前状态、该字语义、完整参数解释和配置动作没有执行。

进一步原静态地址已保存在[下一接收端锚点](next-receiver-anchors.json)：正常Open处理表0x371ba0的数值状态2动作到0x194de8，该函数复制0x98参数后调用0x1454f4/0x145530；SET_REC_FORMAT处理表0x3753e0的状态0动作0x1a1634会准备另一份参数，再调用0x1956e0。这些新锚点为只读反汇编，没有新增运行或格式接受证明。

后续应在这个共同timing消费者里核对实际配置顺序、缓存/字段持有、参数合并与资源请求，不能仅凭“使用同一对象”就断言两份配置已经一致。
