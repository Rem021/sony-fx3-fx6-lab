# Remote DMM 0x1d9：人脸注册准备缓冲审计

**0x1d9 是人脸注册准备路径持有的 remote DMM 单元，AP/CP 配置均映射 extent 0x223（547），单候选槽 0x64000（400 KiB）。AP82 的失败是该单元未被模型支持，并非已到编码器。** 捕获请求 option=0，语义是仅分配；因此不能照抄提示音 option=1 的“分配并打开”回复。原指令定位：AP `2d1b67c..69c`、`2e4f488..4a8`；配置文件偏移见下表；AP82 serial 行 23512–23525。本审计未运行 QEMU，也未改原件、runtime 或 STATE。

入口：[audit_dmm_unit_1d9.py](audit_dmm_unit_1d9.py) → [dmm-unit-1d9-proof.json](dmm-unit-1d9-proof.json)。proof 保存固定 AP/CP SHA256、整段逐指令原字节、24 处关键指令断言、配置原始行、原 DMM 内核符号/重定位、AP82 FDT 全部保留范围、精确模型回复及运行日志摘录。AP 为 ELF image VA；原 `dmm.ko` 是 ET_REL，以下 `.text+offset` 是节偏移，**不是装载后 VA**。工具方法核对于 2026-11-02：[Capstone 官方 Python 文档](https://www.capstone-engine.org/lang_python.html)；私有协议判断均来自本地原件，公开文档不作为 Sony 协议证据。

## 调用者、用途与时序

`2d1b6a0` 是 `2d1b580` 内一次调用的返回地址；函数日志名在 VA `3937760`：`void model::sequence_mode_transition::common_preparation_sequence_of_face_registration()`。`2d2fee0` 同样是返回地址，属于入口 `2d2e950` 的 `virtual void model::sequence_mode_transition::run()`（名字 VA `3937540`），实际 `bl 2d1b580` 在 `2d2fedc`。静态直接分支扫描只找到这个 common-preparation 调用点；退出对应 `2d2fed0→2d1df2c`。名称由原日志字符串和 ADRP/ADD 引用闭合，不冒称已恢复调试符号。[AP `2d2e968..990`、`2d2fecc..fee0`]

AP82 同一 TID327 先有 `FX3_UUD_FACE_RETURN`（serial 行 23508），再发生本次 remote 分配。这里已进入 `run()` 的后续人脸注册准备，不能把整个失败归入前一个 UUD reset 函数。触发条件是 `2d2f290..2b4` 对原状态调用 `2d139e0`，返回非零后分支到 `2d2fed8`；该叶函数在值2/3返回真、0/1/4/5返回假，但本次状态的具体数值未从运行数据确认。[AP `2d139e0..3a0c`；AP82 serial 行 23508–23525]

## AP/CP DmmCfg 几何与物理约束

配置偏移是**文件偏移**，配置没有 image VA。解析器按80B组头、20B行、单位表及44B尾版本恰好消费两文件；记录布局与原 `dmm.ko .text+bd48..bdd8/be68..bf50` 的配置读取一致。以下候选行数是静态几何，动态规则选择未执行。

| 单元 | AP单位表 / 规则行 | CP单位表 / 规则行 | extent / 候选槽 × 大小 |
|---|---|---|---|
| **1d9** | e52c / 1cc，组17c(type29, selector1) | 9934 / 1e0，组190(type31, selector1) | **223 / 1 × 64000**（400 KiB） |
| 1da | e53c / 1e0，同上 | 9944 / 1f4，同上 | 224 / 1 × c800（50 KiB） |
| 1db | e54c / 13c4，组12e8(type34, selector10) | 9954 / 208，组190 | 225 / 1 × d100（52.25 KiB） |
| 1dc（本地临时） | e55c / 398，组17c | CP单位表无1dc | 226 / 1 × e220 |
| 70817（提示音） | e254 / 1b1c..1b80 | 9564 / 1798..17fc | e7 / **6 × c800** |
| 63a（既有模型） | 100f8 / 24cc、24e0 | a854 / 201c、2030 | 700 / **2 × 80000** |

两份1d9原始行均为 `[00000000,00000008,00000223,00064000,0000010f]`，单位属性0。70817/63a行+4为7，1d9/1da/1db为8；这些字段与flags10f的原厂对齐含义**未证实**，不把8说成8字节/256字节，也不把10f说成64KiB对齐。下述64KiB仅是VM预留选择。[配置上述偏移；AP `2d1b67c` 固定unit；原内核 `.text+9ff8..a0b8` 取得root范围]

AP组type29对应根行50：原始 `[24000000,00040014,0000001d,05b00000,00000001]`，按原AP内核 `.text+a09c..a0b8` 的 `lo32 + (u16@+6 <<32)`，根范围为 **424000000/5b00000**；CP组type31根行50为 `[10000000,00080014,0000001f,04200000,1]`。70817分别归AP根b4/CP根8c，63a归AP根f0/CP根8c。这些是所属根范围与原字段，**不是已经定位到1d9的精确原厂槽地址**；CP私有解析/物理域转换、动态模式及对齐未证实，禁止机械套用AP转换器去宣称CP原始物理地址。[proof `configurations.*.roots`；`.text+a09c..a0b8`]

## 最小VM合同与预留建议

建议为三块remote新建 **AP 41dd00000/90000，结束不含41dd90000**。单独1d9需至少64000，按64KiB粒度占70000；连同接下来必经的1da/1db共占90000，实际可用容量合计7dd00。保持local分配走原内核配置，不能把remote与local句柄/地址混为一处。[申请顺序 AP `2d1b644..bc4c`；ICDT `2d1d3b0..4fc`]

本轮已对 **AP82冻结guest.dtb**（SHA d808f668…）做二进制解析：RAM为 `[400000000,540000000)`，共5GiB；检查FDT reservation map、reserved-memory（为空）及全部16个memrsv，建议区均不重叠。除题设四区外，也避开 **41dc00000/10000** 观测区；既有大区包括410200000/9e00000（到41a000000）、420000000/4000000、424000000/c400000、430400000/cfc00000。此为**放得下**的离线证明，尚未把新区加入FDT或kernel memrsv；集成时必须同时建立两层保留并读回。[proof `fdt`、`reservation_proposal`；AP82 serial 行9–24/46；协议地址使用 AP `2e4f23c`，不代表原CP物理区]

| unit | 全局remote索引 / 初代句柄 | AP backing / CP wire | 可见容量 / 保留stride |
|---|---|---|---|
| 1d9 | 8 / 8408 | 41dd00000 / 1dd00000 | 64000 / 70000 |
| 1da | 9 / 8409 | 41dd70000 / 1dd70000 | c800 / 10000 |
| 1db | 10 / 840a | 41dd80000 / 1dd80000 | d100 / 10000 |

这是**软件模型提案**：0/1留给63a、2..7留给70817，共用remote句柄命名空间。句柄为 `8000 | generation<<10 | index`，index<3ff；代次1..31后回1沿用现有模型，重新分配同索引初次8408、第二次8808。低10位/5位代次来自原内核 `.text+9fb8..9fe0`，bit15 remote来自AP `2e4f2b8..2c4`；原CP代次绕回代码未定位，不能称原厂同值保证。CP wire=AP backing−400000000沿用现有虚拟模型，不能称原厂映射。保存allocated、generation、opens、unit、extent、容量和实际传输元数据，拒绝过期/错误域/越界；不能只在op20按unit识别，其余按handle分派。[原内核上述节偏移；AP `2e4f2b8`；既有helper见proof `existing_models`]

本次op20是 **allocate-only/open_count=0**（AP `2e4f490` 固定w2=0）。原内核 `.text+5558..5560` 先分配，`.text+5648..5660→5280` 处理option；`.text+528c..52a4` 在option0直接返回，只有option1/4调用Open。回复+8段数=0，+24地址/+32容量=0是本提案的确定性清零约定；原CP未使用填充的随机/残留字节未证实。以后802a返回实际单extent，option1/op21才增加opens并返回段数据。[AP `2e4f0a8..cc`、`2e4f23c..250`；原内核上述节偏移]

## 无硬件VM的诚实边界与致命性

DMM本身可诚实提供独立字节存储、槽几何、句柄代次与生命周期。ICDT应校验两端活句柄/代次/方向/offset+length，**真实复制local注册数据**到remote backing，并遵循原48B请求及24Bcallback/context/status完成合同；外层等待在AP `2e15ad8..af4`，只回send成功会挂起。既有提示音模型只允许70817且静音清零，不能直接拿它给1d9伪造传输成功；缺少或校验失败的人脸项让原AP代码自然过滤，不伪造有效人脸。[AP `2d1ca40..64`、`2d1d3b0..3e0`；ICDT先例README与AP `2e15a18..b8c`]

随后属于CP侧人脸注册/IMAGING路径：原AP发往90060197的0207/0206，0206明确带1db句柄（`2e41e48..90`）；本次1d9经ICDT上传且保留，但**尚未把1d9绑定到具体CP硬件读写指令**。本函数未见GPE或编码器调用，也没有摄像帧/编码输出证据；不能把注册缓冲叫作可用图像/编码器DMA。若后续请求涉及未实现的识别/图像处理，最小诚实处理是保留登记元数据/字节、明确能力不可用，不产生识别结果、帧或编码成功；静态证据不足以给未知CP计算命令设计成功回复。[AP `2d1d3e0/4fc`、`2d1dc18/2d1ddc0`、`2e41e20..1f88`；proof `unproven`]

致命性分层：

- **已证实致命**：AP82 unsupported unit status−3，serial行23525后行23831–23832触发原 `notify_model_system_error`。1d9分配失败分支 `2d1b6a4→2d1be60..bf34`；ICDT失败分支 `2d1d3ec→2d1d3f0..498→2d1ce7c` 同为assert处理。不能用重试/吞错绕过。
- **文件错误不是同一类致命失败**：`facerec`缺失/短读/校验错走 `2d1ca78/ca90/ca68` 的登记过滤；`facedmy`缺失/短读只日志并继续 `2d1d868..8d0`。这不证明缺文件时上传的尾部字节有定义。
- **CP处理失败是否致命尚未闭合**：所示0206/0207 wrapper在send后直接把输出写0，无同步收包（`2e41e90..94`、`2e41f78..7c`），所以CP未响应不会通过这两个wrapper立即报错；后续回调/同步注销是否等待、CP错误如何上报仍需单独审计，不能宣称CP硬件缺失全程非致命。
