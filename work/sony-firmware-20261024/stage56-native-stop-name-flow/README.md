# FX3 7.02：默认空名称、StopCmp 与媒体资料传递

这轮把上一轮默认分类 `0x97` 的名称用途推进到原代码运行验证：在明确声明的默认查找表、名称向量和录制记录输入上，官方原名称函数正常返回 `0`，输出空字符串；原结束回调把它复制到 MAIN／PROXY 结束记录，MAIN 的媒体资料名称复制后缀继续保留空字符串。已追到的这条调用路径属于 **录制结束信息**，不是编码器 Open 准入检查。

**这不证明空名称对所有消费者无害，也不证明文件已正确写出。** 全局向量构造、实际录制、锁、记录查找、容器关闭／提交、XML／目录／播放器读取以及备份恢复均未完成。目标仍是主录 1920×1080、HEVC420 10bit、约16Mbps、30000/1001；精确30.000fps保持单列。没有相机或 Windows／UU 操作，没有新固件、模块或刷写产物。

## 本轮新增证据

1. 官方默认名称初始化在 `libmpr.so:0x8ef38` 把枚举 `0x97` 与 `0x2cfb4f` 的空字面量配对。全局堆分配／完整构造不在本轮执行范围内；客体中声明一个对应的单项向量，由原 `0x2428a4` 构造其中的短字符串对象。
2. 同一个客体内执行原视频／音频初始化及完整 `0x115fec` 元数据转换，候选 `[VPC6,VQuality6,Frame3]` 生成 HD、30000/1001、raw16000。原 `ConvertVideoCodecTypeName` 全函数调用原分类器，实际返回分类 `0x97`，经原 C++ 字符串操作和原 `strncpy` 产生128字节空名称，正常返回0。raw16000是元数据值，不是测得的成片码率。
3. 名称目的地为可选通知记录 `+0x64`。原调用者 `0x120784` 在调用后不检查该函数标量返回值。生产者 `0x120b24` 将事件 `0x40000001`、UID1和通知记录交给已登记回调。
4. 原工厂指针加载、独立参数打包和独立登记存储片段绑定回调 `0xda760`。原间接调用真实进入该函数，在首个诊断前停止。另一个明确标注的独立后锁入口，经原事件分派进入符号 `RecvWriterEvtStopCmp`，同样在首个诊断前停止。**没有跳过日志／锁并假装返回成功**，没有运行完整工厂、真实 Stop 或完整回调。
5. 在声明的记录归属输入上，原 `RecvWriterEvtStopCmp:0xda4b0` 后查找片段执行 UID 分支：MAIN1 写记录 `+0x80`，PROXY5 写 `+0x1c0`，均为 `strncpy(...,127)`；错误 UID2 在诊断前停止，记录没有改变。未执行实际列表查找、记录归属验证或后续完成处理。
6. MAIN 独立媒体资料复制后缀 `0xd52bc` 用原 `memcpy` 将记录名称的65字节复制到 clip-info `+0x6ac`。此前 `+0x6a8` 的 codec 标量是另一条生产路径，本轮未执行其生产者；对照仅证明该复制后缀不改变已声明的标量字节，不能推出全文件格式无关。

## 原运行库与验证方式

从同版、已固定哈希的官方 ext2 镜像读取两个普通文件及对应符号链接元数据，不挂载镜像、不执行宿主载荷、不创建符号链接：

| 原件 | SHA-256 | 客体显式基址 |
| --- | --- | --- |
| nflasha7 `/lib/libc-2.25.so` | `f9104526eb7e5d2ea533c1a209bb0b83e69367f569e4c966895c8e106e6382c9` | `0x14000000` |
| nflasha15 `/lib/libstdc++.so.6.0.22` | `28f2d082aea5206c42ba15664f39e2eaf7febed8f6264305e7e16aa44c878389` | `0x16000000` |

这些是实验地址，不是相机实际装载地址。只部分解析白名单函数和已定义符号／相对重定位，所有原可执行段在运行后逐段与文件比较。原 `strlen`、`strnlen`、`strncpy`、`memset`、`memcpy` 与六个原 C++ 字符串函数执行；未知执行、系统调用、堆分配均拒绝。链接 hook 仅将 PC 指向原函数，绝不把 PC 写成 LR、伪造返回值或补写输出。观察 hook 不改变客体结果。

运行包含 **50段有界原执行**：28次正常原返回，21次预先声明的边界停止，1次长名称对照在原分配函数入口前拒绝。四组名称结果：

| 输入 | 原名称输出 | 后查找 MAIN／PROXY | MAIN资料名称 |
| --- | --- | --- | --- |
| 官方空字面量，旧值A5 | 空 | 127字节清零 | 65字节空 |
| 官方空字面量，旧值C3 | 空 | 127字节清零 | 65字节空 |
| 人工短名称 `CONTROL`、匹配key97 | `CONTROL` | 复制该名称并补零 | 保留 `CONTROL` |
| 人工短名称、错配key96 | 空 | 127字节清零 | 65字节空 |

人工名称只是证明查找／复制实际工作，不是 Sony 的正式名称或拟刷入修改。第128字节在原 `strncpy(...,127)` 外保留种子；这些短名称在首字节或短名称末尾已有 NUL，不能据此宣称存在实机越界／未初始化缺陷。错误 UID 对照均不写记录；PROXY 对照没有被当成目标 MAIN 主录证据。

首次运行在人工非空名称对照进入跨库 `memcpy` 时因实验链接器未识别 libstdc++→libc 的 PLT 停止。修正为按调用方统一查找 PLT、按白名单解析原被调库后重跑，原代码／数据输出未修改。失败源和回执保留在 `run-20261025/`；通过结果在 `run-cross-library-link-20261025/`。

## 对方案的影响与未完成项

由这些局部证据可推断：上一轮默认分类97不足以证明编码启动会失败，目前没有依据为“通过准入”将 HD 伪装为 UHD 名称。不能把这个推断扩大为容器关闭、媒体目录、XML、回读或播放器兼容性已通过；名称下游仍需在真实文件方案中验证。

下一步优先解决已经明确的上层 VQuality6／raw16000 与资源 FH 不匹配问题：保持真实16Mbps身份，研究受限的资源质量映射和私有预置应用，并核对查询、缓存、封装一致性。上一轮人工上层质量8会生成 raw25000 并进入原诊断，不能直接整项替换。完整应用到 writer／当前 MAIN 的绑定、同步／代次、Open／Start／HAL、真实 HEVC 文件、音频／时间戳／长录／温度及既有模式回归仍全部待验。

同机健康备份、受限恢复器、原字节回读、冷启动和独立救援入口均未验收。官方固件代码哈希不能替代用户机身字节或校准数据。Windows 恢复连接前保持等待；现有相机授权仍仅缓存 PnP，只读盘点以外不执行。16项原始要求与授权不因本轮离线通过而放宽。
