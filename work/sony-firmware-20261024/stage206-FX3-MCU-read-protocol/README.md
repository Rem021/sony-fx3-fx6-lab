# FX3包内MCU读取分支、外设副作用与SIO配置来源

2026-10-29。**已从7.02包内MCU原件绑定InitCom的0x16读分支：128字节帧、小端地址、6字节头、最多120字节数据，回复保留头并另算尾部CRC。官方AP程序的SIO通道/GPIO参数来源也已定位到3个Backup配置ID。** 这推进了参考诊断协议的FX3适配，尚未证明用户机身在拟定入口运行此处理器，也没有完成真实通信、备份、恢复或首刷。

上一轮205提供了硬件资源与当前包MCU字段的新增证据，归类为progress。本轮新增的是具体读分支、通用外设写入、配置来源和回复时效边界，也归类为progress。16项完整要求、已有授权与持续目标不缩减。

## 已绑定的读取路径

| 环节 | 包内原码证据 | 限制 |
| --- | --- | --- |
| 接收 | InitCom按128字节接收，校验前126字节与尾部16位值 | 要求传输状态成功、校验相等及正确运行状态 |
| 命令 | `0x4F80`比较0x16；地址经`0x38784`按小端组装 | 不是证明任意MCU状态都接受此命令 |
| 读选择 | 长度字节bit7清零，低7位范围检查不超过120 | 仅核对读分支，未实现/放行写分支 |
| 数据 | 先清空回复的120字节数据区，再从目标地址复制指定长度到帧+6 | 地址可达性、实际RAM及并发一致性未测 |
| 回复 | 复制128字节当前帧至发送区；命令16序列化绕过状态重建，只封CRC | 在后续循环交付；不等于已经发送或主机收到 |

18份选定原始代码/数据范围、Thumb分支位解码、ARM64原码参数与CRC关联见[读取合同证明](MCU-read-contract-proof.json)、[复核程序](prove_read_contract.py)。线性扫描的locator包含文字/常量池造成的伪指令，未用于声明整段可执行控制流。

参考[A7 IV Darwin实现](https://github.com/DavidBuchanan314/ILCE-7M4-RE/blob/e85e137fc3b88b7cb26e69faa9f1304184678ff7/payloads/fastboot/src/darwin.c)使用相同读帧字段。官方FX3 AP软件CRC的初值0xFFFF、多项式0x1021、126字节覆盖长度及位递推也对应。自己的两份宿主机语义模型比较了4608个状态/字节组合和5种完整长度输入，结果一致；没有执行原AP/MCU代码。[模型结果](CRC-semantic-model-results.json)

**MCU端仍通过0x40039000外设产生CRC。** 以上软件对应及模型检查不能证明其实际外设配置、时序、校验结果或链路已经通过。

## 不能把整次通信称为无副作用

通过CRC后的命令在分派之前，调用`0x6450`，向`0x40011000`外设的+0xC00和+8等偏移写入。相邻代码也设置该外设的加载/控制字段；“硬件看护刷新”是据此作出的解释，物理效果未测量。

这是原接收路径的公共动作，并非0x16内存读分支主动修改目标数据，但足以否定“整个协议只有内存复制、完全没有寄存器写入”。本轮没有执行这些动作。它也没有证明205轮的虚拟计数表被重新装载，或参考载荷因而能够长期运行。

此前所称“当前MCU原件”在这里明确为**当前7.02公开包的组件**；实际机身MCU/ROM身份及执行状态仍未读回、未确认。

## SIO与GPIO需要目标配置

官方7.02 `ud_darwin_firmup.elf`的真实导入绑定显示：

| Backup ID | 所选原码中的用途 |
| --- | --- |
| `0x00F900D4` | 与`/dev/sio`及`%d`拼接，形成通道设备路径 |
| `0x00F900B1` | 作为`UdtrGpioOpen`的第1个配置参数传入 |
| `0x00F9006D` | 作为`UdtrGpioOpen`的第2个配置参数传入 |

这里保留参数的准确位置，没有在未核对提供库前将它们自动标成特定端口/位号。实际值未读取，也未默认成A7 IV参考中的channel0、port4、bit2。当前Ubody文件系统没有名为GPIO/Gpio的提供库；缺少提供库语义与机身值，不等于接口不存在。

既有官方包目录还列出11份经典ALCIN及11份ALCIN_HIBIKI2默认配置镜像，可能帮助继续离线解释这些ID；**尚未解析其格式/值，不能选择其中一份充当同机Backup。** [候选目录](Backup-template-candidates.json)绑定到此前完整成员盘点。后续先核对这些公共模板和`libul_GpioCtrl`的实际提供方，能从公开资料解决的继续离线完成。

## 回复的时效仍需单独处理

参考读取函数只比较CRC和请求头前6字节。InitCom会清除请求的数据区再填入读结果，没有回显本次请求的独立nonce。对于重复的同地址/长度请求，迟到的旧回复可以有相同的头和有效CRC；这些条件不能单独证明它属于当前请求。

本轮没有把消息格式吻合、CRC模型通过或头相等写成“当前机身状态已读到”。后续传输设计必须说明如何处理前一轮回复、严格时效与不确定结果；不会直接将现有匹配逻辑用于恢复写入验收。

本轮没有更改工具0.4、native10或195固定方案。195仅主机root01仍未具体批准、未启动、未重问。相机、USB、MCU、root、管理员、Windows、UU、驱动和GUI操作均为0；`goal_complete=false`、`persistent_write_release=false`。独立进入、同机boot0/p1备份、逆写/冷恢复和MAIN 1080p29.97 HEVC/长录验收仍开放。
