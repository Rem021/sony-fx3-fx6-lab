# FX3 原进程对象句柄与非零退出标记原型

2026-10-30。**已做成监管者自己传出proc目录FD、固定非零成功退出、外层按原对象观察的自写ARM64链条；共享同一模拟进程对象的两端执行通过。它解决了一类外层数字PID误认路径，但父端原生接收/真实隔离入口和完整来源绑定仍未接通，整体准入未通过，不能投放相机或刷写。**

本轮全部原始固件只读取及反汇编；运行的是Mac编译的自写C和Unicorn中的自写ARM64。Linux内核、VFS、proc、进程、凭据、时钟、SCM_RIGHTS复制和Sony回收行为均为明示模型，没有实际Linux进程、相机/USB/缓存查询、管理员操作、认证、上传或固件写入。

## 本轮关键发现

保存的7.02内核在proc inode中持有具体struct pid引用，目录相对查找和stat读取沿这个对象找task，不重新按数字PID寻找。inode驱逐时才put_pid，因此旧目录句柄不能因为同编号分配给新对象就自动指向新任务。这类目录FD保留的是PID对象，不是永远存活的任务。

**stat的0不能作为成功证据。** 保存代码确实先做ptrace_may_access，未获准时把末尾exit_code字段输出为字符串` 0`；允许时才输出task->exit_code。[Linux stat文档](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)说明该字段格式；本轮结论还绑定了实际原指令。[零过滤反例](zero-filter-counterexample.json)中，真实信号9或exit68都可被显示成0。

因此只给自写监管者定义**正常exit42**为完成标记，原始内核退出状态为10752。它只在内部工作器状态10之后由固定_start映射产生；失败2/4不映射。外层只接受原对象为Z、字段52精确10752，随后同一目录对象的task查找脱离。权限过滤成0、信号终止、普通exit0或别的非零退出均不能满足这个条件。该规则不用于解释Sony自身错误码，也不意味着任意非零就是成功。

[58项静态核对](proc-anchor-contract.json)固定7个相邻符号代码范围和12段Linux v4.9.337参考源码，覆盖PID引用保存/释放、对象查找、保护字段的零过滤和退出状态存取。原内核EXIT_ZOMBIE是32，EXIT_DEAD是16；相邻符号范围不是ELF函数尺寸，参考源码不是精确重建的Sony构建。

参考正常源码在exit_notify之前调用exit_files；本轮没有证明原生全部路径的exit_files支配关系。**PID对象已脱离也不表示内核所有退出后清理与引用都已结束。** 本轮结果明确只是原对象的退出标记及task脱离观察，不能替代全部FD/源访问归还、USB恢复或整条备份任务完成。

## 已实现与执行的部分

[collector-anchor.c](collector-anchor.c)保留237的内部监管/空操作，入口先检查PID/TID、父关联及已屏蔽信号，再打开自己的/proc/self，把目录FD通过唯一SCM_RIGHTS条目和私有HELLO发出。它关闭发送方的目录FD及外层通道后才进入内部核心。固定父PID321、通道53和消息关联仍是夹具配置，真实创建/关联还未建立。

[observer.c](observer.c)只相对已给定目录FD读取stat，不使用/proc/数字PID路径，不调用wait或发信号。它核对procfs/目录与文件元数据、PID/PPid/单线程/起始时间，完整读到EOF，解析52个字段；进程名可包含空格、右括号和换行。观察成功标记后，还须看见该对象的task查找脱离，并完成自己拥有的FD关闭。活进程、未回收僵尸、看不到标记或其他错误保持HELD。

## 两个剩余反例仍然有效

如果输入的FD其实来自同PID、同起始时间的外国对象，观察器仍可能接受外国exit42；因此FD来源必须由父端真实创建、私有通道和任务绑定证明，不能只核对字段。当前自发送端已实现，父端C接收、权利清理和完整原生桥还缺。
