# FX3 CP 完成标志的公开 AP 对照与配置分支（2026-10-30）

**找到此前缺少的发送端对照：公开 A7 IV AP 启动映像包含两个标志的生产代码，数值和目标地址均与 FX3 原 CP NOR 消费端一致。** 原配置行的两组独立执行又确认，`DmmCfg.bin` 的 `0x05000000` 在这条参考转发片段中被跳过，`tomco.txt` 的 `0x07000000` 才进入文件查询边界。它改变了配置来源的调查方向，但尚未证明 FX3 的真实交接、配置到达或像素读取。

用户恢复持续目标后，本轮重新核验外盘 UUID、项目入口和[上次受阻封存](../full-goal-blocked-audit-20261029/README.md)14个文件；旧阻塞计数不带入恢复后的审计。另一任务新增的[阶段204](../../sony-firmware-20261024/stage204-public-AP-boot-reference/README.md)提供了此前本任务未取得的公开 AP 原件，成为本轮新的分析输入。没有重跑另一任务的提取、解密或设备程序。

## 来源和适用角色

AP 对照为维护者公开的 [A7 IV v2.00 eMMC/eSRAM 原件](https://github.com/DavidBuchanan314/ILCE-7M4-RE/blob/e85e137fc3b88b7cb26e69faa9f1304184678ff7/emmc_boot/README.md)，固定提交 `e85e137fc3b88b7cb26e69faa9f1304184678ff7`。本轮只读已保存的190,464字节明文 SRAM，核对 SHA-256 `2e37d90bc8f489db13a0319a3e7f8f1e746921c380484147b922957af3e95d74` 及 Git blob SHA-1；没有读取 ROM 秘密、派生密钥或再次解密。

目标侧仍是经典 FX3 7.02 原 `loader_nor.bin`，101,888字节，SHA `4358c839cfb1f22d5eb4e53d67817c42c4e877ba8b0aff375d355ce6294c4942`。根据当前官方写入路线，它属于 **CP NOR**，不能把它的模式或初始化直接当作 AP 独立恢复。

标志和64位地址由原 MOVZ／MOVK 指令组成，不是搜索明文字节所得。独立立即数字段检查与静态反汇编一致。参考传输入口为 `0xfe05d884`，本轮没有执行它。

**这是跨型号的接口对应，不是已经找到 FX3 自己的 AP 发送者。** 没有提供目标 AP boot0 或实际控制器状态，尚未证明调用会完成 PCIe／数据传输、CP 会收到标志，或正常启动会经过这些代码。参考 escape 例程的普通返回尾部还显式把 W0 置零，不能单凭该返回值确认之前的数据与标志已送达。

## 为什么标志不能证明 DmmCfg 已装入

参考装载／转发循环以 `0x90` 字节步长消费表行：首两个64位字段、`+0x10` 分区号、`+0x14` 标志、`+0x18` 路径，与已恢复的 FX3 原默认表布局相合。上述附带地址只在特定高位标志分支被提交，不能直接解释为 DMM 配置到达。

本轮使用此前已封存的 **原 FX3 CP 默认表** 两行作为明确的分析输入，没有改写字段或给函数替换成功返回。它们不是当前机身所选记录，也不是 A7 IV 运行时捕获的表。

| 原行 | 原标志 | 从 AP 参考 `0xfe052d4c` 独立进入的结果 |
| --- | --- | --- |
| `DmmCfg.bin`，分区8 | `0x05000000` | 原分支跳过该行，在 `0xfe052e4c` 的跳过日志前停止；没有文件查询或传输 |
| `tomco.txt`，分区8 | `0x07000000` | 到达原文件大小查询 `0xfe05a1e0` 前停止；没有伪造查询结果或文件数据 |

原逻辑先按 bit31 分流，普通分支随后检查 `(~flags & 0x07000000)`。`0x05000000` 不满足这里的完整位组条件；同样的普通条件也见于参考装载路径。两行的路径指针、原记录 SHA 和全部原指令进入轨迹均保存。

这说明不能把这两个标志或该参考普通转发路径作为 `DmmCfg.bin` 已装入的证据，**不能扩大为“所有启动路径都不装入 DmmCfg”**。实际 FX3 AP 行为、其他类别装载、逃逸映像覆盖范围以及 CP 自身配置装入仍需分别核对。
