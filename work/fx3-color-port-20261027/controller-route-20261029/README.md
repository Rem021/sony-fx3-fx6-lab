尚未达到“FX5/VENICE 整套专业功能与色彩链替换固件可正常刷入 FX3”的停止条件。本轮把描述符交接推进到原控制器查找及类型检查前，并沿原 `kind3` 资源申请找到其两帧缓冲的依赖。12 组有界验证通过，没有提供类型转换、资源申请或硬件成功值，没有真实像素或固件输出。

## 从原调用者到控制器

原调用片段 `0x40a590..0x40a5a4` 经原 getter `0x9cfce8`，写入对象 `+0x8d8/+0x8dc/+0x8e0`：第一个值来自全局 `0x13c4ab8`，后两个是原代码给出的固定 RAM 地址 `0x13c4abc/0x13c5134`。本轮实际执行这段地址生产，不直接填入后两个指针；这些全局结构的内容仍是 guest 的零化初态和明确字段夹具，不是机身 RAM。

原后续输出函数读取第二个全局结构 `+0x394`，选择不同包装器：

| 原缓冲种类与输入标志 | 执行的输出函数 | 原包装器 | 类型检查的目标 |
| --- | --- | --- | --- |
| kind4，标志 0 | `0x428f0c` | `0x69ea22` | `EEController` |
| kind4，标志 1 | `0x428f0c` | `0x69ec28` | `SplitEEController` |
| kind3，标志 0 | `0x429a0c` | `0x69eb0e` | `EEController` |
| kind3，标志 1 | `0x429a0c` | `0x69ed18` | `SplitEEController` |

三个原类型记录及名称均已按文件字节封存：

- `0xbadc28` → `Camera::CamCore::CoreController`
- `0xbaddc8` → `Camera::CamCore::EEController`，记录中的基类指针为 `0xbadc28`
- `0xbae48c` → `Camera::CamCore::SplitEEController`，记录中的基类指针为 `0xbaddc8`

原入口 `0x4ec038` 的四参形态、vptr 前方元数据读取与 RTTI 虚调用，符合 [Itanium C++ ABI 的动态转换合同](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#rtti-dynamic_cast)。这是结合本地原指令的分类依据，没有把通用 ABI 文档当成 Sony 平台完整符合性证明，也未恢复该入口的符号名或执行完整转换。

**类型名不等于主录制归属。** 本轮不把 EE 直接解释成具体监看接口或 MAIN。Sony 的 [Display LUT 官方说明](https://helpguide.sony.net/ilc/2210/v1/en/contents/TP1000888936.html)（本轮读取）描述了监看预览功能，但没有说明这些私有类或其录像绑定。

## 原管理表的执行结果

原初始化函数 `0x69fe88` 建立 VA `0x11e076c` 的管理表、16 个空闲节点和自指空链表。原登记函数 `0x69e4f0` 消耗第一个空闲节点，分配 ID 1 并写入候选地址；原查找函数 `0x69e402` 对 ID 1 返回该地址，对不存在的 ID 2 返回 0。列表链接、计数和原写点均已检查。

8 组调用者用例覆盖上表四种分支及空表/已登记两种状态。空表由原函数返回 2，执行到原错误清理调用前停止；不提供错误清理或重新初始化成功值。已登记用例由原链表查找取得候选地址，停在 `0x4ec038` 第一条指令前，记录源类型 `CoreController` 与目标类型；不提供转换结果，也不进入原控制器虚调用或提交。

候选地址是显式夹具 `DATA+0xb000`，**没有构造真实 EEController 实例**。对象 `+0x8e4` 与原登记 ID 的绑定同样是夹具，尚未通过正常资源申请产生。对象自身描述符 `+0x70` 显式设置为无效句柄，避免把零化内存中的 0 误当作当前图像，掩盖上轮传入的描述符。这些前提与原 getter 的地址生产分别记录。

每组执行两个独立、有界的调用者前缀，并重设入口寄存器和栈；不能把停在类型检查/错误清理前的两段执行视为连续两帧正常完成。上轮 scene/模式/片段活跃寄存器、look22、VFX/STP、锁、pre/EI、硬件设置和队列返回夹具仍保留；未与真实资源状态合并。

## 正常 kind3 申请方向

原调用者 `0x40a55a..0x40a58c` 将 kind3 资源申请结果指向对象 `+0x8e4`。之前封存的原选择器在 context 1/5/7 分别选择 `[NRV_0]`、`[NRV_0, NRV_1]`、`[NRV_0, NRV_1]`，名称来自原固件资源表；不根据名字认定物理芯片或 RAW/CMOS 接口。

本轮另执行 3 组原 kind3 包装器→原 broker 前缀：

1. 三组都先进入 `0x4056f4`，资源 ID 为 4（`NRV_0`）。原传入 R1 随 context 1/5/7 为 `0/4/6`，不赋予未经验证的通道/位掩码含义。
2. 原代码开始申请两个 `0x50` 字节描述符；本轮只推进第一个，输出目标 `0x117adf0`，申请键 `0x4af`，原包装器 `0x44f004` 参数为 `[0x117adf0, 0x4af, 1, 0]`。
3. 经原 `0x44d710`，停在共用句柄操作 `0x4a032c` 前：前两参数为 `0x2a, 5`、输入栈字为 2。没有提供返回值，甚至未进入已有硬件成功适配器，因而没有正常控制器句柄或成功的整组资源申请。
4. 后续静态源码显示，两次描述符申请之后才会调用 `0x69e746`；它进入 `0x23db58` 的具体对象创建分支，创建返回成功才调用同一个原登记函数 `0x69e4f0`。这条后半段目前是静态调用关系，**没有执行或假定创建成功**。

因此后续应补原资源申请、具体控制器创建和正常 ID 绑定，而不能把本轮候选地址的查找当成已接通这些步骤。
