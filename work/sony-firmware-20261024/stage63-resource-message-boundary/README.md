# FX3 7.02：原资源消息构造与未绑定OSAL申请边界

本轮从同一原请求继续，执行了原资源提供者前段、原资源元数据构造、原消息对象构造与复制，得到**216字节资源请求**，再通过原veneer停在尚未绑定的`osal_valloc_msg_wait`间接分支前。目标FH的A5／C3及原UHD三组对照共21段有界执行通过。

另完成原OSAL模块静态依赖盘点：47个外部符号均有现有原固件中的静态来源证据，含44个内核导出候选和3个模块导出记录。**本轮没有重定位、加载或执行OSAL模块，没有申请到真实消息缓冲区、发送消息、得到回复或打开硬件编码器**。

## 原请求实际推进到哪里

为得到新的原生暂停状态，重新执行了stage62的原manager／factory／空闲队列前缀；这不是重复计为两项新成果。外部请求消息、partial dispatcher头、独立RAM存储、明确logger初始化标记及原静音setter仍为测试输入。

原`+0x22d394 → +0x27bdb4`继续执行，首次通过原`+0x27bca0`初始化原资源元数据对象`V+0x60aa38`，写入202条记录，并由原`+0x27be00`设置初始化标记。它们是**元数据记录，不是202个实际分配或可用的硬件缓冲区**。

仅包含该原数据对象的客体页被改为RW。每次引擎写入仍逐项限制在精确的0x2010字节对象内，并且PC必须来自原构造函数，或是原初始化标记的8字节store。没有用宿主填充表、设成功标志、产生指令执行结果或改原文件。原映像其余字节、既有导入、单条客体BL、logger测试字节及编译包装对象继续逐项核对。

随后原`+0x27bec8`调用原消息构造`+0x960a4`、原216字节复制`+0x96240`及原消息来源setter`+0x964ac`，来到原消息分派`+0x99004`。三组生成的消息均为：

| 项目 | 原代码产生的值 |
| --- | --- |
| 命令 | `0x61003c` |
| 消息内部状态 | 2，内联数据 |
| 数据长度 | 216 |
| 来源标识 | `0x806800f3` |
| 数据+0／+2／+4 | `u16 0x20`／`u16 0`／`u32 0x470` |
| 数据+0x14／+0x16 | `u16 0x1111`／`u16 0x11` |
| 其余数据字节 | 0 |

这些字节全部由原代码及原清零／复制生成。宿主只构造比较用参考数组，没有将参考数组写入客体输出。目标FH与UHD的这个初始资源请求相同，说明此处验证的是共享的资源准备步骤，不能据此认定HEVC参数已经被硬件接受。

原`+0x99118`进入`+0x2f028`veneer，实际加载的导入目标为0。在`+0x2f038`的`br x4`执行前停止，实参为：

```text
W0 = 0x61003c
X1 = 0x10007548  原调用者栈内指针输出槽
W2 = 0xd8        216字节
W3 = 1
X4 = 0           该原OSAL导入尚未绑定
LR = V +0x9911c
```

没有执行零地址分支，没有给输出槽补地址，没有模拟分配、同步发送、OSAL返回码或回复。所有客体地址均为离线布局，不是已核实的机身地址。

## 原OSAL模块依赖查到什么

已固定的`osal_uipc.ko`为AArch64可重定位ELF，包含47个未定义符号。其`vermagic`为`4.9.337-scel+ SMP preempt mod_unload aarch64`，同包内核版本字符串也是`4.9.337-scel+`。这里只核对文件元数据，不据此宣布ABI、当前内核状态或实际装载兼容。

全部节的重定位为326个`ABS64`、56个`PREL32`、430个`CALL26`，合计812项；含义按[Arm AArch64 ELF ABI原文](https://github.com/ARM-software/abi-aa/blob/main/aaelf64/aaelf64.rst#573relocation-types)核对（2026-10-26读取）。本轮没有应用这些重定位。

四个消息函数不仅有定义，还已通过原`__ksymtab`的值／名称成对重定位和`__ksymtab_strings`核对导出；不依赖文件中是否保留`__ksymtab_函数名`这种局部符号。

| 未定义符号来源 | 静态核对结果 |
| --- | --- |
| 44个内核符号 | 找到唯一成对值／名称候选，并核对前后合法、排序的导出名称记录 |
| `osal_create_waitable_thread` | 原`osal_utm.ko`定义及实际成对导出记录 |
| `osal_wait_thread_exit` | 同上 |
| `udif_devnodes` | 原`devno.ko`数据定义及实际成对导出记录 |

其中`kmalloc_caches`和`system_freezing_cnt`的候选值在内核文件覆盖范围外。本轮没有把这些地址映射为虚构的已初始化内核数据。其余候选也只是静态地址来源，不是当前内核实例或可调用服务的证明。

原`init_module`包含对`udif_driver_register`的重定位；注册、回调初始化、内存池、线程、锁和调度器状态均未执行。下一步需要核对实际节布局、重定位范围及依赖初始化边界，不能用非零函数地址代替服务已经就绪。

## 补提取与失败记录

`osal_uipc.ko`最初缺少的`udif_devnodes`不在nflasha15的模块目录里。按原分区目录找到同一官方包的nflasha7，校验分区SHA-256后，用既有只读ext2 reader提取一个普通文件`/kmod/devno.ko`，6344字节，SHA-256：`cca1d9acd87a718c7742d168ea0de402b01a7c04cd40433ff2ca4071150dbc23`。没有挂载、跟随符号链接、设置执行权限或运行模块。

保留了三项初始尝试：继承的旧消息构造边界在已核对原函数前停止；导出审计曾错误要求存在具名局部导出符号；首次在nflasha15查找devno失败。之后分别扩大已审核的原函数范围、解析真正的成对导出记录、核对正确原分区后继续。失败源码和说明均保留，没有改固件函数或补成功返回来迁就测试。
