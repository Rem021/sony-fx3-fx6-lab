# FX3 原封装元数据与 HD 格式分类

2026-10-25（本地日期），仅离线执行固定原 `libmpr.so`。

**16M 候选能经原初始化函数和完整元数据转换函数，生成 1920×1080、30000/1001、原码率字段 16000。** 因此不能直接用上层 FF 质量代替当前 16M 身份：质量 8 在同一路径进入原 `Conv ERROR` 日志，而质量 6 正常返回。

同时发现另一个独立问题：候选进入后续格式分类链时，原键函数不接受 1920 宽度；以原默认初始化表的八项条目作为明确查找输入，分类返回默认值 `0x97`，原 UHD 对照则命中 `0x8e`。**目前只定位到格式/名称转换链，尚未确定该回退是否影响描述性元数据、writer 准入或实际文件写入，不能据此判定 MP4 无法写入。**

## 实际运行的原函数

从已封存原 setter 的输出 `[VPC=6, VQuality=6, FrameRate=3]` 建立声明的 writer-state 输入，再执行：

1. 原 `0x115e18` 视频元数据初始化、原 `0x115e54` 八槽音频元数据初始化。这两个函数也出现在原调用者 `0x11d8bc/0x11d8cc`。
2. **完整原 `0x115fec`** 元数据转换，从入口到 `0x116768` 正常返回，期间执行原 level、帧率和扫描转换，实际写入输出字段。
3. 原 `0x117a6c` MPF profile/level 转换。
4. 原 `0x24d79c` 格式分类，调用原 `0x242b84` 键函数与原树查找/取值函数。

这里的 setter 输出由宿主复制为明确输入；实际应用模型到 writer-state 的完整更新、真实对象/通道/代次仍未接通。没有执行整个 writer、MP4 mux、文件写入或音频编码。

## 参数与质量对照

| 声明输入 | 完整元数据转换 | 原生成宽高 / 帧率 / 码率字段 | 后续分类 |
|---|---|---|---|
| 16M 候选 `[6,6,3]`，A5 旧内容 | 正常返回 0，输出有效字节为 1 | 1920×1080 / 30000/1001 / 16000 | 默认 `0x97` |
| 同一候选，C3 旧内容 | 同上，已观察字段一致 | 同上 | 同上 |
| 人工上层 FF `[6,8,3]` | 在原 `ConvertVPCToLevel` 的 `printf` 入口停止 | 已写码率字段 25000；有效字节仍为 0，其余结果仅是部分输出 | 未继续消费部分输出 |
| 非目标 HD9M `[6,26,3]` | 正常返回 | 1920×1080 / 30000/1001 / 9000 | 默认 `0x97` |
| 原合法 UHD 控制 `[5,13,7]` | 正常返回 | 3840×2160 / 60000/1001 / 150000 | 原表值 `0x8e` |
| 候选仅将输入 state+4 设为 1 | 元数据仍正常返回，输出 byte46 变为 1 | 仍为候选几何/帧率/码率 | 转入另一分类函数，入口前停止 |

码率是原字段值，不是实测码流速率。level、profile、MPF 等结果均保留其枚举命名空间：候选 level 枚举 5、profile 枚举 1、MPF 结果 45，不能直接当作 H.265 标准中的同数字 level/profile。

输入 state+4 和输出 byte46 的完整业务语义尚未绑定。本轮正常分类结论限定在该输入为 0 的条件，另一分支没有拿正常路径代替。

`Conv ERROR` 分支在调用 `printf` 前已经写入默认 level；原调用者随后会覆盖返回寄存器，不能仅凭这次日志断定真实录制必然中断。本轮未执行 `printf`、未提供其返回，也未继续该负例的下游转换。

## 初始化与旧内容

原初始化和转换在所观察的 0x48 字节视频区内仍不写七个字节：`+1/+2/+3/+0x1d/+0x1e/+0x1f/+0x47`。两组旧内容对照说明已观察的目标字段不依赖这些字节；并不证明它们对所有消费者无用、可随意覆盖或相机存在未初始化缺陷。

音频初始化及转换只证明这份声明输入下的元数据写入；没有音频采集、编码、声道实录或音画同步验收。

## 格式分类键与查找输入

原 `0x242b84` 对当前分支只接受宽度 3840 或 7680，并检查对应高度、profile 与 level 范围。1920×1080 候选的键返回 `-1`；目标 level 枚举 5 也不在该函数的接受范围内。

原默认 map 初始化函数 `0x24b634` 中有八组常量，覆盖两项 7680×4320 和六项 3840×2160 组合，映射值为 `0x8b…0x92`。本轮核对这些原指令，运行原键函数产生八个键，再把条目放入**明确声明的平衡查找树**。原分类/查找函数随后实际读取这棵树；没有伪造查找返回。

map 节点、全局 header 和存储链接是输入，C++ 全局构造、分配器、平衡过程及真实运行时 map 未执行或观察。该默认初始化函数不含 HD 项；其它运行路径是否会修改/扩展它仍需核对。不能把空 BSS 或合成树当成相机当前全局状态。

此查找的 UHD 正例命中 `0x8e`，HD 正例及 HD9M 对照返回原函数预设的 `0x97`。分类结果随后用于 `ConvertVideoCodecTypeName` 链；其对实际 writer、容器标识和录制可用性的影响仍待追踪。也不应把 UHD 格式值强行套给 HD 来消除回退。

## 对 16M 方案的影响

当前证据支持继续保留上层 16M 身份，研究资源内部的受限选择/私有预置；它尚未证明这种桥接可用。还必须解决原 FH 主录表不匹配，核对所有下游格式分类、元数据和缓存使用，再补真实同步/代次/生命周期及完整编码请求。

正式结果为 **36 段有界原 A64 执行**，包含八次原键生成及六组初始化/元数据/下游对照。首次正式运行通过。原代码页与固定原件一致，无字段输出、日志、分配器或返回/PC 跳过适配器；原本地 PLT 只解析到已允许的原函数。

源码、字节、轨迹和哈希复核由同一代理完成，没有新增独立实现或实机重放。

目标仍为经典 FX3 7.02 的 MAIN 1080p、30000/1001 fps、HEVC42010 约 16 Mbps；精确 30.000 单列。实际质量/资源桥接、完整 Open/Start、模型/query/cache/mux、成片/音频/时间戳/音画/长录/温度、同机健康备份、受限恢复回读、WBI/冷启动及独立救援要求全部保留。

本轮没有连接 UU/Windows 或相机，没有认证、切模式、变更驱动、读取素材、上传模块、WBI 或刷写。相机授权仍仅 Windows 缓存 PnP 盘点，尚未形成实机主录或救砖保证。
