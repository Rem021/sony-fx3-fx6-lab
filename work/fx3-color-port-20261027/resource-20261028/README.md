# FX3 色彩移植：原 VFX SDK、资源组合与 CP DMA 链

承接 [采集字段消费者复核](../consumer-20261028/README.md)和[选择适配原型 V2](../route-20261028/README.md)。本轮将上一轮整个 `set_builtin` 外部返回值边界，推进到 **原 CP 控制器 → 原 VFX SDK → 原 MLUT 命令构造**，并在另一明确边界后执行 **原 CP 命令分派 → ID 22 查表 → 70 项 DMA 列表构建**。

七种资源组合全部通过；错误路径会拒绝提交或重置原状态。实际运行时的主录／监看资源分配仍未恢复，完整 FX5 菜单和 VENICE RAW／ISP 链没有因此完成。全部工作为 Mac 上隔离 CPU 实验，没有访问相机／USB、修改完整固件或写实际寄存器。

## 从 acquire ID 到资源组合

上一轮原 `SetVfxMlutParam` 在 `0x3264f0` 调用 VA `0xa4f8ba`。本轮执行该 SDK 函数，找到原资源解析器 VA `0x488094`（file `0x380094`）：

1. 原解析器读取 VA `0x13eaff8` 的四行所有权记录，每行两个 32 位值：所有者 ID 和命名空间标签。
2. 根据请求的所有者与标签，生成四个资源槽的匹配位掩码。
3. 只接受下面七种组合，其余掩码返回 5；它们并非七个独立物理 MLUT 引擎。

| 匹配掩码 | SDK／核心内部组合编号 | 原范围函数给出的资源槽 | 原 CP 寄存器目标基址 |
|---|---:|---|---|
| `0x1` | 0 | 0 | `0xf4009000` |
| `0x2` | 1 | 1 | `0xf4109000` |
| `0x4` | 2 | 2 | `0xf4209000` |
| `0x8` | 3 | 3 | `0xf4309000` |
| `0xf` | 4 | 0–3 | `0xf4409000` |
| `0x3` | 5 | 0–1 | `0xf4509000` |
| `0xc` | 6 | 2–3 | `0xf4609000` |

范围函数为 VA `0x4892c8`；VFX 组合转 MLUT 类型的表位于 VA `0xd09228`，七项在这份固件里为恒等映射。CP 的原寄存器基址函数 VA `0xa1411e` 对编号 0–6 计算 `0xf4009000 + (编号 << 20)`，另有原表 VA `0xd00ddc` 与之对应。

原 SDK 对两个命名空间参数 0／1 依次查询，其记录标签分别为 1／2。这里尚未给命名空间命名为主录或监看；资源记录均为声明 fixture，没有读取机身当前 RAM。组合编号 4–6 对应多槽资源，寄存器地址是否以硬件广播或其他机制实现，仍需硬件映射资料或实际行为佐证。

## ID 22 还有真实的 SDK 准入条件

原 SDK 不仅核对外观编号。它还检查对应资源的状态，以及 VA `0x13eb088` 的前置准备所有者是否等于请求者。满足条件才调用核心 setter VA `0xa14d86`。

核心函数在栈中构造 56 字节命令，之后调用 VA `0xa1f2f2` 排队：

```text
u32[14] = [
    0,                // 命令类型
    22,               // 现有 ACESREC709 外观 ID
    资源组合编号,
    0x0042e681,       // 原 CP 完成回调 Thumb 地址
    0x02ae085a,       // 队列／事件标识
    0, 0, 0, 0, 0, 0, 0, 0, 0
]
```

本轮对两种命名空间下的全部 16 个掩码执行原资源解析器，共 32 组；七种合法组合分别从两种命名空间进入原 SDK，共 14 次成功命令构造。另测 17 个拒绝／失败案例，包括：非法资源组合、前置所有者不匹配、资源未就绪、外观 0／30／255、排队返回错误，以及同步原语返回错误。

同步原语、底层资源状态探测和真正排队均保留明确的声明返回值。这里证明的是这些输入条件下原代码的准入／命令行为，不能把 fixture 的所有权说成相机当前分配。

## 原 CP 控制器与原 SDK 已放在同一 guest

`cp_control_sdk_guest.py` 执行原控制器、刚恢复的完整 SDK 选择路径、核心命令构造，以及原完成回调。原型使用同一个声明所有者 ID；七种组合各有：

| 阶段 | state | look | pending | 核心命令数 |
|---|---:|---:|---:|---:|
| 准备返回成功 | 1 | 0 | 0 | 0 |
| 原 SDK 接受并构造提交 | 2 | 22 | 1 | 1 |
| pending 时再次调用 | 2 | 22 | 1 | 1 |
| 人工输入成功状态，执行原回调 | 2 | 22 | 0 | 1 |

再验证无所有者、资源未就绪、排队失败、前置所有者不匹配、前置准备失败和回调失败。原控制器回到未就绪状态，未把失败当完成。

**前置准备和 EI 设置尚用声明的函数合同；回调到达也由 host 明确输入。** 这比上一轮把 `set_builtin` 整段作为成功替身更深入，但仍不等于硬件导致回调。

## 原 CP 分派器已展开成 70 项写入描述

使用上述原 SDK 生成的命令，分别供给原命令分派器 VA `0x470ec0`。这是 host 在两个 guest 边界间传递真实构造结果，未伪称实际 OSAL 队列收发。

原命令 0 分支进入 VA `0xa1ed26`，调用原查表 VA `0xa193ea`，取得 CP 自己的 ID 22 记录。配置数据使用上一轮原初始化器产生并封存的 `CP-look22-initialized.bin`，70 项、每项 140 字节；哈希 `a4f057164b12be25a2e9e80bcdd6e78bffe3d7685606e8dde39d22b1e98c10e0`。

随后执行 `mlut_make_lli_table`（VA `0x470f78`）：

- 七种资源组合分别生成 **70 项、每项 16 字节**的 DMA 列表，目标缓冲 VA `0x2025570`。
- 每项源地址与原配置指针一致；目的地址等于上表的基址加该项原寄存器偏移。
- 核对全部 70 项的字数、下一项指针、控制字和最后一项终止位，并核对缓冲边界、栈及保存寄存器。
- 对七种组合生成七份独立的二进制列表；原构造路径共执行 62,462 条 guest 指令，含一次提交失败探针。
- 只有声明的提交返回成功时，原代码才将对应的软件外观影子值更新为 22；返回错误时保持未更新。

虚拟到物理地址翻译在此实验中明确声明为恒等映射，缓存同步作为边界截获；每份列表原代码发起 70 次 16 字节列表同步。实际物理地址、缓存效果、硬件 DMA 和帧结果均未验证。三个源指针仍指向未知的运行时选择字，保持地址原样，没有拿零值代替实际内容。

## 与旧 AArch64 实验的关系

早期 AArch64 AV 镜像的基址函数只在所测 IP 0 下返回有效地址；CP 的原实现则接受上述七种资源组合。本轮没有把 AArch64 的 IP 1 反例套到 CP 上，也没有假定两颗处理器的地址空间相同。两份原件中配置载荷一致的证据仍保留，但控制合同必须分别执行验证。

## 仍待闭合的场景绑定

目前已确认原 VFX 控制路径从对象 `+0x10d0` 读取 acquire ID；但其有效值何时由哪个场景取得，尚未建立。原 `AcquireVfx`（file `0x3259bc`）通过通用资源代理在 `0x2fc336` 被调用，仍需把代理结果追回具体软件对象和正常录像场景。

扫描同偏移曾找到 `0x94678e` 的写入点，复核后发现它基于 VA `0xd091f0` 的另一张表，并打包输入的 14 位数值，不能将这个同偏移写入误当成 acquire ID 的生产者。`resource-offset-candidates.json` 的 41 项均只是候选。

接下来需要建立“主录／监看场景 → 所有者记录 → 资源组合”的对应，再核对 MLUT 输入所处的信号域和记录文件元数据。上一轮新增编号 12 在监看元数据函数中走默认分支的问题仍开放，本轮没有凭数值相似就补一个未经定义的标记。

Sony [Display LUT 官方说明](https://helpguide.sony.net/ilc/2210/v1/en/contents/TP1000888936.html)于 2026-10-28 再次核对，其监看定义只能帮助划分功能，不能替代这里欠缺的实际资源与像素证据。整套专业菜单、传感器 RAW／ISP／标定链仍是更大的未完成范围。
