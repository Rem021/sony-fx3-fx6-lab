## 来源与真实注册链

从既存7.02 `nflasha15.img`（SHA256 `df0a2cf2ebb0d884605d041a6dcb701092bd36848956855b8d3d7a7164a3a1c5`）重新取得六个文件。`libObj.so` 为2876600字节，SHA256 `c4681d209a7fe2ed63752be3b0be89ab7b7ce400679c00068c8c6e47d39f83ae`。[来源清单](current-main-capture.json)。以下地址是ELF链接VA或指定模块节偏移，均不是实机PC。

导出函数 `udtr_senser_init` 位于 `0xEE0B0`。它在服务注册结果非零、`Backup_read(0x004B0000)`返回正值且首byte为1／2的条件下，在 `0xEE188` 调用重定位名为 `osal_reg_msg_queue_cb` 的PLT：

- ID与回调上下文均为 `0x004B0376`；回调地址为 `0xED990`，句柄保存位置为 `0x2CE198`。
- 用户API按bit15为0走IOCTL注册，而不是直接调用内核导出API。IOCTL低32位为 `0x80000008`，内核用户注册路径最后以低16位 `0x0376` 注册异步代理。
- 发送者的ID为 `0x804B0376`；内核发送路径中，bit31置位但bits30…28为零，仍取本地低16位队列。它与注册端是同一队列，不能因高位不同而忽略匹配。
- 通用内核代理、用户pending线程之后才调用上述业务函数。此前找到的OSAL唤醒/包装层仍成立，但不再是本条请求的最终停点。

## 接收函数会改模式文件

非空消息的选中普通路径先调用 `0xED8CC`，通过 `stm_system` 请求执行 `/usr/bin/us_remove_modes.sh`。当前镜像中的对应 `/bin/us_remove_modes.sh` 内容是删除 `/setting/updater/mode*`，随后显式 `exit 0`。该脚本未检查 `rm` 的返回状态，因此脚本成功码不能单独证明旧文件全部删除。[原脚本](originals/7.02-main/bin/us_remove_modes.sh)、[调用包装](current-remove-wrapper.txt)。这里未执行命令，也未验证运行时路径解析和文件系统状态。

在移除包装返回0、后续文件创建/关闭正常的条件下，指令分支为：

| 消息中的32位值 | 随后创建的文件名，均位于 `/setting/updater/` |
| --- | --- |
| 0 | 不新增文件 |
| 2 | `mode` |
| 3 | `mode`、`mode3` |
| 4 | `mode`、`mode1` |
| 6 | `mode`、`mode6` |
| 其余，包括5／7 | 进入命令错误、释放输入消息的局部路径，不分配正常回复 |

创建包装调用 `open`，原参数为flags `0x42`（Linux的`O_RDWR | O_CREAT`）、mode `0x124`（八进制0444），然后关闭文件；它不是检查存在性的只读操作。本回调中没有 `fsync`／`sync`，没有直接重启或AP分区装载调用。这只描述所列代码，不排除其他线程或外部调用者另行重启。

因此适配工具不能把这条队列当成只读探测，也不能在尚无恢复条件时自动试发送。它会影响下一次启动的持久标志。[创建包装](current-create-flag.txt)、[10项独立原始编码核对](endpoint-raw-audit.json)。

## 发送返回0并不确认模式已经设置

当前7.02主系统 `ud_send_lsi.elf` 为10248字节，SHA256 `5fbcdb8d9795828febbf6ce9cb966aec2adeff6311577184e4fb8abecfd163e7`。在发送返回0后的选中路径，它等待接收3000个时间单位，把接收结果0或`-1022`都转到释放/正常结束路径；未检查回复的命令或正文。[原发送/接收段](current-helper-reply.txt)。本轮不把该时间单位未经验证地改称实测3秒。

接收函数正常回复路径分配4字节并发送到原来源ID，回调内未给该4字节写入业务状态。分配器是否初始化内存不是本轮结论；**这份回复没有在本函数里形成可验证的“模式设置/落盘完成”状态字段**。

原 `up.sh` 有5／7参数分支，而本接收函数不处理这两个值。若它们确实到达已注册的这个接收者，且移除包装返回0，会先尝试清掉模式文件，再走无正常回复的错误路径；发送者的上述超时处理又可能掩盖失败。这是有条件的静态路径，不是你的相机已发生的故障。

还核对了脚本结尾：存在 `/root/IAMUPDATER` 时会在调用 `ud_send_lsi.elf` 前退出，不能把历史p1中放有同名辅助程序当成“它在恢复环境中也会走相同调用”的证明。
