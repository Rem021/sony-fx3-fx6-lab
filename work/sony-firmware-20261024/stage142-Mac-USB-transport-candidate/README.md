# FX3：Mac 描述符读取候选与首次测试边界

2026-10-27。**现有 Mac 足够准备下一步 USB 元数据识别；尚没有只靠这两台电脑即可保证救回 FX3 的通路。** 用户目前只有 Mac、Windows，没有 RP2040/Pico 或串口工具。Windows 仍依此前指示暂缓使用。

本轮新建的 Mac 私有传输候选已编译并完成离线检查，真实 libusb 动态库没有被加载或初始化。只复用了已授权的 Mac IORegistry 缓存查询：缓存中有一台 `054C:0DA1 / ILME-FX3`，位置值保存在 [缓存回执](current-cache-target.json)；这次 IOUSB 树未提供接口/端点及二进制描述符属性。原始树和序列号未保存。缓存存在不能证明当前相机健康、固件版本或同机身份。

## 为什么改用私有构建

来源是 [libusb 官方 1.0.30 发布包](https://github.com/libusb/libusb/releases/tag/v1.0.30)，下载字节、来源和源文件 SHA 见 [source-inputs.json](source-inputs.json)。尚未另行核对发布者独立校验值；本机构建不宣称等于上游原版。

原 Darwin 实现的初始化/枚举会尝试 `USBDeviceOpenSeize`，描述符失败时还可能执行 `SetConfiguration`、挂起/恢复及重试。因此仅“不调用 Python open()”不足以满足本次元数据测试范围。

私有改动见 [源修改回执](private-source-patch.json)、[首次修改脚本](patch_private_libusb.py)和[收紧脚本](harden_descriptor_candidate.py)：

- 未设置目标即拒绝全部设备；在创建 USB 设备访问对象前，以缓存位置、VID `054C`、PID `0DA1` 过滤。服务 PID `0336` 在此处拒绝。
- 显式设备 `GET_DESCRIPTOR` 最多一次，失败也消耗额度；不抢占、重设配置、挂起/恢复或重试。多配置描述符拒绝，避免后续 `GetConfiguration` 分支。
- 配置描述符及接口元数据仍经 IOKit 只读 API 获取；无法由源码保证操作系统内部实际总线请求次数，不将“一次显式请求”表述为“一次总线包”。
- 两处拒绝设备的分支补齐 IOObject 释放。普通设备打开、接口接管等上游函数仍存在于动态库内，但本工具没有绑定或调用这些接口。

[构建回执](native-build-receipt.json)记录任务目录内的动态库、C/ctypes ABI、编译命令及 SHA。执行了构建系统、自有 C 布局程序和模拟动态库；未执行 Sony 固件原生代码，也未初始化真实 USB 库。没有全局安装库、驱动或修改 PATH。首轮编译失败及收紧前的成功构建、源码和测试均保留。

## 具体首次读取方案

[descriptor_probe.py](descriptor_probe.py) 默认 `--plan`，只读取本地文件。[方案快照](first-descriptor-trial-plan.json)固定候选、目标、期限与操作范围。`--query-descriptors` 当前会在创建工作进程/加载库前拒绝；未创建真实单次凭据或进行实际描述符查询。

如果获得对应新增授权，先要求相机保持普通 MSC、目标端口不变，再用已授权缓存做唯一目标交叉核对。随后记录独占单次凭据，由单独进程执行目标限定的设备/配置描述符及接口元数据读取。它会创建选中设备的 IOKit 访问对象并执行标准 USB 读取，**超出仅缓存查询**。

此流程不调用设备打开/抢占、接口 claim、驱动 detach/attach、Sony 厂商命令、认证、模式切换、素材、设置或固件操作。工作进程期限 15 秒，超时发终止并最多再等待 2 秒；无法确认结束时明确保留未知，单次凭据保留，不自动重试、重置或补发。主机进程退出本身不证明底层请求完成或相机健康。

本次测试即使成功，也只获得元数据；不能证明认证/传输端点角色、完整备份、同机恢复、BootROM 救援或 HEVC 主录。下一步还要完成真实传输、接管/归还与停止条件审查，再提出独立的受限认证方案。
