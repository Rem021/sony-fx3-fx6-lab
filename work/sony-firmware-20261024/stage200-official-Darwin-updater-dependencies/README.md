# FX3官方Darwin发送端、驱动参数与结果边界

2026-10-29。**在7.02官方更新包中，已定位到199轮那一帧`0x11/4`的AP侧发送程序，并核对其SIO参数与历史FX3恢复分区驱动相符。** 这闭合了程序/字段层面的来源，不等于AP恢复环境已经能从故障状态独立启动。Darwin更新路线仍不能作为“主系统刷坏后一定可救回”的依据。

只读取既存容器和原件，执行宿主解析与静态检查。没有运行提取出的ELF、脚本、内核模块或guest代码，没有相机、USB、管理员、驱动安装、Windows、UU或GUI动作。195 root01仍待原来的具体回答；没有重复询问或创建固定作业。16项目标、所有授权与现有候选保留。

## 当前发送程序已绑定到7.02原件

[7.02 Ubody原件](../stage182-boot-selector-and-recovery-admission/current-updater-evidence/original-members/udtrbody.squashfs)为1253376字节，SHA256 `62e86fad175e0326969d5f1cea29d780feb496ce8034acd2c9c3954320d8ccaa`。从它重新提取的`/bin/ud_darwin_firmup.elf`为14408字节，SHA256 `f0b0fd8fd1fd3c2c348744faeb9b0267668b99ebf5875560ef2fd7dddb424ea8`，没有拿其他任务的候选副本当原件。

程序是Linux AArch64动态ELF。原启动入口的LDR字面量与`__libc_start_main`导入，指向主函数`0x400C30`；不是仅在数据中找到一段孤立字节。[入口审计](entry-and-dependency-audit.json)。地址均为来源ELF VA，未取得机身PC。

主函数先初始化机身SIO/GPIO，随后：

- 在128字节缓冲`0x44F140`的前两byte写`[0x11,4]`，调用内部收发函数`0x401544`。
- 收发函数计算前126字节的校验值，放到`+126`，操作GPIO并调用机身SIO驱动。
- 因而199轮Darwin InitCom所消费的命令/子值，现已找到**当前7.02包内的AP发送者**。这里仅建立逻辑帧字段和程序来源，不宣称已有真实线缆/总线收发证明或完整端到端启动验证。

[原始编码及14份选中切片](official-sender-proof.json)、[当前构帧](official-frame-template.txt)、[当前收发](official-SIO-wrapper.txt)。

## SIO契约与版本身份分开

当前7.02程序使用请求`0x40046740`。请求编码里的大小字段不能替代真正的参数布局：原程序构造的是32字节参数块，包含tx指针、rx指针、32位长度128以及尾部零值。

历史官方2.04/2.05 p1中的`sio.ko`均识别该请求，复制32字节参数，取`+16`的长度，正数超过256时截到256。128未触发这个截断。选中的状态正常/用户复制完整路径最后返回**请求长度128**，不是统一返回0。[参考驱动分派](reference-sio-dispatch.txt)、[长度](reference-sio-length.txt)、[提交](reference-sio-submit.txt)、[结果](reference-sio-success.txt)。

两份历史模块全文件SHA不同，但字节差异全部位于GNU build-id note；将该note置零后逐字节相同，包含重定位及其余节，而不仅是`.text`相同。其vermagic为`4.9.186-scel`。**这是两份历史原件的比较，不是你当前机身p1模块的身份核验。** 当前主系统的GPIO库也没有被当成p1提供者替换进去。

成功路径仍依赖模块的实际加载、硬件完成/错误状态、用户复制和外围设备行为。没有执行模块，没有从选中路径推广所有错误、阻塞或物理状态都已验证。

## 官方工具需要已运行的AP环境

历史2.04/2.05 p1里的`ud_darwin_init.elf`均为10304字节、同一SHA256 `c943c7462e4d94b834b891555a2224c4a2c34d722204368e66d6d97d3eca91ad`。它们与当前7.02 Ubody的刷写程序分开记录。

历史p1的`/sbin/init`先完成Linux挂载、调用驱动加载脚本，再按电源IC类型执行Darwin初始化，随后启动更新主流程；驱动脚本明确加载`sio.ko`。当前7.02 XML的Darwin阶段引用`us_darwin_firm.sh`，`thread="yes"`；在历史p1中，该脚本调用刷写程序处理boo/core文件。[依赖审计](entry-and-dependency-audit.json)。

程序还依赖机身Backup服务提供SIO通道及GPIO相关参数，以及动态库和Linux设备节点。它不是Mac/Windows上的通用USB救砖软件。**这条路线需要AP Linux/更新运行环境先可执行，因此没有自行解决AP起不来时怎样装载p1的问题。** 历史p1是否等同当前已安装p1仍未核对，未从版本历史作默认推定。

## 三种“成功”不能混用

| 信号 | 本轮来源证据 | 能证明的范围 |
| --- | --- | --- |
| SIO ioctl返回128 | 历史驱动选中路径返回请求长度 | 该驱动的局部状态/复制路径；不是已进入MCU更新或救回AP |
| 历史初始化ELF返回0 | 若最后保存状态为0、回复状态不是4、之后计时比较超限，局部路径仍可能返回0 | 返回码单独不能证明收到目标状态4；仅为静态条件路径，未实测故障 |
| `Darwin init --- OK`及脚本exit0 | 原脚本未检查子程序状态，普通顺序执行模式下打印后显式exit0 | 不是初始化程序成功、目标状态确认或设备恢复回执 |

最后两项只在历史原件和列出的普通ABI/计时条件下成立，不能擅自给当前机身归因。没有执行原脚本，也没有用它发起初始化。后续适配必须保留实际收发和目标状态的证据，不能只沿用外层成功提示。

## 模拟与硬件校验边界

当前AP刷写程序的校验函数是软件循环；199轮对应Darwin校验函数`0xBDA4`则通过`0x40039000`寄存器读写取得结果。原字节可见写入输入byte、读结果寄存器，但本轮没有验证该外设的实际配置/时序或它与AP软件校验的硬件等价性。没有补一个猜测的CRC外设模型来宣布模拟通过。[MCU校验原件](MCU-CRC-peripheral.txt)。

同样，本轮没有形成整机模拟器。所用Sony[FX3 7.00开源页面](https://oss.sony.net/Products/Linux/B2B/ILME-FX3_Ver700.html)及已保存源码归档只作参考，不声称精确对应7.02完整构建。对归档的特定SIO文件名筛选为空，不能据此证明等效/改名代码不存在。维护者[硬件文档](https://github.com/ma1co/OpenMemories-Docs/blob/master/hardware.rst)列有Darwin Cortex-M3历史机型，也没有被用来指定FX3当前MCU料号或板上引脚。
