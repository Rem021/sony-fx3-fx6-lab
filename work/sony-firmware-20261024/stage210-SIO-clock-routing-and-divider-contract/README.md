# FX3 早期 SIO与计时合同

2026-10-29；经典 ILME-FX3 7.02；离线原件研究。

本轮在当前官方NOR加载器中定位到SIO事务，并确认其计时函数与A7 IV参考加载器**完整84字节相同**。同时，当前内核的3个SIO资源描述符没有填入独立的hclk／dclk／dclksel配置，因此不能从这张表推导SIO父时钟。209轮的配置值19与参考3之差仍未闭合，下一步应追早期速率字段的初始化及其配置来源。

## 当前早期收发函数

原件是 `loader_nor.bin`，101,888字节，SHA-256 `4358c839cfb1f22d5eb4e53d67817c42c4e877ba8b0aff375d355ce6294c4942`；官方 `pformat_config.txt` 给定加载基址0xFE049000。以下为据此标注的文件地址，不是实测机身PC或已证明可达的恢复入口。

在0xFE052348的选中事务中：

- 从0xFE0625CC读取速率字，从0xFE0625D0读取SIO通道；GPIO位／端口从0xFE0625D4／5D8读取。
- SIO地址公式是0xF1005000＋通道×4096；速率字分别按移位规则写入SIO+0x14／+0x18。
- FIFO位于+0x100；传输参数为128字节，长度寄存器写127左移24；控制字段、GPIO低有效片选和结束收尾与参考事务的相应结构对应。

这把当前官方早期事务与参考结构联系起来，**没有证明上述速率字段当前是3或19**。查到字段读取位置不等于找到了初始化值。两个线性地址候选脚本仅辅助定位，不构成完整控制流／别名覆盖；未找到选定写点不能证明写者不存在。

## 计时来源与阈值

当前事务调用0xFE05CAB8，后者转交0xFE05863C；A7 IV参考加载器的包装0xFE062418转交0xFE05AAD0。两份叶函数的84个原始字节完全相同，没有执行其中任何指令。

该函数读取 `CNTPCT_EL0`、`CNTFRQ_EL0`，使用如下整数运算：

`CNTPCT / (((CNTFRQ * 0x431BDE82D7B634DB) >> 64) >> 18)`

两份启动代码都包含把2,000,000写到 `CNTFRQ_EL0` 的指令和对应原始字面量。在该声明值下，分母为2，结果相当于按声明频率换算的微秒计数。函数不读取输入x0；caller传入的2不能被命名为“物理timer2选择”。这些是代码和声明值的合同，没有测量真实计数器频率，也没有排除后续阶段更改声明值。

当前事务中的两次计数差比较分别是101／1001。第一基线在SIO配置和GPIO拉低之前读取，第二基线在GPIO释放之前读取，故**阈值不是从对应GPIO边沿开始计的101／1001微秒，也不是实测脉宽**。参考载荷声明150／1200微秒延时，并依赖另外一个标称4MHz的Timer0；这台FX3上Timer0的真实频率、GPIO瞬态及链路均未验证。

这项结果为后续时序适配提供了当前原码依据，不需要继续把早期计时完全当未知tick；它仍不能放行SIO配置或首次刷入。

## 内核资源表为什么不能回答父时钟

当前官方7.02原内核SHA-256为 `da4a66fa29f6b4033233c0d8e7bd9a6f0ffab0cc18d85a44aa6f3830b7c4820c`。其 `sio` 表位于文件偏移0x63F838，3项、每项152字节：物理基址为0xF1005000／6000／7000，长度均0x1000。

依照公开结构（40字节IOMEM、40字节IRQ、72字节CLOCK），每项尾部72字节时钟配置全部为零；当前原内核的UDIF时钟帮助函数及原始描述符都已保留。公开 [FX3 Ver7.00 GPL平台定义](https://oss.sony.net/Products/Linux/B2B/ILME-FX3_Ver700.html)的SIO项也只初始化iomem／intr。这里用参考声明解释布局，再核对当前原字节；没有把7.00归档等同整个7.02构建。

结论仅限“这些描述符没有给出非零时钟控制／选择参数”。它不能证明SIO没有物理时钟、其他初始化阶段没有改过时钟，或速率寄存器19与3对应何种Hz。需要继续查早期配置初始化及其依赖，而不是从空字段猜测父频率或把19直接替换3。
