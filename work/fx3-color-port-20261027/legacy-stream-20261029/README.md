# FX3 完整旧格式内存流与镜头入口类别限制

2026-10-29。**完整旧格式内存流已由原解密控制代码逐块处理，并能继续恢复原更新镜像、进入原 TAR 控制器；保留 FX3 机型字段时，它仍被原 LENSDATA 预处理拒绝。** 这同时验证了格式层的一段完整消费过程，以及“能解密、尺寸够小”尚不足以进入真实镜头更新链。没有可正常刷入的 FX5／VENICE 色彩替换固件。

接续[原控制器时序与输入模式](../controller-20261029/README.md)。没有操作相机、USB、机身文件、mount、原生 Sony 库或原更新脚本，没有保存新固件容器。所有测试密文、明文和合成类别变体只留在内存中，落盘的是脚本、哈希、状态和源片段。

## 从整个密文流到原消费者

在原 7.02 明文中保留 1,253,376 字节的更新镜像，接上上一阶段 5,120 字节的无执行权限文本／XML 测试 TAR。原头部只调整 `firmwareSize` 和对应头 CRC32；偏移、机型、版本和更新镜像保持原值。得到 1,259,008 字节的测试明文，按旧格式封装为 1,235 个块、1,264,640 字节密文，小于先前核对的镜头暂存 2 MiB 限制。

头字段布局和附件类别谓词与[固定提交的维护者解析器](https://github.com/DavidBuchanan314/fwtool.py/blob/3955d7890fc38daf942bb52827599bfe35de4a14/fwtool/sony/fdat.py)交叉核对；输入规则的接受与拒绝由本轮原指令验证，不由该宿主解析器代替。

原 `MsDecryptorModule` 构造、线程运行标志、读块、`DecryptorModule::execute`／decrypt、原 AES 包装、和校验、长度／结束检查及输出分派实际解释执行。输入 ReadData 使用严格内存适配器，维护剩余字节计数；`RingBuffer::IsEnd` 已改用当前 AP 原函数，它读取明确提供的 producer EOF 标志及剩余计数。没有执行真实生产线程和完整环形缓冲并发。

AES 数学和 key setup 是 Apple CommonCrypto 替身：执行原 `Dec_ScrambleInit`／`Dec_Scramble` 包装，但不执行 Sony 原生 AES 或模拟 OpenSSL key schedule 内存。原格式常量仅在内存使用，未输出值。完整流调用 AES 单块数学 79,040 次，全部还原为预期明文，输入无剩余，最后输出带结束标志。

随后将**同一份解密输出**交给独立 guest 中的原头部检查及更新镜像组装：恢复出 1,253,376 字节，SHA-256 `62e86fad175e0326969d5f1cea29d780feb496ce8034acd2c9c3954320d8ccaa`，与原镜像相同；剩余明文再交给原控制器，到达补充配置产生的系统请求入口。

这是字节相同的跨 guest 交接，不是一个实际进程的完整初始化和装载。原控制器的内存文件系统、stat、mutex 以及初始脚本返回 0 的显式替身仍存在；后续系统请求不执行、不返回伪造成功。[完整流与下游结果](decrypt-stream-results.json)

## 解码成功与完整输入的差别

七组解码检查包括一组完整测试流和六组小型边界输入：

| 条件 | 原解码结果 |
|---|---|
| 完整测试流 | 1,235 块全部消费，明文逐字节相同 |
| 两个有效块 | 完整输出 1,057 字节 |
| 第一块提前带结束标志，后面仍有一块 | 返回，输出 1,020 字节，留下 1,024 字节未读密文 |
| 最后一块缺少结束标志 | 原异常 `0x30002`；此前已有 1,020 字节输出 |
| 最后一个密文块只有 1,023 字节 | 原异常 `0x30002`，未开始 AES 解密 |
| 和校验损坏 | 原异常 `0x30002` |
| 数据长度字段为零 | 原异常 `0x30002` |

提前结束的观察适用于所声明的顺序输入／EOF 条件，不外推为完整外部容器可接受尾随数据。失败前可能已有输出，也不能把异常理解成原生事务回滚或机身未发生动作。这里所有输出仍在内存中。[原流结果](decrypt-stream-results.json)

## LENSDATA 入口不是直接替代路径

进一步执行原 UFP 的镜头准备窗口 `0x2f48..0x3034`、原 UFU chunk 搜索、原 516 字节头信息读取、AES 包装与类别比较。媒体根路径是显式 `/fixture`，文件接口只读内存；原 AES 初始化明确提供，没有冒充 UFP 的实际完整启动。

| 测试头 | 原结果 |
|---|---|
| FX3 原机型值 `0x91030080` | 返回 2，在 IPC 前拒绝 |
| 仅在合成数据中调整附件类别字段并重算头 CRC | 推进到原 OSAL allocation 请求入口，服务 `0x912503d0`、命令 3、消息 8 字节；立即停止 |

原门槛是机型字与 `0x00ff0000` 按位与后等于 `0x00a00000`。这解释了为什么把小型旧格式机身输入直接命名成 LENSDATA 仍不能通过所查准备步骤。合成类别值只是定位下一关的夹具，没有证明它匹配任何真实镜头，也没有伪造 OSAL 回复、继续暂存、调用 crypter 或进入设备更新。[两组镜头头部检查](lens-header-gate-results.json)

该内存输入只有 UFU 标识和 FDAT chunk，不称为通过官方完整 UFU CRC／尾部验证。真实请求来源、服务状态、后续机型与版本判断、启动和恢复仍未验证。
