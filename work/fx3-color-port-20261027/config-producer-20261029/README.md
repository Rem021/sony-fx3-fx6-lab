# FX3 CP 配置文件的原装载描述与 NOR 消费入口（2026-10-29）

**仍没有可正常刷入 FX3 的整套 FX5／VENICE 功能或色彩链修改固件。** 本轮找到了此前缺失的配置文件装载描述：官方第二段 BK4 记录的 `0xfa0080` 表将分区8的 `\DmmCfg.bin` 指向 `0x809a08e00`。原 NOR 参数函数在明确提供原模板的 RAM 环境中读出了完整表，原消费代码也接到了 FAT 挂载／文件打开边界。没有证明用户机身当前选取该记录，未执行机身文件读取、内存写入、缓存硬件维护或刷机。

开始时核验外盘 UUID `F9404A58-A1C4-409F-8E78-9A6B7EEB3F7B`、现有项目入口及非 Git 边界；[上一阶段](../mmu-software-init-20261029/README.md) 29 个封存文件全部独立回读通过。上一轮属于取得新证据的 progress。原件和旧封存不改，另一 agent 的设备／恢复工具与租约未操作。

## 从文件名字串定位原参数表

先对原 `nflasha15` 和 `nflasha7` 两个文件系统的全部 **847 个普通文件**搜索五个精确 ASCII 标记。前者是 `/usr` 分区，不等于整个 AP 系统；本轮没有用无匹配扩大为不存在加载器。匹配仅在原启动脚本中出现 AP 的 DMM 文件参数。

转查此前已固定来源的官方 BK4 原记录，发现 `DmmCfg.bin`、`tomco.txt`、`cpapp-b.bin` 等文件名位于第二记录的参数 **`0xfa0080`** 内。重新从 SHA 固定的官方 FDAT 读取全部22份模板：tar名称／类型／大小与头校验成立，原 `backup.sum` 大小和 CRC32 成立，全部44段 BK4 的记录求和校验成立。

该参数的原长度为 **9,216 字节**，有64个144字节槽。两段记录各自的表在22份模板中均一致；第二段有11个非零槽，第一段有9个。这里的 `bank0/bank1` 仅沿用既有文件名表示模板内第一／第二记录，**不表示已经判定机身主备槽或运行时选择**。

每个槽按原 NOR 消费指令读取 `2×u64 + 2×u32 + 120字节路径`。第二记录的第3槽为：

| 原字段 | 值 | 交叉依据 |
| --- | --- | --- |
| 源分区 | `8` | 原 FAT 中存在 `/DmmCfg.bin`；启动 fstab 将分区8挂到 `/cp` |
| 原路径 | `\DmmCfg.bin` | 参数原字节，文件名不是宿主猜测 |
| 目标起始 | `0x809a08e00` | 等于同记录参数 `0xfa0182` |
| 目标末端 | `0x809a21dff` | 原加载器使用 `end-start+1` 比较文件长度 |
| 保留容量 | `0x19000`，102,400字节 | 等于同记录参数 `0xfa0183`；其专门消费者尚未据此恢复 |
| 模式原字 | `0x05000000` | 原条件代码另有模式、状态和跳过判断，不能直接当作必定装载 |

这个完整槽在22份模板中一致。原 CP 文件为43,320字节，SHA `820dc02b6a001636b93fff51d90baaced1ba75cf9bbaa90600dfc7fd7a705166`，可容纳在该范围内；计算出的文件末字节为 `0x809a13737`。这是原默认装载描述和容量关系，不是实际 RAM 内容或已完成文件复制。

## 原 NOR 参数函数确实读取这份结构

从官方 FDAT 内的 `0750_nor_loader/loader_nor.tar` 独立读取原加载器，未导入或重跑另一 agent 的脚本。`loader_nor.bin` 为101,888字节，SHA：

`4358c839cfb1f22d5eb4e53d67817c42c4e877ba8b0aff375d355ce6294c4942`

同包原 `pformat_config.txt` 指定其装载基址为 `0xfe049000`。

两个原 BK4 记录分别作为明确输入放入隔离 ARM64 RAM。原 `0xfe04d63c` 检查 BK4 标记并初始化原参数根；原 `0xfe04c7b4` 查询 `0xfa0080`，经原属性定位、原长度读取和原复制，分别返回 **`0x2400`**。两次输出都与各自9,216个原字节完全相同，后续16字节哨兵未改。没有查询、锁、文件或服务成功回复适配器。

两组原代码负例也通过：不存在的 `0xfaffff` 返回 `-1` 且整个输出区保持哨兵；只在 RAM 输入中改变 BK4 标记的夹具被原初始化拒绝，原文件没有修改。

## 原消费链停在真实依赖处

原 `0xfe0545dc` 配置入口构造 `0xfa0080`，调用原参数包装器并将表置于软件装载缓冲区。代码以 `0x90` 步长读取槽，取分区、起止地址与 `+0x18` 的路径；静态直接调用点分别提供 `0x0c000000` 和 `0x09000000` 模式。具体分支仍依赖原加载状态和运行标志。

完整配置入口的严格实验停在 `0xfe058a6c` 读取未知的备份就绪状态 `0xfe26c300` 时，没有给它填入“就绪”。同包 `LdrBkupList.txt` 的固定列表也不能代替完整 BK4 参数表；其中没有 `0xfa0080`，不能据此声称实际 compact／full 记录选择已经接通。

为了验证具体描述槽的消费，另用两个明确独立的原代码入口：

- 原 `0xfe054794` 片段从原查询输出的第3槽加载分区和两个地址，得到 `W0=8`、`X26=0x809a08e00`、`X25=0x809a21dff`，停在原 FAT 挂载函数 `0xfe057f0c` 之前。
- 另调原文件包装器 `0xfe057e98`，输入该槽的原路径与目标地址；原代码将目标保存在 `X21`，停在原文件打开 `0xfe057fa0` 之前。这个独立调用不表示前一次 FAT 挂载成功。

静态原链后续为 `0xfe057fa0` 文件打开、`0xfe058178` 字节流读取；文件辅助函数返回后才进行所列范围的长度比较。本轮没有为这些函数提供文件系统或设备回复，也没有执行其正常完整流程，更没有把文件放入候选地址来制造成功。

## 三份文件与 CP 地址域相符

同一第二记录还指定 TOMCO 和 CP 主程序。用原 CP `0xb54930` 的四项64位范围表换算，而非直接截掉高位：

| 原文件 | 描述中的物理目标 | 原 CP 表换算地址 | 原文件长度 |
| --- | --- | --- | --- |
| `DmmCfg.bin` | `0x809a08e00` | `0x09a08e00` | 43,320 |
| `tomco.txt` | `0x800100000` | `0x00100000` | 710 |
| `cpapp-b.bin` | `0x800108000` | `0x00108000` | 15,980,568 |

这将此前的 DMM 源候选、TOMCO 原解析基址和 CP 原镜像地址接到了共同的原装载描述。它仍是原常量表的换算，不证明物理页已读取、实机 MMU／TLB 已设置或用户机身使用了该默认记录。没有恢复 DRAM 芯片型号／驱动、CMOS RAW、实际缓存或完整色彩 ISP。
