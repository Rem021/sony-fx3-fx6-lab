## 原接收注册与有界验证

原函数 `0x4d77e4` 调用 `0x49ef00`，注册队列 `0x61003c`、回调 `0xab95e1`、用户参数 0，并把原分配出的注册记录保存到 `0x13f8fd8`。原记录 `+8` 写入队列分派包装器 `0xa874e3`，`+0x14` 写入服务回调；原队列上下文 `+0x14` 指向该记录。

在已声明的 RAM 元数据池、索引初态、上下文 0、IRQ mask=1、临界区返回 0 条件下，这些指针由原分配和注册指令产生，未用钩子塞入回调、注册记录或服务成功结果。三个 context 1/5/7 原 NRV 请求均保留上一轮的原消息头、216 字节长度和 14 字节核心字段写入。

本轮分别验证了三个明确边界，不能合并成一次成功请求：

1. **原注册完成**：原 `0x4d77e4 → 0x49ef00` 返回 0，原队列与回调记录关联成立。
2. **原提交前缀**：另从原 `0xa878ca` 入口使用原请求指针执行 `0x49f368`，停在 `0x52bd1c` 的内核线程身份查询之前。没有补造内核身份、没有完成同步提交。
3. **单独进入原注册回调**：使用原记录里的 `0xab95e1`，原回调读取消息头的长度与回复 ID，停在 `0xab71cc` 分派器第一条指令前；实参为 `R0=0x9005601f`、`R1=原消息指针`、`R2=216`。这不是前一步真实交付的回执。

严格模式不提供上下文／临界区适配，原注册路径停在 `0x52c488` 的 MPIDR 读取前，元数据消耗仍为 0。它没有注册成功。合计 **4 组有界案例**：3 组适配环境中的原注册／提交边界／独立回调前缀，1 组严格边界。没有服务回复、图像缓冲或物理像素。

## 申请处理与配置来源：静态证据

原分派器 `0xab71cc` 从请求拷贝最多 40 字节到局部帧，按请求类型查 `0xd11f94` 的 46 项表。表内 `0x20` 项是原 Thumb 指针 `0xab6191`。以下均来自有哈希的原窗口，**没有执行处理器或填写回复**：

- 处理器把请求类型加 `0x8000`，与客户端期待的 `0x8020` 相符；请求 `u16+0x14` 经局部帧 `+0x20` 转到回复 `u16+6`。
- 请求 `u32+4` 的 `0x4af` 经局部帧 `+0x10` 传给 `0xab9830`，后者按 key 遍历单位配置表。它还依赖运行期单位、句柄和 extent 状态。
- 符合句柄／模式条件时，`0xab9e28` 从 extent 描述记录计算 64 位基址加偏移，连同大小写到 16 字节返回记录。没有从真实服务取得这些值；不能把静态字段形式当作可用物理地址。

配置初始化 `0xaba7b6` 读入 key／ID 列表到 RAM `0x1fba6d0/0x1fbc6d0`，并把表指针写到 `0x13f8ff4`。它通过原跳板 `0xab60ae → 0x4d7a84`（`dmm_module_GetConfigData`）读取。后者调用 `0xa84be8` 查询参数 **`0xfa0182`**，把取得的 64 位值按 `0xb54930` 范围表换算，再经 `0x53894c` 转换后拷贝；流读取偏移保存在 `0x13f8ffc`。

这些 RAM 表地址已超出这份平面 CP 文件覆盖范围。尚未取得参数 `0xfa0182` 的正常生产者、配置流明文和填充后的单位 `0x4af` 表。因此本轮证明了从申请到配置依赖的原代码关系，没有恢复真实缓存配置、CMOS RAW、MAIN 像素绑定或完整色彩处理链。
