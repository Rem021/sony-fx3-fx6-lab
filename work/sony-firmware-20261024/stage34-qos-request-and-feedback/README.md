# FX3 QoS 请求、确认与码率数值转换

本轮确认码率还有一条独立的QoS消息路径。原代码在显式客体输入下，可以把目标字段值16,000,000精确转换；16,000,001至16,000,063会向下取整到16,000,000，较低的trace上限还会限幅。**这不是FF模板默认码率、真实上游单位或16Mbps实录的证明。** 上阶段已证实的现有FH主录参数不匹配仍然成立。

另一个实质发现是：原static-QoS动作的一个前缀先缓存参数，再组装0x117确认；到确认发送入口之前没有执行编码参数转换或HAL应用。即使给出0目标或0 trace上限，该前缀也组装同样的确认，而后面的原转换片段会进入诊断。因此，收到确认不能替代实际应用、参数回读与码流验收。

## 两种不同的码率结构

| 结构 | 本轮已绑定字段 | 执行范围 |
|---|---|---|
| set-QoS请求，0x48字节 | +4为目标更新标志，+8为32位目标值 | 原缓存设置器确实按标志读取/保存 |
| 发送封套，0x54字节 | CID0x2103、MID0x010a，0x4通道字段后接原0x48请求 | 原复制与头部构建；消息对象构造之前停止 |
| Open完成载荷 | +0x20为64位trace值，+0x28为64位target值，+0x30为64位CPB值 | 原解码与回复复制，但输入来自明确合成的HAL缓存 |

此前检索到的`[CODEC V]target_bitrate`诊断属于`open_comp_param`。它描述的是完成/缓存结果，不是set-QoS请求的同一布局。本轮分别核对，不把64位完成字段套在32位请求字段上。

尚未绑定真实策略如何生成请求、字段的上游单位、FF行386/preset0x19450默认值，以及实际HAL返回值。16,000,000是候选16Mbps数值实验，不能由函数名和转换公式单独确立实机单位或录制码率。

## 原缓存动作与确认的先后关系

原0x24d738动作在日志之后的0x24d78c处，把通道后面的0x48请求交给0x2486fc/0x248b8c。目标更新标志为1时，它保存新值到QoS对象+0x18/+0xe0；标志为0时保留旧值。随后原指令构造CID0x2103/MID0x0117、长度0x14、其余本轮通道与状态字段为0的确认包。

本轮在0x27dab4回复发送包装器入口停止。调用轨迹包含缓存设置与确认构建，未进入0x248d64参数转换或HAL。原数据还显示另一个同类缓存/确认动作，以及一个直接组装确认的动作前缀；它们的真实数值状态、实际可达条件与完整运行顺序尚未验证。

独立执行的已接收消息分派fixture确认：本轮0x54请求可沿原源/CID/通道/MID检查抵达0x249e1c的首个诊断之前；此处后续调用0x251f90状态分派器，本轮没有连成完整状态机或真实传输。

所以本轮只证明一种原处理前缀可以在转换之前组装确认，不推断所有0x117的完整语义，更不把确认当作“目标码率已应用”。实际方案仍需检查当前配置代次、处理动作、后续消费/编码、对应返回值及真实样片。

## 原数值转换结果

在原0x248d64的独立调用fixture中，缓存目标取自前述原设置器，trace上限为明确的原缓存字段输入。函数先取目标与有效trace上限的较小值，再构造目标更新字段。本轮在随后的第一个原诊断之前停止，没有执行整个固件参数提交。

| 请求/缓存条件 | 原目标字段结果 | 边界 |
|---|---|---|
| 目标16,000,000，trace上限20,000,000，更新开 | 精确16,000,000 | 更新位0x80已置，原诊断前 |
| 目标16,000,001，同上 | 16,000,000 | 同上 |
| 目标16,000,063，同上 | 16,000,000 | 同上 |
| 目标16,000,000，trace上限10,000,000 | 10,000,000 | 限幅后的字段，原诊断前 |
| 新填16,000,000但更新标志关，旧缓存10,000,000 | 保留旧缓存；目标输出未写、更新位未置 | 清理待处理字段的运行时调用之前 |
| 更新开，目标0 | 未生成目标字段 | 0x248f50发起诊断之前 |
| 更新开，trace上限0 | 未生成目标字段 | 0x248e8c发起诊断之前 |

原解码形式是`(value_minus_one + 1) << (6 + scale)`。这些有效输入路径使用scale0，数值粒度64；输出字+0x18的写入及更新位均由原指令产生。未写字段使用显式哨兵核对，避免把预先填好的输出当作固件结果。

这是有条件的数值表达/限幅证据，不是全体范围的支持验证。原帧参数准备调用点位于0x2463f8、0x24674c，真实调用者、全部参数、后续日志、待处理清理和HAL消费均未执行。不同阶段的独立调用顺序也不代表实机顺序。

## 合成HAL缓存只用于核对反馈布局

对流类型14/HEVC_MP4和21/XAVC_PROXY_HEVC，原0x22c3cc选择同类HEVC缓存参数路径。给定显式的common+0xe000指针及合成参数字段，原0x225b7c能解码trace、target与CPB，再由0x246154复制到Open完成载荷的对应64位字段。

两个对照分别使用trace18,000,000/target16,000,000与trace12,000,000/target9,000,000，特意让两者不同以核对字段身份。合成原缓存字节和读取后未变的校验均保留。

**没有从HAL返回、实际通道或机身中读取这些数值。** 本轮没有执行0x22ba98外层锁/通道查询，也没有执行实际Open完成消息或真实回读。不能拿这两组显式输入充当FF默认值或实机反馈。
