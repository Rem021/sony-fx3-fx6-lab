# FX3 原图像记录表与描述符生命周期（2026-10-29）

尚未达到“修改后的 FX3 固件可正常刷入”的停止条件。本轮把原 MLUT 调用之后的缓冲管理推进到描述符复用、到期清理和输出参数交接，并修正上一轮对一个入口的命名。13 组有界原指令验证通过；没有真实像素、完整 VENICE/FX5 ISP、修改固件包或设备执行。

沿用 [上轮封存](../stp-buffer-20261029/README.md)，校验其 29 个文件后开始；未重跑其已封存实验，也未改写其记录。这里只在 Unicorn 的 RAM 中执行原 CP 指令。CP 原件 SHA-256 为 `c90d00d807874a5309dc1b65b203287e83608ceee513cc57b53409333fb6bcba`，VA = 文件偏移 + `0x108000`。

## 本轮确认的连接

1. 原构造函数 `0x9cf02c` 初始化 VA `0x1172e70` 起的 240 条记录，每条 `0x88` 字节。四个区段各预留 60 条，区段间距 `0x1fe0`；组 3 起点是 `0x1178e10`。本轮从填充字节 `a7` 开始执行，逐字节检查全部记录的初始化结果及未触碰的填充区，停在析构登记 `0x5579d4` 前。没有提供登记成功返回。
2. 文件初始配置中，`0xf1b630` 的四组计数是 `[2, 2, 60, 1]`；`0xf1b620` 为 `[0, 1, 1, 1]`。这些字段可在运行时变化，不能当作当前机身 RAM，也不能把组号称作 MAIN、监看或物理 ISP 引擎。
3. 原 `0x9cee38` 根据已有描述符的两个字匹配，写入记录 `+0x64` 的帧/子帧组合和相关元数据。本轮显式提供帧号、时间字及已有描述符，执行原写入函数，未伪造传感器数据或分配回复。
4. 原 `0x9cecb8` 对比 `(frame << 8) + subframe` 与记录 `+0x64`、`+0x68` 的 32 位差值，按符号条件触发清理。过期借用描述符被原代码清空；未来标记保留；带所有权的描述符停在原释放包装器 `0x44de7c` 前，未提供释放成功值。
5. 原 `0x403a78` 会检查现有记录、查询键和状态；适用时复用记录，否则释放/清理旧对象并进入申请包装器。键 `0x440` 与 `0x614` 的两个正例均由原代码复制 `0x50` 字节描述符，强制将复制件 `+6` 所有权标志清零，随后原临时对象清理不会释放原记录。原记录的所有权标志仍为 1。
6. 两个正例继续由原调用者构造输出参数，在 `0x428f0c` 前捕获第三参数：`+0x18=0`、`+0x20=1`，`+0x28/+0x2c/+0x30` 是三个来自描述符的测试字，`+0x68=0`、`+0x78=5`。这证明这段元数据交接，而不是这些字已指向有效像素。
7. 原空记录需要申请、旧借用记录键不匹配、或状态标志需要查询时，执行均推进到共用入口 `0x4a032c`，参数前两字为 `0x2a, 5`，输入栈字为 2。本轮停在此入口，未提供任何返回值；静态窗口可见其后的句柄表/位图选择，但尚不据此命名具体服务或声称已进行服务收发。

## 对上一轮解释的修正

上轮 `buffer-query-results.json` 的 `before_original_frame_query` 只是停止点标签。展开原函数后，`0x9cecb8` 应解释为**按帧标记清理记录**，不能把原始 R0 当成“成功取得帧”的证明。`0x403a78` 也包含复用与申请，不能简化成只读查询。旧封存保持原样；本轮 [源码结果](lifecycle-source-results.json) 明确记录修正。

初次断言把输出参数中的标志相对偏移写成 `+0x28`，实际是 `+0x20`；已按原指令修正，并保留 [失败断言与观察值](attempts/payload-offset-assertion.json)。该调试观察不计入正式 13 组。
