## 更正上一轮格式字段

stage52 将 `record+0x36` 的单字节值 5 命名为格式，名称有误。原编码读者实际从 `record+0x28` 取输入格式、从 `+0x29` 取伴随开关；`+0x36` 是十个连续 16 位几何字段的起点。stage52 输入在该几何字段的低字节放了 5，实际格式 `+0x28` 仍为 0，因此不能引用它作为格式 5 的生产证据。

该轮“48 字节复制”和选定的 `+0x3e/+0x40 = 1920×1080` 字节结果仍成立；队列/帧槽寿命证据不受此命名错误影响。旧原件、执行源码和封存回执保留，修正在[范围更正](scope-corrections.json)和当前持续目标中登记。

原虚表对应的 RTTI 名称是 `C_DataflowInfra_Entry_ImageSizeInfo`；另一个标签绑定为 `C_DataflowInfra_Entry_CameraInfo`。本轮用原类型构造和 setter 产生输入，避免继续依赖上一轮的手写字段暂称。

## 原生生成与填充

执行链为：

1. 原 `0x95b9c` 在声明的 RAM 后备缓冲上完成 SSYC 容器构造；`SSYC` 根头由原代码生成。
2. 原 `0x91dd4` 构造 `ImageSizeInfo`，12 次原 setter 设置格式、开关及十项几何，原 `0x91e68` 导出 48 字节内容。
3. 原 `0x0a4894` 再次原生构造/导入该类型，通过原序列化写者 `0x952d4` 写入事件。其余八类标签由各自原构造器与 typed 发布入口加入。
4. 原帧槽分配器借出并清空记录后，**完整原 `0x1479d8`** 从入口运行到正常栈返回。它实际执行全部标签查找、有效标志写入、CameraInfo 翻译 helper `0x12bd78`、伴随复制、两个句柄字段及最后一项标签复制。

容器地址、后备存储、输入数值、组件状态及句柄均是声明输入。其它标签使用原构造器的默认内容，不能称为真实相机参数或语义完整的帧。没有执行入队调度、IPC 传输、整个输入控制器动作或实机数据生产。

## 对照结果

| 声明输入/操作 | 原帧填充结果 | 独立原编码打包结果 |
|---|---|---|
| 九类标签齐备，1920×1080，输入格式 5 | 八项记录内查找有效标志均为 1，格式位于 `+0x28`，完整函数返回 1 | start-input `+0xe8/+0xea = 1920×1080`，`+0xf8 = 5`，到真实锁包装器入口前停止 |
| 在同一原容器中替换 ImageSizeInfo 为 1280×720、格式 6，再借槽 1 | 容器仍为九项，没有追加重复键；新槽取得新值，槽 0 的旧值保持 | 匹配高度的声明描述符下，生成 1280×720、格式 6，到同一锁边界前停止 |
| 缺 ImageSizeInfo，其余八类存在 | 图像有效字节为 0，几何/格式为零，**完整函数仍返回 1** | 格式转换成原无效/默认值 8；对 1080 高度的声明描述符进入原 padding 诊断前停止 |
| 缺 CameraInfo，图像标签仍在 | CameraInfo 有效字节为 0，图像几何仍正确，**完整函数仍返回 1** | 几何片段仍可打包 1920×1080/格式 5；不能当作其余字段或完整请求有效 |

函数返回 1 来自尾部最后一类标签的读取结果，不是前面所有标签的合并验证。因此应分别读取有效字节；不能把“完整 helper 返回”当作整帧有效或可以提交编码的证明。上层实际如何处理缺标签仍需继续绑定，本轮没有证明实机缺陷。

编码打包从独立片段 `0x24cfb8` 进入，使用同一客体中刚由完整帧填充产生、且此后未改的记录。入口寄存器和外部描述符高度是声明上下文，正常几何诊断之前的动作部分未执行；没有绕过或提供日志/锁成功返回，也没有执行真实 Start 包装器 `0x22b358`。两类输入格式 5/6 与 MAIN 流类型号仍是不同命名空间。
