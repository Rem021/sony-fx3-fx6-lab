## 两个参数字段的实际来路

此前原同步片段读取参数对象 `+0x900/+0x908`，但该参数向量由实验预填。本轮沿原 getter 和构造器恢复：

```text
原 GetInfo 构造函数 VA 0x9d1038
  → 场景状态 +0x13a8 的 0x32c 字节处理阶段记录
  → 原 ARM memcpy 两次复制到 +0x16d4 和 +0x1074
  → 原向量构造器 VA 0x9d7210：vector[+0xc] = 场景状态 +0xde0
  → 参数 +0x900 = 场景状态 +0x16e0 = 阶段记录 +0xc
  → 参数 +0x908 = 场景状态 +0x16e8 = 阶段记录 +0x14
  → 原 ImageParam_Sync 片段生成资源配置
  → 原资源选择、分配、所有权与色彩 SDK
```

记录 `+0xc` 来自构造函数的一个栈参数；`+0x14` 则由原处理回调指针的比较分支产生，并受原全局条件影响。它们不能直接解释为用户菜单的录像模式编号。原诊断字符串分别为 `GetInfo.cpp` 与 `ImageParam_Sync.cpp`；脚本中早期 `drive-info` 片段标签仅为研究文件名，不充当原类名或物理驱动语义。

`0x32c` 是所查原复制窗口的长度；构造函数只写其中部分字段，剩余清零内容属于声明场景夹具，不能据此声称完整场景已初始化。

原默认 getter 返回向量 `0x118b6c0`，另一 getter 可返回 `0x118b788`。本轮真正执行的是原向量构造器在声明 RAM 地址构造同一布局；没有宣称读回这两处真实机身 RAM。[原片段、常量与调用候选](vector-source-results.json)

## 七组连续检查

每组先执行原构造函数，再执行原两次复制与原向量构造，最后让原同步代码消费实际生成的字段，没有在中途手工填写 `+0x900/+0x908` 或资源配置号。回调函数体不执行；下表地址均是构造函数接收的原文件中已有 Thumb 指针。

新增原调用片段 `VA 0x407a94..0x407ab4` 自行提供 `0x40fc09` 和栈参数 0。进入该片段的分支条件与寄存器 live-in 仍是夹具，尚未执行整个正常调用者；其他几组的回调／栈参数仍直接声明。

| 原处理回调指针 | 原栈参数 | 声明的同步标志 | 原构造类型 | 同步输出四字段 | 后续 |
|---|---:|---:|---:|---|---|
| 默认 wrapper 的 `0x416105` | 0 | 0 | 0 | `0,0,0,0` | 配置为零，停止在资源请求前 |
| `0x40bb9d` | 0 | 0 | 1 | `8,8,1,1` | 原 kind 15 请求没有申请 VFX |
| `0x40bb9d` | 0 | 1 | 1 | `8,10,1,2` | 同上，输出槽保持哨兵值 |
| `0x40de65` | 0 | 0 | 3 | `1,1,1,1` | 原分配器得到 group 0 |
| `0x40fc09` | 1 | 0 | 2 | `1,5,1,2` | 原分配器得到 group 5 |
| `0x40fc09` | 4 | 0 | 2 | `5,7,2,4` | 原分配器得到 group 4 |
| 原调用片段提供的 `0x40fc09` | 0 | 0 | 2 | `1,1,1,1` | 原分配器得到 group 0 |

后四组沿既有原控制器与 SDK 生成 look 22 命令。look 22、空闲资源表、硬件／锁／队列成功、EI 参数仍沿用明确夹具；本轮没有证明正常菜单会自然选中该 look，也没有执行回调完成或读取像素。

这比先前直接填写两个参数字段多恢复了一层实际生产关系，但依然需要证明正常拍摄调用者如何选择分支、回调和栈参数，以及对应输入／输出缓冲通向哪里。[七组执行及原写入记录](scene-context-results.json)
