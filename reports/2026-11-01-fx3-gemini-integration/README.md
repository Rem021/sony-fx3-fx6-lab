## 记录中的必要更正

1. 固定read0实际为**17B请求 +12B响应头 +88B数据体**。285/286中“12B请求”是文字/键名错误；以批准的stream.c中read0_packet[17]及sizeof发送为准。原批准包和历史回执保留。
2. STOP实际返回**STALL（status3）**，随后对象释放成功，原口MSC和存储驱动恢复，helper/observer退出；不能写成STOP返回status0，也不能据此证明全部机内线程均已结束。
3. SERVICE实现调用的是**USBDeviceOpen**。实际成功打开与主机串行收发不证明机内全局DMM/选中路径不存在其他访问；原方案也承认默认管道并发未完全排除。286对互斥/析构路径的静态结论可保留，不能扩大为已验证的整体会话隔离。
4. 固定read0成功对原件A/B门控的意义仍依赖原处理器和表绑定成立；不能宣称最高认证级别或同机固件哈希已证明。
5. 新缓存只存同机一致性布尔值，不复制历史缓存中的原串号或隐私key。

## 如何结合模拟器与真机成果

- 真机通信05作为已验证的受控服务入口基线，保留固定构建和全部回执；不再重复通信03的已解决版本校验问题。
- VM用于原请求/消费者、菜单状态、内存布局和绘制协议预演；新的菜单或H.265候选先经过这条线核对全部消费者。模型回成功、黑色清屏或VM退出0都不能代替真实编码器输出。
- VM运行链仍由既有Claude Lead串行持有；当前GPE独立模块和静态审计由该Lead验收后接入。本轮没有接管runtime/STATE.json、拿运行锁、重启QEMU或给其他agent发送指令。
- 原件AdjustControl的op0xFF只是内存缓存槽，不能加载libJit；op0x00涉及挂载/dev/nflasha6到/tmp/jiritsu，且加载前检查/tmp/jbusy。下一步先把创建者、挂载/卸载、路径/槽所有权及失败退出合同核清，再决定最小诊断范围，不能用/tmp名称将文件分支称为纯RAM。
- 第2项后半段仍是机内受限空任务入口；完整健康备份、独立恢复/写回、目标MAIN 1080p HEVC实录与持久化准入仍未通过。FX5/VENICE整套跨刷没有因此获得可用方案。
