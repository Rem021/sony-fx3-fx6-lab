## 原厂实际插件合同

服务线程按固定路径复制和 dlopen 库，再依次查找这些导出：

| 导出 | 原指令明确使用的合同 |
|---|---|
| CreateScriptI | 返回对象指针，保存到服务对象+0x20；调用前没有准备明确的语义参数 |
| LoadScriptI | x0为该对象，x1为排队的脚本路径指针；只检查返回值低8位 |
| RunScriptI | x0为对象，x1为清零后局部初始化的0x18f8字节栈上下文，x2为排队参数；返回值随后被覆盖，未作成功判定 |
| DestroyScriptI | 接收对象指针；返回值未检查，随后dlclose |

错误路径还会读取对象+0x38的字符串指针。完整对象和运行上下文布局尚未恢复，不能用空指针、空结构体或只补同名导出冒充适配。第227轮step/status并非这些导出，也未适配这里的线程上下文。

请求发送器分配32字节消息，将操作码及三个**原指针**写入偏移0、8、16、24，没有在该函数内深复制字符串。适配时必须另行证明数据在异步消费期间仍有效；排队成功不是脚本执行完成。

## 运行与停止的具体边界

普通run先排队操作1，看到状态14后再排队操作2，随后返回；它不等待RunScriptI或其子进程完成。RunScriptI是在Jiritsu线程里同步间接调用的，返回后才继续处理后续队列。因此若该插件调用阻塞，同线程暂不能消费停止操作3；这是一条静态可行时序，并非已观察到的真机故障。

stop发送操作3后轮询状态10。计数初值31，最多请求30次100000微秒usleep，名义等待约3秒；真实调度与睡眠时长未测。排队失败或超时会把状态写为30并返回，这个函数不join、不kill、不dlclose。

即使看到状态10，也不独立证明线程已经返回：工作线程在`0xc040`先写10，最后的ret在`0xc058`。另一个exit函数确实调用osal_wait_thread_exit，但随后直接清空线程句柄，没有检查该调用的返回值。不能通过状态10、句柄清空或run返回宣布所有代码／后代都已停止。
