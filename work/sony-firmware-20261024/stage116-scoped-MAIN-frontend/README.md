# FX3 7.02：受限 MAIN 前端副本与完整参数的外部数据寿命

2026-10-27。**新增一个编译执行的 guest-only 前端候选：只在声明的目标门控、原调用点与源核心条件下，调用原 MPR 通用函数产生 VPC6，复制原参数值范围，保留质量6/帧率3和其它字节。** 它没有接入真实应用、菜单、Sony配置代次或相机，也不是可部署模块。

另确认原 Set/GetMovieRecParam 的关键寿命差异：保存器会为 `+0x118` 长度、`+0x120` 指针描述的外部数据另做复制，并重写保存指针；读取器只复制结构，返回的指针仍指向共享存储。第二次保存可改变旧读回结构所指的数据，因此整包字节副本不是独立拥有全部内容的快照。

[正式结果](run-scoped-original-data-writes-20261027/frontend-trial-results.json)：8 组正例、30 组拒绝对照、4 组原应用调用点，共78个有界阶段。全部只在 Mac Unicorn 内存中执行，无 Windows、UU、相机接口、真实锁、模块装载或刷写。

## 前端候选做了什么

[scoped_frontend.c](scoped_frontend.c)由 Apple clang21 以 `aarch64-none-elf` 编译，链接到客体中的三个原函数：

- 原 `GetVideoParamComb(1,2,0,1,0)`，以原指令返回6。
- 原 `movieRecParam` 构造器，调用同固件原 memset 清零0x1c0（448）字节。
- 同固件原 memcpy，复制0x1bd（445）字节有效参数范围。

候选随后仅写目标副本 `+0x170` 的类型。源核心必须为 `[5,6,3]`，副本成为 `[6,6,3]`；有效值范围内只有 `+0x170` 这一字节不同，三个末尾填充字节由构造器归零。质量不会为匹配FF而全局改成8。

复制保留了声明源中的音频、代理和其它字段字节。**这些源字节是实验数据，没有经过完整应用构包或参数检查，不能称为实际有效的音频/代理配置。** 外部数据指针先保持借用，前端没有凭结构复制就声称拥有其数据。

客体门控检查固定试验控制地址、magic、armed/idle、session、epoch、源/目标地址和长度、两者及控制区重叠、目标核心、外部数据与目标/控制区重叠。对照覆盖错magic、关闭/忙、两种代次错误、错调用点、容量不足、重叠、越界指针、质量8、其它帧率和三类外部数据范围错误；拒绝不写副本。

这些是**我们定义的试验ABI和地址范围**，不是Sony的安全入口、实机空闲状态或可信代次。没有实际分配器、共同锁、相机身份、并发防护或源对象生命期证明。候选只准备副本，不执行保存器或发送请求；不能据其检查放行任意外部数据长度。

## 原应用的两个保存调用点

原 `mpr_SetMovieRecParam` 内的 `0x2e6f7bc`、`0x2e6f9b0` 都把 X19 参数对象交给同一 `SetMovieRecParam` 导入。本轮以独立声明的 X19执行各调用前原 MOV/BL，停在导入之前，核对X0与原LR。

编译候选接受的调用点数值来自这两处，但该数值仍由试验调用者提供。**没有安装拦截、改原调用指令，或证明实际应用会在可信目标配置下调用候选。** 前一处周围有额外控制操作，两处的完整前置构建和同步没有执行；不能只覆盖其中一个就称为正常运行时全覆盖。

## 原保存和读取片段

原 `movieRecParam` 构造清零448字节，Set/Get复制445字节，不能把两种长度混同。

1. 原 SetMovieRecParam 入口执行原 memset和memcpy，在首个诊断前停止，栈中的445字节等于前端副本。
2. 另一个独立后检查/后锁帧执行原保存片段，将445字节复制到库内共享对象。外部长度0时，原代码清零共享长度/指针；声明长度48时，原代码另复制48字节到共享区并改写指针。随后停在解锁之前。
3. 原 GetMovieRecParam 序言在读锁前停止；独立后锁片段复制445字节到读回对象，再停于解锁前。结构中的外部指针指向共享副本，读取器没有再复制外部数据。
4. 对48字节控制，再运行另一个独立原保存片段，改变共享副本内容。先前读回的445字节结构保持不变，指针仍相同，但指向的数据已经改变。

所有锁、完整参数检查、诊断、后续消费者和函数整体完成均未执行。48字节是声明控制，**没有由此建立原共享外部数据区的最大容量**。这不是实机竞态、固件缺陷或完整并发安全证明。

因此，未来诊断若要跨事务保留完整参数，必须同时确认外部长度、容量、所有权、同步和复制完成，再导出独立数据副本；仅保存结构和指针不够。目标前端还须让借用的源数据持续有效到原保存器完成复制。

## 边界和复核

Sony指令与原文件未修改。自编译对象的三处CALL26只链接到我们自己的LDR/BR地址跳板，再执行原函数；跳板不提供成功返回或输出。原库数据页仅在guest中按已定位的保存范围允许写入，每阶段检查其它映射字节、scratch和栈保护区不变；原构造、memcpy/memset和类型helper自己返回。

第一次试验被沿用执行器的“只许写栈/scratch”检查挡在原共享数据复制，未形成通过结果。为本实验逐阶段增加精确guest数据输出范围后，78阶段通过；没有扩大到主机或相机，也未改Sony原逻辑。初始未运行的C/对象因设计复查补上控制区和外部数据重叠检查后单独保留，不是通过版本。

同一代理完成源、边界与哈希复核，不属于独立引擎复验。本轮候选没有替换阶段75后端原型，两者都不可部署。
