# FX3：VCD侧QoS消费与已有缓冲转交

**本轮证明了上一轮生成的QoS目标字怎样被原MIPS代码消费，以及在明确的已有缓冲输入下怎样继续复制。** 这把两份参数可能不一致的问题推进到编码器侧的软件状态；没有证明硬件编码器已经采用目标值。

仍只用Mac离线执行。相机、Windows和UU均未操作；C适配器、官方文件、模块和刷写权限未改变，完整16项目标继续保留。

## 新接通的原路径

stage78正式结果保存的64字节前缀，原样交给同版官方`vcd_firmware_imola2.bin`中的`18fdb4`。其目标更新分支在`18fe30`检查掩码`80`，再调用`18faa0`：

1. 从QoS块`+18`读取编码后的目标字，写入声明状态对象`+198`。
2. 将状态对象`+280`的bit29置位。
3. 将状态对象`+1`置为1。

以上偏移来自实际原指令与读写轨迹。“状态对象”由本轮明确提供RAM，不是机身读回或实际流的完整初始化结果。原例程不读取448字节codec块，因此不能把它描述成直接覆盖那个块；它更新的是另一个参数状态。

stage78只保存了该输出的前64字节，本轮只允许读取这64字节，未补齐或宣称重建了完整128字节传输。实际目标分支只读掩码4字节和目标字4字节。

## 对照结果

两种旧内存值A5/C3各做六组输入：

| 输入 | 原消费结果 |
| --- | --- |
| 可选参数关闭 | 声明的16M状态保持，不置待处理字节 |
| 原生成16M调整 | 状态目标16M，置更新位和待处理字节 |
| 原生成20M调整 | 状态目标20M，置更新位和待处理字节 |
| 保留20M字、只把更新掩码清零的人工负向对照 | 不读目标字，状态仍为16M |
| 原尾部字段复制选项 | 原代码把240000、8008及两个零字节组成8字节参数；停在`1a085c`入口前 |
| 原生成20M、再声明后端无句柄 | 先完成同样的消费；后续更新例程停在未知GP运行时状态读取前 |

“20M字保留而更新位关闭”只是验证原分支确实受标志控制，没有生成或执行机身补丁。尾部字段的数值关系仍为`240000/8008 = 30000/1001`，本轮只验证下一层收到的字节，没有执行时序helper或验收真实帧率，精确30.000仍单列。

## 已有缓冲条件下的下一步

对16M和20M四个正例，在同一个客体中独立调用原`19bda4`。明确提供一个已有句柄与后备RAM缓冲，原代码沿非空分支转换所存地址、复制292字节参数，并设置后端状态的`40`更新位：

- 目的缓冲`+1c..+13f`逐字节等于源参数，目标字位于目的缓冲`+28`；16M/20M各自保持。
- 前后保护区不变；整个源状态只发生已声明的后端更新位变化。
- 外层待处理字节仍为1，未由本试验清除；不能据此宣称上层提交、完成通知、所有权归还或代码卸载已完成。

句柄、地址和缓冲均是试验输入，不是原分配器返回或真实物理映射。292字节内还有未分类的声明旧值，本轮不将它认定为语义完整、可提交硬件的请求。完整上层调用、自然执行顺序和硬件完成均未执行。

无句柄对照在原`19bdd8`的GP相对读取之前停止。后续分配路径还包含当前Capstone模式未识别的指令编码；保留原字节，不识别为某个已知指令、不替换成NOP、不补线程或分配返回。外层`18fd58`还有`BE000064`的MMIO读取，也保持未执行。以上边界不是对宿主Mac或相机的访问。
