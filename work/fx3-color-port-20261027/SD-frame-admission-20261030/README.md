# FX3 SD 输入长度、验签与解密数据的对应关系

**本轮接上了历史 SD 更新引擎中，外层 FDAT 长度、实际输入缓冲区、签名区间及后续解密之间的静态调用关系。没有找到可让目标修改内容通过正常验签的路径，仍未达到可正常刷入 FX3 的门槛。**

重启恢复时，上一阶段 [Pro 目录研究](../Pro-catalog-sources-20261030/README.md)的 70 个封存文件全部核对通过；未重复下载、查询目录或进行 RSA 修改测试。当前没有子 agent，未重启另一任务的设备采集、恢复或待批准操作。本任务没有待答确认。

本轮只读取既有原件，没有执行 Sony 程序、启动更新器、连接相机、运行 guest、生成修改固件或接触私有签名材料。

## 原件适用范围

代码取自官方 3.00 Windows 升级包中 **2.04/2.05 过渡更新引擎**的 initrd；三个相关库在两版之间逐字节相同。它们不是用户机身当前安装的 7.02 引擎读回件。之前对 7.02 原包的数学验签是真实 7.02 数据，但不能据此把历史校验程序说成当前机身校验程序。

从三个原库完整捕获 51 个函数，逐个对照 ELF 装载段、导出符号、原始字节与 SHA-256；另外核对 29 个关键指令位置和 9 个原虚表分派关系。没有通过自写函数或成功 stub 补齐原调用。详见 [原合同](original-contract.json)、[缓冲区合同](flow-contract.json)、[末端合同](tail-flow-contract.json)及 [验证回执](verification-receipt.json)。

[索尼当前 FX3 7.02 页面](https://www.sony.com/electronics/support/camcorders-and-video-cameras-interchangeable-lens-camcorders/ilme-fx3/software/00298561)仍将适用机型列为 ILME-FX3，并规定 2.02 及更早版本需要先经过 2.04/2.05。该页面没有为本任务的跨型号修改提供准入证据。[研究作者](https://github.com/ma1co/fwtool.py/issues/39)指出的 SD 输入组件与本轮原件名称吻合，但其 A7 IV 研究不能替代 FX3 实机结论。

## 长度如何进入签名函数

`BufferManager::Initialize`（`libsdfileinputupdaterapi.so:0x9a48`）读取 `sysconf` 页大小 P，形成分配长度：

`M = uint32(-P) & 0x40000000`

随后保留一页及三个 `0x80000` 工作块，固件输入环形缓冲区容量为：

`C = M - P - 0x180000`

若页大小为 4096 且分配正常，C 为 `0x3fe7f000`（1,072,164,864 字节）。这只是原更新器的分配合同，**不是实测页大小、FX3 物理内存容量、缓存芯片规格或 RAW 缓冲区大小**。

`searchFDAT`（`0xa0e8`）读取大端 32 位 chunk 长度 L，并在 `0xa25c` 与当前空闲缓冲区大小比较。超过上限走错误路径。匹配首个 `FDAT` 后，L 经 `SetBuffSize`（`0x91d0`）写入解密对象 `+0x540`。

`execWriteFirm`（`0x95b8`）经过原条件变量等待，再请求 `RingBuffer::ReadDataWithoutCopy`。其返回实际长度 N，受请求长度、连续容量和已有数据量限制；不能直接把外层声明长度当成实际完整读入量。

在正常初始化及分配合同下，N 小于 1 GiB。对于 `N >= 272` 的输入，随后转为 32 位的 `N-256` 不会发生 4 GiB 截断。因此，“利用外层巨大长度，使验签只覆盖修改内容之前的一小段”这一特定设想，没有得到该正常路径的支持。未执行畸形输入或寻找可刷写 exploit。

## 验签和解密使用什么数据

设无拷贝读取返回的数据指针为 B。原代码使用：

| 用途 | 原代码中的位置或长度 |
|---|---|
| SHA-256 输入 | B，长度 `uint32(N-256)` |
| RSA 签名 | `B+N-256`，长度 256 |
| CBC IV | 验签返回成功后，从 `B+N-272` 读取 16 字节 |
| 密文长度状态 | 同时把 `N-272` 写入解密对象 `+0x538` |

原 `ReadDataWithoutCopy` 返回当前环形缓冲区读指针，**不推进读位置，也不扣减排队数据量**。后续 `DecryptorModule::updateData` 对同一个 ring 调用 `ReadData`，经 `readFromBuffer` 取出数据并推进读指针。至此能静态对应验签视图与后续解密输入，未发现两套独立文件偏移让修改后的密文直接替换已签名数据。

原 `VerifySignature` 要求 `RSA_verify` 返回值恰好为 1；函数清理后返回 0。`execWriteFirm:0x96bc` 只在该返回值为 0 时继续到 IV 读取和解密初始化。显示的失败分支进入 `ApiException` 抛出代码。本轮没有执行实际异常展开、线程调度或写入流程，也没有证明运行中缓冲区不变或没有竞争。

## 7.02 原包与这个区间的对应

仅解析三份原包的外层记录并复核原件 SHA-256，复用已封存的 RSA 结果，没有重做验签和损坏样本测试。7.02 原件：

| 项目 | 字节数或偏移 |
|---|---:|
| BODYDATA.DAT 总长度 | 811,876,768 |
| 第一个 FDAT 载荷文件偏移 | 132 |
| FDAT 载荷长度 | 811,876,624 |
| 密文长度 | 811,876,352 |
| 密文加 IV 的既有签名覆盖长度 | 811,876,368 |
| 签名长度 | 256 |
| FDAT 后的 DEND 记录 | 12 |

这与原函数 `N-256`、`N-272` 的区间一致。UFU 外层元数据或 DEND 不在这个已有签名覆盖区间内，但这不等于修改它们能改变已验证并进入解密的固件内容。[三包外层记录](original-wrapper-frames.json)、[既有 RSA 结果](../input-20261028/official-key-rsa-verification-results.json)

## 仍然开放的边界

这不是完整畸形输入安全审计。显示的长度检查没有单独建立 `N>=272`；过短输入可能产生减法下溢或把 IV 指针移到返回数据之前。部分读取未检查精确短读长度，部分 Seek 返回值也未被调用者检查。它们是待分析行为，**没有被证明能控制执行、安装修改包或正常启动**，也未向原程序或相机提交此类输入。

完整 FX5 专有供体、VENICE 实时 ISP 与传感器标定、FX3 的真实 RAW 输入及缓冲区适配、整套专业菜单到主录像素的行为仍缺。没有产生目标修改固件，没有证明当前 7.02 引擎接受修改，也没有正常启动及独立恢复回执。九项整体验收条件原样保留在 [验证回执](verification-receipt.json)。

本阶段推进了输入长度和数据对应的证据，不改变可刷入结论；达到门槛后停在实际刷机之前的用户要求继续有效。
