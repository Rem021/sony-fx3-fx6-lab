# FX3 7.02：原调用指令到临时栈副本，再返回原调用者

本轮把 stage57 的独立“生成临时副本，再把副本指针交给匹配器”推进为**离线客体中原调用指令真正进入编译包装函数，包装函数真正调用原匹配器**。两组目标输入中，编译器在自己的栈帧内生成152字节临时视图；在明确排除诊断代码的独立后半段，原匹配器读完该视图、返回386，编译器尾声恢复栈并返回原调用者，由原 `mov w23,w0` 接收结果。没有宿主设置匹配返回值或重写返回PC。

这是有边界的调用帧证据，**不是完整匹配器、真实钩子装载或硬件验收**。诊断未执行，后半段是复制保存状态后的独立执行。相机实际装载地址、Sony模块ABI、MMU、代码发布／指令缓存同步、真实 owner／配置代次／共同锁、全体消费者、Open／Start／HAL、成片及同机恢复仍待验收。目标与16项完整要求保持不变。

## 实验改动与原执行

本轮明确改变了**客体中的一个原调用指令**，不再声称整份客体代码完全原样：

- 原 `av-cam.bin+0x21ed18` 是调用原匹配器 `+0x225eb8` 的 `BL`。
- 原 LIRO import 装载及其原映像完整性检查通过后，才在内存客体中把这一条 `BL` 指向新分配的包装函数区域。
- 包装函数的唯一外部符号 `sony_matcher` 由试验链接器绑定到原匹配器入口，真正执行它的原指令。其他映像字节、匹配表、原预置均逐段保持；原固件文件没有修改。
- 新区域采用模型地址 `0xffffffc002000000`，在原映像之外、实验中满足直接分支范围。**这不是相机实际可用地址，也不是静态空洞或实机分配证明。** 不输出重封包固件、Sony可加载模块或刷写补丁。

原 queued Open、common 复制／初始化到调用点的路径使用既有空闲队列、ID和节点存储输入。真实运输、完整工厂启动和当前相机对象身份仍是未验证范围。新包装函数不接收人工匹配结果，不依赖一个额外的持久临时缓冲区。

## 临时副本与归还

`fx3_match_adapter(owner,source)` 先把原152字节输入复制到自己的栈，再检查复制内容的固定136字节描述、common 缓存描述及 MAIN1／tail10／tail25。只有候选 FH／16M 输入满足时，把栈副本 `+0x38` 的质量4改成6；原 source 和 common 质量4保持不变。其他输入仍把**原指针**传给原匹配器。

两组目标的实际记录如下，数值是客体地址，不是实机地址：

| 观察点 | SP／参数地址 |
| --- | --- |
| 原调用指令进入包装函数 | SP `0x10007ac0`，原参数 `0x10007de8` |
| 包装函数调用原匹配器 | SP与临时参数均为 `0x10007a10` |
| 原匹配器正文读取临时参数 | 读取时SP位于该参数以下，包装函数帧仍在 |
| 返回原 `+0x21ed1c` | W0=386，SP恢复 `0x10007ac0` |

包装函数的临时参数位于176字节的编译器栈帧内，152字节范围完整落在活动帧内。原匹配器正文的读取轨迹、原返回和包装函数尾声均由真实客体指令产生。这个局部结果符合常规 AArch64 子程序调用／返回与栈管理模型；具体参数和SP关系以本轮原指令实测为证，不把通用约定当作 Sony 实机ABI认证。[Arm AAPCS64 原文](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst)

**返回后栈字节仍在，不代表该地址还能被后续使用。** 原诊断代码、其他调用者或线程是否保留了指针，尚未证明；本轮不能宣称全局无逃逸、可安全回收代码或全局空闲。原 Open 的外层调用栈仍未退出。

## 通过结果与限制

5组输入共25段有界执行，包括原装载／构造和包装函数参与的路径：

| 输入 | 包装函数行为 | 原匹配结果 |
| --- | --- | --- |
| 目标FH，尾旧值A5 | 传栈内临时视图 | 386 |
| 目标FH，尾旧值C3 | 传栈内临时视图 | 386 |
| stage54既有人工FF对照 | 传原指针 | 386 |
| 代理FH对照 | 传原指针 | −1 |
| 原UHD对照 | 传原指针 | 431 |

人工FF对照只是匹配输入，不能认定它对应上层合法16M模式。目标视图仍只改变第 `0x38` 字节，未解释的尾字保留；原描述／缓存不变。非目标对照没有被套用到MAIN主录或当作有效成片。

首个匹配诊断仍在原 `+0x27d528` 前停止。后半段在**另一客体**复制上述实际产生的栈、arena和寄存器，只把W20设为原 `+0x225f94` 的常量3，从原 `+0x225fa0` 独立进入。X19保留原包装函数实际传入的临时指针，不像stage57那样由宿主选择新缓冲区。该独立正文原样返回，经编译器尾声回到原调用者，接着又在原诊断前停止。未执行的诊断／名称函数是否完全中性仍未证明，不能把两段称为不间断完整执行。

编译产物是228字节文本、136字节只读数据的 freestanding AArch64 `ET_REL`，只有一个包装函数，4项重定位，唯一未定义符号按白名单绑定原匹配器。新代码所有写入限制为客体栈；观察hook只读或停止，不设置结果、指针、寄存器返回值或PC。

首次运行把实验单指令改动放在原装载检查前，被原映像完整性断言拦下。已把改动移到原检查成功之后；**没有放宽或删除原检查**，C包装函数与原映像都没因此修改。失败源和目标文件保留在 `run-20261026/`，正式结果在 `run-post-loader-patch-20261026/`。

## 接下来要补什么

本轮只推进资源匹配调用位置和局部临时参数寿命；stage57的私有16M写者尚未作为真实后选择钩子接入。本轮没有重新声称硬件码率已改变，也没有以调用栈复原代替拍摄模式复原。

后续需要核对原匹配诊断传递的数据、实际 owner 的外层同步和设置更新顺序，再把匹配后的原行选择／通道准备与私有预置应用接合。当前所有模型地址都必须与同机程序指纹、实际装载器和内存布局核对后，才能形成上机方案。仍需完成同机健康备份、受限恢复／原字节回读、WBI／冷启动与独立救援，以及真正HD29.97 HEVC42010约16M主录、音频／时间戳／长录／温度／既有模式回归。

本轮没有重连UU或操作Windows，相机授权仍仅Windows缓存PnP。最后已确认UU断连／主机离线；后续UI只允许虚拟屏1及UU文件传输，不切用户实体屏幕、不发全局Alt+Tab。没有相机接口、认证、模式、驱动、机身文件、模块、WBI或刷写操作。
