# FX3 模型更新与 profile 生命周期边界

本阶段执行固定官方7.02原件的局部函数，使用合成模型、变更上下文和模式输入。没有运行相机、模式切换、保存、监听器或恢复；完整目标仍未完成。

## 新证据

### 两个 getter 是可写模型值槽位，不是已证明的可选列表

HS帧率 getter `0x2934d14` 与配对 getter `0x2934d28` 返回相邻4字节槽位。实际帧率修改分发器把这两个指针和内部key `0x39c` 交给通用更新函数 `0x1e49a38`。该函数先经过变更记录分发，再把同一32位值写入两槽位，并设置包装对象的 changed 标志。

内部注册表再次将 `0x39c` 绑定到 `setting_movie_rec_frame_rate_xavc_hs_4k`；它与格式、三个质量组使用同一4字节变更记录处理器。这里没有证实菜单可选范围或持久化地址，配对槽位也不能据此叫作相机备份。

8个合成值的局部更新测试通过：0、1、2、3、7、8、9及0xffffffff。测试上下文显式选择原处理器的“不再记录”分支，未模拟真实线程/日志/通知或保存。正常记录分支另作负例，在未建模线程上下文入口停止，未给它补 adapter。因此这些结果只证明局部复制行为，不能推成生产上下文对任意枚举都可接受。

一个独立同值测试使用旧值=新值=2；原变更记录处理器直接返回，但后续仍写两槽位并设置 changed=1。**同值写不等于只读操作**；本阶段只在客体 scratch 内演示，未对机身设置写回任何值。

注册表另确认内部 `0x7a7` 为 `setting_ntsc_pal_selector`、`0x12ca` 为 `frame_rate_4k_120fps_100fps_availability`。这些名称提供后续组合约束入口，不是已证明的可选值列表，也不是SDK/PTP属性或备份地址。

### 新 profile 的生命周期没有因原对照通过而自动成立

以同一批其它合成参数，分别给 builder 和 query 提供原合法 HS frame0及实验 frame2，比较17个模式值：

| 模式值 | 本阶段观察 |
|---|---|
| 5、6、7、8、9、15 | 普通 movie 实验参数返回；builder与query均为目标组合 |
| 0、1、2、3、4 | frame0基线返回；保留frame2时 builder与query进入原错误路径 |
| 10、11、12、13、14、16 | 其它模式依赖/合成fixture未闭合，不能判定实际行为 |

它们是分别构造的输入上下文，**不是相机真实切换顺序或保存后重启测试**。本阶段不擅自给每个数值补完整模式名称。代码级对照证明当前 ordinary-only 入口不足以覆盖所有生命周期；没有发生相机故障或诱发变砖。

部署前仍须选择并验证一种一致策略，例如退出普通movie前恢复合法状态，或将profile作为独立状态解释。不能未经调用者、菜单及持久化证据，就强行采用其中一种。一个可继续验证的方向是让实验激活状态独立于原合法设置，以便先检查不改变原设置的生命周期；这不替代最终菜单、保存、冷启动及恢复要求。
