# FX3 WBI恢复范围、内核恢复入口与eMMC交接区

2026-10-29。**当前7.02官方WBI的1399个段已按Sony参考格式重新校验；头部恢复入口与同包Linux内核的64字节原码完全匹配。段表没有直接覆盖当前NOR装载器配置的地址，本轮没有从WBI取得独立AP加载器或同机boot0备份。** 这收敛了“是否能直接从快照取到早期救援代码”这一候选，但不以局部搜索宣告所有隐藏/变化副本均不存在。

阶段9已经解析过这1399段，本轮复核并扩展其物理范围、元数据、尾部和内核来源证据，不把旧段表说成新发现。没有执行Sony代码、脚本、模块或guest，也没有相机、USB、root、管理员、Windows、UU、驱动或GUI操作。持续目标、16项要求及全部授权不变；`goal_complete=false`、`persistent_write_release=false`。

## 格式与完整范围

既存 `nflasha5.img` 为209112512字节，SHA256 `ac7373c58a75b7685cc2fc8e920440ec37534d15c11f447ecdea546e255fb9b1`。Sony[FX3 Ver7.00 GPL页面](https://oss.sony.net/Products/Linux/B2B/ILME-FX3_Ver700.html)所给参考源码中的 `warmboot.h` 定义88字节头、64字节段记录；`warm.c` 和 `wbi_raw.c` 定义元数据XOR及非压缩序列。本轮在7.02原件上验证其布局兼容，未声称取得7.02精确构建源码。

| 本轮核对项 | 原件结果 |
| --- | --- |
| 标志与扇区 | `WBI2`，flag=0，sector_size=512 |
| 段数／元数据XOR | 1399／1399全部匹配 |
| 实存／展开数据长度 | 208760832／237330432字节，分别与各段求和一致 |
| 零填充记录 | 82段；没有实存数据，由长度和标志描述 |
| 段表范围 | `[0x0C717200, 0x0C72CFC0)` |
| 目标物理地址边界 | `[0x400001000, 0x420000000)`；排序后无重叠 |
| 低于4GiB的目标记录 | 0 |

原表顺序并非全局物理递增：第1378段之后回到第1379段的较低地址。原序保留，范围查询另行排序，不能因这一点错误拒绝原镜像。地址基准 `0x400000000` 是16GiB地址值；以上覆盖范围也不能推断机身总RAM容量。

头部flag没有设置 `WBI_CKSUM`；段数据cksum停在初值。**元数据XOR匹配不等于段数据经过原生校验，更不等于安全启动或可刷写验证。** 本轮另外以完整来源SHA和各段SHA固定所分析的字节。[完整审计](WBI-layout-audit.json)、[解析程序](audit_wbi_layout.py)。

## 恢复入口是官方Linux内核中的代码

头部 `resume_vector=0x4004A67F0`，落在第3段实存范围，对应WBI文件偏移 `0x43B9F0`。按该段物理起点 `0x400080000` 与ARM64 Image头的text_offset `0x80000` 对照，同包 `vmlinux.bin` 文件偏移为 `0x4267F0`；64字节逐字节相同。

第3段起始64字节也与内核Image头一致，包括 `ARMd` 标识。这比只从地址猜测内核位置多一项独立字节核对。不过，比较的5963776字节整块中仍有673字节不同，原因未确定；不能把运行快照片段和原内核文件整块互换，也不从64字节一致推断全部版本/运行状态一致。[对应关系](kernel-image-correspondence.json)、[恢复入口原字节](resume-source-slice.json)。

这确认的是**官方保存状态所声明的内核恢复位置**，未观察你的相机从该入口运行，也没有证明它能进入p1、恢复坏文件或处理主系统无法启动的状态。

## 未从该范围取得早期装载器

所有声明恢复段都位于上述RAM地址范围，没有记录直接覆盖当前NOR文件配置的 `0xFE049000` 起始范围。这个地址查询只依据现有源布局，不把NOR文件默认等同于已经验证的AP启动区。

对整份WBI还检查了已保存的当前NOR／SPI装载器完整字节序列，以及共35个128字节固定位置样本，均未匹配。这个结果只排除所查的相同序列；不同版本、重定位、变化副本或其他未识别启动代码仍不能据此排除。[查询与样本结果](WBI-layout-audit.json)。因此本轮没有取得可用于适配独立恢复入口的AP boot0原件。

## 后面的eMMC区域是交接数据线索

原段表后追加的第1379段位于物理 `0x403E00000`，虚拟别名 `0xFFFFFFC003E00000`，实存139264字节。当前p3 initrd启动脚本恰以此值传入 `emmc.ko` 的 `tbl` 参数。

重新提取的原模块中，`tbl` 参数通过 `param_ops_ulong` 对应 `.bss+0x528`；初始化函数从重定位给出的 `.bss+0x1B8` 加 `0x370` 读取同一位置，并检查传入数据的字段，随后向eMMC初始化/CID/CSD设置路径提供参数。四份原模块切片及参数重定位已绑定到这项关系。

**这是交接地址和消费者的匹配，不是完整启动区或分区表恢复。** 本轮没有解释完整交接结构、导出CID/CSD内容、认定p1容量或读取当前机身。[交接区证据](emmc-handoff-proof.json)、[当前脚本原件](originals/p3-initrd/sbin/initrc/insmod_drv1)。

## 段表之后的尾部仍完整保留

段表之后还有261632字节，其中2298字节非零，包含 `RBUF`／`SUBS` 标识和日志样式内容。它们不属于头部声明的1399个恢复段。本轮没有完成整个尾部协议解释，不能将它全部称为零填充、自动裁掉，或认定它已提供另一份加载器。[尾部定位](tail-nonzero-blocks.json)。所有原件保留，未生成修改WBI或设备写入方案。
