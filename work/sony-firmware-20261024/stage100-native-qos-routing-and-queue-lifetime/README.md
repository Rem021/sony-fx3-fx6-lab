# FX3：原码率命令分派、状态选择与请求寿命

**新增证据是原状态机能够按自己的ROM表选择码率命令的排队或转发动作，以及一层队列只保留请求指针。仍未找到会自然产生目标16Mbps请求的实际MAIN策略，也没有主录或救砖验收。** 本阶段没有修改官方文件、客体C原型或相机；仅使用Mac上的官方av-cam样本进行有界离线执行。

下文地址和字段偏移为十六进制；状态数字及统计计数为十进制。

## 状态选择由原代码完成

原`17effc→17f018`按状态读取`36c8e8`的24字节表行，分别调用原后继状态函数、条件和动作，没有由宿主指定动作指针或填造它的返回值。两种旧值背景A5/C3下，观察到：

| 明确声明的数字状态/条件 | 原执行结果与停止范围 |
| --- | --- |
| 状态1，未在处理事件 | ROM选择`185044→17df28`排队动作；停在原日志入口，未执行该整段动作 |
| 状态3、8、18，未在处理事件 | ROM分别选择`185084/18510c/18522c→17b7a4`，经原构造函数安装的虚表进入`189ce8`；停在原日志入口 |
| 状态0，未在处理事件 | 原后继函数返回22；在`184c34`处理函数之前停止，未运行诊断/后续处理 |
| 状态21或22 | 原事件包装器完整返回0；状态21变为22，状态22保持22；这不是编码成功或失败码 |
| 状态3，已在处理事件、嵌套事件标志0 | 原代码准备复制0x4c字节，在`27da84`复制提供者之前停止，没有补复制结果 |
| 状态3，已在处理事件、嵌套事件标志1 | 停在`1849a0`重复事件处理函数之前 |

这些数字未映射为实机“录制中/待机”等名称。back对象的状态、活动标志、所属对象与目标绑定都是明确fixture；完整原工厂、构造、正常状态转移、当前MAIN选择和同步未验证。已进入的动作会留下真实的中间标志和栈帧，不能把暂停点当作动作返回。

原`a6eb0`时序对象构造函数和内部`1a2554`完整返回，安装`370c10`虚表，其`+18`确实指向`189ce8`。原`17792c`把明确的时序对象参数存入状态上下文`+20`。本阶段未宣称这个人为提供的绑定就是相机当前MAIN，也未启用构造后仍为空的内部策略指针`+278`。

## 下层转发没有证明参数已应用

在独立的较低栈上，原`14555c→14670c→1345e4→135f28/135fd4`把0x48请求复制到CID0x2103/MID0x010a、总长0x54的封套，通道2来自明确配置输入，在消息对象构造之前停止。原状态动作暂停栈逐字节保持，未跳过它的日志、伪造返回或继续其调用者。

16M、20M、目标0，以及目标更新标志关闭的对照都按原样进入封套。这只说明这段转发不是最终码率验证；实际策略、数值合法性、资源质量、编码器应用和错误处理仍在未验证范围。打开请求`+28`标志时会先到`148a20`，本阶段停在该更新helper之前，未强行绕过。

## 指针队列与仍在运行的请求

在明确的日志间隙后，原`17dfc4`检查状态上下文`+448`，空队列时把请求指针写到`+458`；原`17b4d8`出队后把计数清为0，旧指针槽仍保留。已有队列项的对照在原忙碌日志入口前停止，队列字节不变。

同一客体中的顺序对照是：先把16M请求入队，再由宿主明确把该请求原地址的目标改为20M；原出队代码仍取出相同指针，并沿原状态3的ROM动作进入时序码率入口。此时队列计数已经为0，但原处理调用栈仍暂停在日志入口，请求内容仍为20M。没有把出队指针手动填给动作，也没有在中间补原函数返回。

这是隔离指针与副本寿命的试验，未证明相机允许这种改动顺序、存在竞态或内存缺陷。它给后续方案增加了具体核对项：**该层入队不等于建立独立参数副本，出队不等于编码应用完成，也不等于所有模块代码已退出。** 另一条嵌套事件路径准备复制0x4c字节，不能把本层指针结论推广到所有队列；它的复制提供者和后续完成同样未执行。

## 接口相同偏移不能混接

静态追索还核对了原构造参数：`a624c→139894`的第三个指针参数是父对象`+116988`的包装器，存入接收对象`+338`；不是`a61f4→a6eb0`构造的父对象`+115a10`时序对象。因此`13a464`读取`+338`再调用虚表`+18`，不能直接认作时序`189ce8`调用。相同的虚表偏移属于不同接口，需沿原指针绑定逐层识别。

`topology-and-ROM-audit.json`记录实际指针、构造/调用片段及23行静态表。动态验证仅覆盖上表所列状态和条件；未将静态表或人为对象拼接算作正常MAIN请求生产者。
