# FX3 帧槽归还、队列与几何标签来源

2026-10-25（本地日期）。仅离线执行官方映像中的原指令，未连接相机。

**已证实：队列清空和帧槽归还是不同条件，单看其中一项不能判定可以恢复数据。** 本轮还接通原事件标签读取及调用者的有效标志写入，把 1920×1080 几何从明确声明的标签输入复制到原分配器借出的帧记录；真实标签生产、MAIN 绑定和硬件编码仍未验证。

## 帧槽与待处理队列分别观察

原控制器 `+0x947a8` 是待处理索引队列的数量，应收紧上一轮“使用计数”的暂称；它不是活动帧槽数量。另有每槽三个字节，位于 `controller+0x8ade0+3×index`，本轮按结构称为 `[active, marker1, marker2]`，不把 marker 当成硬件完成证明。

| 原代码对照 | 队列项数 | 活动帧槽 | 实际结果 |
|---|---:|---:|---|
| 原分配器连续借出 40 槽 | 40 | 40 | 分别返回 0–39，逐槽清空记录 |
| 对这 40 项完成原出队，未走可选通知 | 0 | 40 | 每槽标志为 `1,1,0`；再借仍返回 `-1/空指针` |
| 另一客体中借出 40 槽，再逐槽运行原双 marker 包装器 | 40 | 0 | 全部标志为零；再借仍因队列满返回 `-1/空指针` |

这些对照使用原 `0x15ed14` 建立的 map 和原 `0x15f8c0` 分配器，map 节点存储及对象链接是声明输入。没有执行整个控制器构造或真实线程。

原出队 `0x161590` 先取队头索引，并调用 `0x162d7c`，该 helper 返回后才减少队列计数、推进读游标。原 marker helper `0x15fa50/0x15fb64` 分别设置两个 marker；两项齐备时进入 `0x162c88` 清除三个标志，但不减少队列数量，也不擦除记录内容。

已验证原双 marker 包装器 `0x15fa10` 对 `0xffffffff` 直接返回 1 且不修改池；未知索引 40 和空队列出队均停在原诊断入口，未冒充完整错误处理返回。因此返回 1 也不能单独当作一次实际归还。

## 复用、旧内容与代次边界

在队列已空、40 槽仍活动的对照中，为槽 0 放入明确的旧几何值，再运行原 marker2：槽 0 的三个标志被清零，旧内容保持。随后原分配器重新借到 0，并自行清空全部 3352 字节记录，旧几何归零。清标志与清内容是两件事。

本轮还故意在重新借到 0 后，再调用一次相同槽号的 marker2。原低层 helper 接收的是索引，标志变为 `1,0,1`；随后原出队设置 marker1 并清除该槽标志。这只是受控调用顺序说明低层索引不能自行表达代次，**没有证明 Sony 实际会发送迟到回调或存在实机 ABA 缺陷**。上层锁、对象寿命、取消规则和当前配置代次仍未绑定。

恢复观察必须同时绑定当前对象、槽和代次，证明相关生产者、回调和线程已退出。不能保存一个旧槽号后，仅看清零结果就复原其内容。

## 出队中的可选通知仍是运行时边界

原 helper 读取记录 `+0x63c` 的 32 位值和 `+0x630` 字节。声明值为 7 且该字节为 1 时，原出队进入 `0x27c1a8` 通知调用；本轮在该入口前停止，队列仍为 1、标志仍为 `1,0,0`，未注入通知成功返回，也未把 `+0x63c` 改成 `0xffffffff`。

只把该字节改为 0 的对照跳过通知，原出队完成，队列变为 0、标志为 `1,1,0`。这说明补完整出队时还需真实通知实现及同步语义，不能用无通知路径代替所有情况。

## 几何字段的原输入来源

原输入动作 `0x147544` 经 `0x134810 → 0x14fe08` 借用同一帧槽池，稍后调用填充 helper `0x1479d8`，再通过逐帧 API 发送该槽号。静态调用链已经定位，完整动作尚未执行。

填充 helper 中的 `0x147a2c..0x147a40` 调用原 `0x0a3f3c`，把事件内一个标签的 48 字节内容放入 `record+8`，并把读取是否成功写入 `record+0`。本轮实际执行了这段调用者、原标签构造、原序列化查找、原复制及有效标志写入：

- 明确声明的标签输入在对应位置放入格式字节 5、1920×1080；原代码将它们送到 `record+0x36/+0x3e/+0x40`，有效标志为 1，全部 48 字节一致。
- 换成不同标签键，或不给标签根，原代码返回未找到，刚借出的记录前段保持零、有效标志为 0。

标签容器、根标识、条目、内容均是受控 RAM 输入；条目标识常量取自官方原件。该正例不是相机真实标签、传感器输出或实际 MAIN 格式。原 `0x1479d8` 的其余字段、上游标签生产者、真实帧率/格式身份及完整消息传递仍待接通。
