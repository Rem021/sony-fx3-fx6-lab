## 新确认的实际加载差异

[静态核对结果](native-loader-audit.json)直接重读官方7.02保存的 im ELF 和 libIMDB，绑定13处原始分支指令、6段连续原指令及225条既存IMDB记录，没有执行原固件。

原 im 的 `THREAD_APP` 将 `0x4030a8`、三组 `THREAD_INFRA` 将 `0x402f94` 写入属性，再经 `0x403bc0` 调用 `osal_create_waitable_thread`。两个回调进入 `0x4064fc`，该处分选72字节IMDB记录；选定分支经 `0x406374 → 0x4061ec`，按记录类型进入既有库加载器。保存的225条记录中未见新候选的路径或两个导出名。

这证明已观察到的常规应用／基础设施初始化路线是**线程回调注册**，不能证明候选要求的主线程上下文。第227轮的零参数 `step/status` 解决了自己的参数合同，并没有让它成为已注册的原厂入口，也没有实现重复调度和主机回传。不能通过删除主线程检查、改IMDB、写全局preload或忽略返回值来宣称已经适配。

以上为条件分支和保存文件的静态证据；未观察线程实际创建成功/TID，不穷尽其它主线程、间接、服务或替代加载路线。因此后续应调查**可达的具体加载入口及其真实上下文**，再决定程序架构，不能继续仅给既有候选增加包装层。
