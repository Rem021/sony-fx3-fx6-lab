# FX3：共享 movie 事件与介质录制启动链

**普通电影录制与推流都发送相同输入的 `EID_MOVIE_REC`。普通录制另有可定位到原 MPR 库的 `PrepareRecStart → RecStart` 介质录制流程；共享 movie 事件不能证明两者复用同一编码器。** 本轮补上了介质启动请求的原生成方式及 MPR 参数检查入口，尚未补上目标 MAIN 编码配置。

2026-10-27，仅 Mac 离线。地址与偏移为十六进制，数量及表内参数为十进制。原固件未修改，没有操作 Windows、UU 或相机。

## 从函数名转到实际调用

原应用的两个函数分别是：

- `2da8c48`：`sequence_start_movie_recording::async_infra_wrapper_imaging_set_key_clear_and_movie_rec_start()`。
- `2db0ea4`：`sequence_start_streaming_output::cam_start_movie_rec()`。

两个函数的原代码都先以输入单字 0 调用 `2dd89d4`，再以输入单字 0 调用 `2dd4ad4`。在整个原应用 `.text` 对直接 B/BL 的扫描中，后一包装器只有这两个直接调用点。间接调用不在扫描范围内。

本轮执行各自原序言，再以两个独立的日志后入口核对其调用参数，未跳过日志返回继续整条流程。原 `2dd4ad4` 静态指向 `2e3f628`；该原函数生成 24 字节事件参数，事件 ID 为 `3001`。离线执行停在 trace 身份取得函数之前，未发送请求、取得回复或完成事件。

这些证据不把事件定性为“仅采集、绝不录制”：事件的完整接收端尚未核对。它们足以说明，不能仅凭 `cam_start_movie_rec` 的文字把推流编码器当作卡内 MAIN 编码器。

## 普通录制的另一条实际路径

原 `sequence_start_movie_recording::run()` 调用 `start_recording_movie()`，候选入口分别为 `2daaa08`、`2da961c`；原名称地址、调用指令和分支片段均记录在来源审计中。

`start_recording_movie()` 中可定位到两个独立的 MPR 请求：

| 应用调用点 | 应用包装器 / 原构包体 | 原动态链接符号及库内定义 |
| --- | --- | --- |
| `2da9b90` | `2ddaf54 → 2e5c5e8` | `mpr::PrepareRecStart`，`libmpr.so+ce8e4` |
| `2da9e14` | `2ddaf94 → 2e76854` | `mpr::RecStart`，`libmpr.so+dc504` |

调用者把对象 `+1c0/+230` 的字传入介质参数，把 `+320/+324` 的字传入选择分支；RecStart 另传 `+31c` 和一个 64 位值。上述对象字段的真实当前值、配置代次和完整业务语义未绑定。源程序的原诊断字符串明确称输出字段为 `numOfRecStartMedia` 和 `mediaId[0/1]`；本轮使用的两个 ID 是显式输入样本，不是实机介质 ID。

原构包体在声明输入下生成下表结果。每项均以 A5/C3 两种旧内容背景执行：

| 选择输入两个字 | 原生成介质数量 | 原生成介质 ID |
| --- | --- | --- |
| 0、0 | 2 | 两个输入 ID |
| 0、1 | 1 | 第一个输入 ID，第二槽为 `ffffffff` |
| 1、0 | 1 | 第二个输入 ID，第二槽为 `ffffffff` |
| 1、1 | 0 | 两槽为 0 |

PrepareRecStart 生成完整 28 字节局部参数，首字 `6c`，在调用原 MPR 导入入口之前停止。其回复区没有被写入，不能声称 Prepare 成功。

RecStart 生成完整 56 字节局部参数，首字 6。在本轮已执行的局部请求中，介质数量、ID、一个原映射参数和 64 位输入均可复核。输入索引 0/1/2/3 分别产生 `+1c` 字值 0/90/180/270；其单位和完整用途未绑定，不能称为帧率或码率。

RecStart 的原序言先执行至首个日志；之后从 `2e76910` **独立进入**构包正文。中间事件对象、锁、520 字节初始化和状态处理没有执行，`X27` 的静态页地址明确作为输入。因此这里的完整局部参数不等于完整有效运行时请求、整个包装器成功或原生连续执行。输出停在原诊断函数之前，未调用 `mpr::RecStart`。

## 接收侧的实际来源

原 MPR `RecStart` 内部调用 PLT `80eb0`，其符号与本库定义绑定到 `SetRecStartInfo`（`ccbdc`）。该函数又通过 PLT `7ca10` 指向 `CheckRecStartInParam`（`cc1c4`）。另外，原 RecStart 内还存在 `EnqueueExecEncOpen`、`EnqueueExecReady`、`EnqueueExecEncStart` 等调用；本轮只做静态定位，没有把它们当作执行完成。

把应用原生成的 56 字节参数**逐字节不改**作为声明输入，分别执行 SetRecStartInfo 的原序言和独立日志后参数传递，再执行检查函数的原序言与独立日志后入口：

- 数量为 1 或 2 时，原代码读取该数量并取第一个 ID，进入原介质 ID 查找函数 `82e90` 前停止。
- 数量为 0 时，原代码进入另一诊断入口前停止；没有伪造其日志返回、错误码或验证完成。
- 两个独立函数使用不同的局部栈区域，前者暂停的保存帧保持不变。

本轮没有执行介质注册表查询、状态锁、整个参数检查、配置复制、编码器 Open/Start、封装或卡内文件写入。当前证据没有证明所选 ID 有效，没有建立实际 MAIN 实例，也没有证明这些请求接受目标 HEVC42010/16Mbps。

## 核验与下一步

正式结果为 **4 组调用者、2 组事件参数、8 组 Prepare、14 组 RecStart、6 组 MPR 入口核对，共 82 个有界阶段**。核对整个声明栈/输出范围以外未改，输入参数未改；原 ELF 客体只读，未解析导入、修补固件或提供成功返回。源码、轨迹、原始参数和中间结果保留，复核仍由同一代理完成，未新增独立引擎或实机验收。

首次运行在已读的原 trace 调用指令 `2f6ddac` 前，被宿主允许范围的尾界截住；允许区间原本没有覆盖该最后 4 字节。修正宿主范围至 `2f6ddb0` 后到达预定的未执行身份函数边界。失败源文件、回溯及修正后的 70 阶段中间结果均保留；正式 82 阶段结果另存，原代码没有改动。
