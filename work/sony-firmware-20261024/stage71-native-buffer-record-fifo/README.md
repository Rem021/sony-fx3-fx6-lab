# FX3：ROI-map 记录队列与输出转交范围（2026-10-26）

本轮只在 Mac 离线执行原函数，补清了上一轮停止入口的语义：**`+0x22da80` 是把两个原始字段放进记录队列，不能把它当作物理内存释放或指针来源验证。** 原日志将该队列命名为 `roi_map_queue`。配对的 `+0x22d9b0` 取出并复制记录。

另一段原转交代码验证了：队列变空、common 的指针清零之后，输出仍持有复制出去的指针。因此，后续停止／回退必须覆盖输出消费者，不能仅依据源指针或队列计数。这里没有执行完整目标请求、硬件编码或恢复。

## 原记录队列

原管理对象构造使该队列的计数、读写索引归零。接着使用原 enqueue／dequeue，在两组明确的数值输入上完成容量8、满队列拒绝、空队列拒绝、先出3项／再入3项后的回绕、完整FIFO顺序检查。共2例、56段有界执行。

输入的高位A5／C3数值没有对应真实分配的相机缓冲区，也没有在客体中映射其所指区域。原函数仍把两个64位数值入队／复制出队，不读取这些数值所指的内存。返回0只证明这次记录操作走完，不能证明缓冲区有效或底层内存已释放。满／空拒绝时队列保持不变，空取出也不改之前的输出；逻辑空队列仍保留旧槽位字节，不代表这些旧字节仍是活动记录。

两个原函数通过真实原 logger 的已声明静音分支返回，未伪造诊断返回。初次检查误把队列诊断按 matcher 参数格式解码，失败及源副本保留；正式版本仅改为原始实参观察器，原 Sony 指令和 logger 执行未改变。

原文分别为 `roi_map_queue empty`、`roi_map_queue full`；另一处为 `fail to alloc ROI MAP dmm area`。这些名称与原字符串字节核对，不将这个特定队列混同于整个主码流的缓冲区或物理分配器。
