# FX3 父端C监管核心与双端ARM64联测

2026-10-30；经典ILME-FX3 7.02；Mac离线开发，自写ARM64程序与假Linux内核。无相机操作。

**父端C核心现已和第221轮子端协议完整连接，15项检查、38组场景通过。** 固定会话占用、GRANT／READY／GO／DONE、子进程退出观察和RAM输出复读都由父端机器码执行；两份ARM64镜像通过明确的假内核队列交互，不再由Python直接预置GO。本轮仍未实现实际fork／exec、机内加载或调用路径，不能充真机全局排他、备份或刷入验收。

## 正常结束后，原存活会话才能继续

[parent_module.c](parent_module.c)提供显式submit／poll入口，构造函数只写内存标记。候选按root／主线程和参考im完整文件SHA过滤调用上下文；实际im身份未观察。父端既有socketpair的SO_PEERCRED关联创建者，逐消息SCM_CREDENTIALS关联指定子进程；两者不能混为一项PID证明。

父端在固定RAM根下独占创建`/tmp_wbshd/fx3-boot-owner-session-v1`，0700目录与0600的`owner-session.pending`均保留。不读取记录来推断完成，不删除、超时回收或在PID消失后接替；部分写入、同步失败和旧目录都使新实例拒绝GRANT。记录只覆盖该RAM生命周期，未证明跨断电或重启保留。

同一个存活C上下文在私有内存中维护IDLE／RUNNING／HELD。提交时复制整个handoff和请求，再核对关联、参考父身份、固定目录及子进程关系；只有内核wait4非阻塞观察仍为有效在途子进程时才发送GRANT。收到正确READY才发送GO，之后必须同时满足以下条件才回到IDLE：

- 逐消息凭据、完整320字节DONE和256字节handoff均匹配，返回码为0，没有重复或额外消息。
- wait4返回指定子进程，退出状态严格为正常0；PID不存在、公开JSON或完成消息单独到达均不足。
- [output_validate.inc](output_validate.inc)复读128字节请求、256字节清单及全部块，核对请求／窗口／范围／容量／配置、块和整窗口CRC、长度／EOF及前后元数据；文件与目录关闭均成功。
- 整个检查仍在期限内，原会话目录身份没有改变，控制通道关闭成功。

poll使用非阻塞等待参数；它们不是实际内核调用绝不阻塞的保证。异常进入HELD后仍观察原子进程及通道，但不会再发GO、自动重新提交或凭迟到退出解除占用。重复调用构造函数也不会清空已有会话。正常多窗口采集保留，未缩成永久只允许第一个窗口。

## 复现并修复了一处错误释放

最初12项通过的父端只看私有DONE与退出码，缺少第220轮已有的输出校验条件。[原反例](output-validation-gap/receipt/gap.json)证实：在DONE后改坏一块数据，初版仍返回IDLE，而Python独立解码器拒绝CRC。

用[同一个探针](probe_output_validation.py)对两份固定自写二进制再次比较，子端返回和退出码都为0、同样改坏输出：

| 父端 | 模型中的结果 |
|---|---|
| 初版，SHA开头`eda3c4bb` | [错误释放到IDLE](probe-old/receipt/probe.json) |
| 当前，SHA开头`5a9ab04e` | [保留HELD／UNKNOWN](probe-new/receipt/probe.json) |

因此当前版本把输出复读作为释放条件，保留原要求。两个探针都不是刷入或救砖通过项，初版源码、二进制及反例未覆盖。

## 最终验证与构建

[最终15项检查](runs-final/receipt/results.json)覆盖38组场景、34个父端实例；27个子端进入显式调用，另11个只初始化且未获得GRANT。所有自建工作线程已正常结束或经明确的自建阻塞门协作释放，没有强杀、设备复位或重启读操作。

- 同一存活父端能顺序采集不同任务，也能完成boot1四窗口：128／128／128／126块，组装33,423,360字节合成源，SHA为`0bf7d4c932dc8a583aa5101bad7c8e7a8d6191c15c54479847c83b62434cc625`。
- 原读取阻塞时，同父端的新提交不产生许可；另一父端实例也不能取得同一固定目录。两个父端同时争抢时，只有一个发送GRANT。
- DONE后子进程仍在途、退出0却无DONE、重复DONE、非0退出、子／父通道关闭错误、错误凭据及额外描述符都不释放异常占用。
- 255字节部分记录、同步失败、ECHILD和等待错误实际到达各自故障分支；新实例不能接替失败或已成功结束的原所有者。不同参考父PID／子PID的正常路径也通过。
- 正常DONE和退出0之后，损坏块体、错误块索引、清单／请求绑定改变、输出身份变化、关闭错误或期限超出均保留HELD。

父端262,936字节，SHA为`5a9ab04e92e06dd5fbddbff0c95e1736ac4c0850a8ad9a346a01669104e0eb39`，236处代码链接处理（18处32位负载／存储重定位）及1处初始化相对重定位。[构建回执](runs-final/built/build.json)；第221轮子端二进制保持SHA `23327fd5c43ecf44858f0705edc30db1ed795d1bc2272bf75bbeaf1ae8e8b3a3`。

父端出现了原受限链接器不支持的285重定位。本轮只在本地dynparent构建器增加32位整数无符号偏移负载／存储处理，检查指令、4字节对齐与回算；没有修改正式elflink源码。[Arm ELF规范](https://github.com/ARM-software/abi-aa/blob/main/aaelf64/aaelf64.rst)与保存的原文支持该位域解释；正／负链接检查及两个ARM64端的实际模型执行均通过。[Linux等待手册](https://man7.org/linux/man-pages/man2/waitpid.2.html)和Linux4.9 wait.h／unistd参考用于核对WNOHANG与260号wait4。[ABI记录](kernel-and-link-ABI-review.json)

首轮夹具仍把父端self/exe长度写成子端423,000字节，导致正确的40,920字节im过滤拒绝；当时两个表面通过的检查也未到达目标故障分支，不算安全证据。校正夹具并加强到达条件后12项通过，随后复现并修复输出释放缺口，当前最终15项通过。各轮记录及对应源码快照保留，不混算旧测试。

## 尚未证明的部分

父端和子端确实执行了我们自己的ARM64机器码，但Linux进程关系、wait4、socket、凭据、root／tmpfs属性和共同单调时钟全是模型输入。实际独占创建、文件读写与CRC输入是Mac普通用户的本地夹具文件。没有运行Sony代码、Linux内核、实际装载器或真实相机程序；原厂文件只作数据哈希。模型中的同一路径串行不证明真实机内所有调用已经受控，具备特权的其它代码仍可能绕开尚未部署的父端。

submit接受未来启动器提供的子PID与199号父通道，但本轮并未创建真实相机子进程、准备继承描述符、加载模块或显式分派子端入口。父im扩展方案与独立keeper方案也不能直接互换：后者需要同时改父身份合同。下一步是把受控启动／继承通道／显式调用和退出观察接成同一条可核对链，继续先离线验证。

参考im身份、受保护root固定域、完整加载代码与用户批准不能由文件SHA或凭据推断。启动区实际数据视图、硬件访问归还、同机完整备份、独立AP救砖、逆写与冷启动均未验证；软件窗口完成不证明这些事项。全部16项要求和MAIN1080p29.97 HEVC／长录验收保持，exact30单列。195仅主机root01仍未具体批准、未启动，本轮没有USB／缓存设备查询、管理员或相机操作；0.4／0.5正式包及23源码不变。目标active，未放行持久刷写。
