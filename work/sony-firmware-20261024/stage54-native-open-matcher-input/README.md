# FX3 原 Open 队列与匹配器附加输入来源

2026-10-25（本地日期）。仅离线执行固定官方原件。

**已用原队列消费、handler 分配/登记和 common 调用链，产生匹配器实际要读的附加字段。** 对声明的 MAIN 描述符，原路径生成 `+0x88=1/ENC_MAIN、+0x8c=10`，而此前人工对照使用的 `+0x88=2` 对应 `ENC_PROXY`。改用这轮原生生成的数据后，FH 目标仍返回未匹配；人工 FF 质量对照仍命中行 386。

该结果补上了资源 Open 到 common 匹配入口的一段实际调用桥，**仍未解决 16M 的上层质量选择与查询一致性**。没有证明硬件 Open/Start、真实主录或恢复能力。

## 原调用链实际到达哪里

原 `0x22f34c` 从声明的 Open 待处理队列取出一条请求，原生复制 0x88 描述符，并补入尾部常数；随后沿下列原调用链运行：

`0x229808` Open 处理 → `0x227cdc` 分类 → `0x228e40` handler 分配、ID 分配与 map 登记 → 原 `0x21e26c` 复制/清零/分派 → `0x21ecf4` 表构建器 → 原 `0x225eb8` 匹配器入口。

运行在匹配器第一个诊断 `0x225edc → 0x27d528` 前停止。没有替换日志、锁或 HAL 返回，没有在途中重新设置 PC，也没有人工写入上述附加字段。

每例先执行完整原 common-handler 构造。Open 队列、空闲 handler 队列、可用 ID 队列及空闲 map 节点存储是声明的 RAM 输入，不是完整工厂构造或实机登记。原代码从这些队列取出 handler、生成/登记 ID 0，并把请求的 UID 输入 0x2a 写到 common 绑定字段。handler ID、请求 UID、帧槽索引和硬件通道身份分开记录，不把它们混称为当前相机 MAIN。

## 附加字段的语义与原生产者

| 字段 | 本轮原生产结果 | 来源及边界 |
|---|---|---|
| `+0x88` | MAIN/UHD 为 1，proxy 为 2 | 原 `0x227cdc` 根据描述符分类，`0x22984c` 写入；原名称表绑定 1=`ENC_MAIN`、2=`ENC_PROXY`，不是输入像素格式枚举 |
| `+0x8c` | 10 | 原队列消费 `0x22f388/0x22f3ec` 写入的高 32 位；某些已有 handler 分支还会改写它，本轮新分配状态没有经过那些分支，完整业务语义仍待绑定 |
| `+0x90` | 25 | 原队列消费和 Open 处理写入的常数；没有据此宣称它是实际录制帧率或码率 |
| `+0x94` | C3C3C3C3 | 本轮明确的旧栈内容输入，原路径未赋值；不得当作实机未初始化缺陷。已执行匹配循环不读取该字 |

读取观察确认，独立原匹配循环只读取这四个尾字中的 `+0x88/+0x8c`。这不证明其它消费者也不读 `+0x90/+0x94`，更不能任意覆盖它们。

## 使用原生尾字段的匹配对照

匹配循环前的诊断仍未执行。为保持边界清楚，另建一个客体，将原调用链已经产生的 RAM、栈和寄存器作为明确输入，从原诊断后的表循环进入；W20=3 取自原 `0x225f94` 常数。原匹配器正常返回到原调用者，调用者实际把返回值保存到 W23，并在下一次诊断前停止。

这段独立执行仍假设省略的诊断不改变相关状态，没有把它与前一段冒充一次完整连续 Open。

| 描述符 | 原路 `+0x88/+0x8c` | 原匹配结果 |
|---|---|---:|
| 目标 MAIN HD29.97 HEVC42010，FH | 1 / 10 | -1 |
| stage33 的人工 API-quality24 / FF 对照 | 1 / 10 | 行 386 |
| 匹配代理规格的 FH 对照 | 2 / 10 | -1 |
| 原 UHD59.94 QT150M 控制 | 1 / 10 | 行 431 |

FF 描述符沿用已封存的人工质量对照，**本轮没有证明设置模型会真实选择它**。其命中现在不再依赖把 MAIN 的角色设成 2；但匹配表命中仍不是硬件格式接受或可录制证明。

旧 proxy 在人工 `(2,1)` 下命中行 607 的结果保留为条件对照。它不能作为本轮原 Open 新分配路径的生产值：这轮 proxy 实际得到 `(2,10)`，结果为 -1。其它已存在 handler、代理配置及上游路径尚未覆盖。

## 不能直接把上层质量改为 FF

本轮还在原 `libmpr.so` 中核对了纯码率函数及独立质量转换片段，无日志返回适配：

| 上层 DefStruct VQuality 输入 | 原转换后的 API 质量 | 原 `GetVideoBitrate` 返回值 |
|---|---:|---:|
| 6（现 16M 候选） | 22 | 16000 |
| 8（可转向 FF 的质量） | 24 | 25000 |

这些是原 helper 的原始值，不是实际码流测量。结合已封存的资源质量转换 22→FH、24→FF，直接把上层质量从 6 换为 8 会同时改变查询/估算的输入身份。此前 FF 原编码预置的目标字段为 24,498,176；私有副本改为 16,000,000 的候选也不能自动修正所有上层查询、缓存和 mux。

下一步必须明确新模式在各层的身份，以及在哪里进行受限的资源质量/预置选择，保持 16M 查询、实际目标字段与所有消费者一致，不能只换一个常数消掉 FH 的失败。

## 队列清零仍不是退出

原 Open 队列消费后，待处理数量已经为 0，但原栈仍在 common/匹配器调用中，handler 已被分配并登记。这是同一客体中的具体观察，不是相机运行时状态。它继续支持恢复要求：队列、对象登记、在途调用和代码退出必须分别观察；这里的 Open 队列也不同于 stage52 的帧槽索引队列。

## 验证、限制与目标

正式结果共 **24 段有界原执行**：四组各五段调用链/构造/匹配执行，加四段质量/码率检查。首次停于 ID 函数许可范围遗漏的原 `ret`；核对原字节后仅补到该 `ret`，另目录完成 20 段，再增加质量对照，以另一目录正式完成 24 段。失败轨迹和两个较早版本均保留，原映像未修改。

使用原 LIRO 装载器与内核原内存函数；全部客体映像检查通过。源码/字节/轨迹/哈希复核由同一代理完成，未新增独立实现或实机重放。

目标仍是经典 FX3 7.02 的 MAIN 1080p、30000/1001 fps、HEVC42010 约 16 Mbps，精确 30.000 单列。真实上层选择、完整消息/状态/同步、完整 Start/HAL、模型/query/cache/mux、成片/音频/时间戳/同步/长录/温度、同机健康备份、受限恢复回读、WBI/冷启动及独立救援要求全部保留。

本轮没有恢复 UU/Windows 连接，没有打开相机接口、认证、切模式、变更驱动、读取素材、上传模块、WBI 或刷写。授权仍仅 Windows 缓存 PnP 盘点，没有新增变砖可恢复保证。
