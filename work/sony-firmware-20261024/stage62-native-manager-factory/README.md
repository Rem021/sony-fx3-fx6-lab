# FX3 7.02：原管理对象、factory与空闲队列进入资源提供者边界

本轮用原固件函数补上了上一轮部分环境中的对象关系：**原管理对象构造 → 原factory构造（6个MAIN、2个其它编码对象）与原setter绑定 → 原factory重置／队列初始化**均正常返回。随后原请求从这些原队列取得实际构造的对象，继续原匹配／预置／尺寸准备及管理对象缓存查询，到达下一层资源提供者入口。

目标FH的A5／C3旧值及原UHD对照，共21段有界执行通过。此前`+0x22d394`入口的管理对象为0，本轮由原setter绑定为原构造产生的对象；不再人工写入空闲ID、空闲handler或map-node队列。

仍未执行资源提供者正文、OSAL消息申请／同步发送／回复、真实单例／线程启动／锁域／当前owner、硬件Open／Start或录制。没有相机、Windows、UU或刷写操作。完整目标和16项验收保持不变。

## 本轮执行的原构造路径

使用既有固定哈希的av-cam、LIRO和内核原`memset`／`memcpy`绑定，分别在客体RAM调用：

| 原入口 | 实际完成的范围 |
| --- | --- |
| `+0x22cc8c` | 管理对象构造，25次原清零调用；缓存槽初始化 |
| `+0x226d2c` | 6个原通用对象、2个其它编码对象、容器构造；8次原`+0x22c99c`绑定 |
| `+0x2270d4` | 原重置与空闲ID／MAIN／其它槽／map-node队列初始化 |

原构造的6个通用对象起点为factory+0x40、步长0xe518，另外2个对象起点为factory+0x56080、步长0x269b0。8次setter均从原factory首指针取得同一个管理对象，且原重置后仍保持该指针。

原初始化返回后，空闲ID为8、MAIN槽6、其它槽2、MAIN map-node为6。消费一个MAIN请求后，原代码自然得到ID 0，并将相应计数变成7／5／5；map保存的是原构造的第一个handler。上述队列内容由原函数生成，测试脚本没有补写这些队列。

两种旧值下，管理对象、factory构造及重置各自执行前后都逐字节检查整个4MiB客体arena，**各自声明对象之外的数据保持不变**；三类函数均沿原返回路径回到入口SP。它证明了这组有界构造的范围与返回，不证明真实单例的生存期或机身内存分配。

## 从同一原请求继续

保留stage58的唯一客体BL重定向和编译匹配包装函数。目标原FH描述仍为FH，仅匹配临时视图使用FF，目标得到原行386；原UHD得到431。原common描述和源参数保持。

请求先从原队列到`+0x21dd54`入口暂停，再用同一寄存器／栈／内存，从这个PC继续，没有复制成另一客体或补返回。原`+0x22d394`正文与`+0x22de54`缓存查询这次实际执行；原缓存未找到所需键后，原调用者来到`+0x27bdb4`，在其第一条指令前停止。

```text
通道申请 +0x22d394：X0 = 原构造的管理对象（客体地址0x11020000）
资源提供者 +0x27bdb4：
  W0 = 0x61003c
  X1 = 原调用者栈内输出区（0x10007968）
  W2 = 0x470
  W3 = 0x11
  W4 = 0
  W5 = 0x806800f3
  LR = av-cam +0x22d3fc
```

这些地址和对象存储是模型布局，不是机身物理地址或当前进程映射。没有给资源提供者补缓冲区、物理地址、回复或“成功”返回。

## 已定位的下一层依赖

静态原代码显示，提供者`+0x27bdb4`会进入消息包装链`+0x27bec8 → +0x99004`，后者通过av-cam veneer调用OSAL消息接口。用原av-cam头指针、veneer位移及LIRO重定位逐项对应到：

| av-cam veneer | LIRO重定位偏移 | 原符号 | 已有提供者文件 |
| --- | --- | --- | --- |
| `+0x2f028` | `+0x398` | `osal_valloc_msg_wait` | osal_uipc.ko |
| `+0x2efb0` | `+0x368` | `osal_snd_sync_msg` | 同上 |
| `+0x2f03c` | `+0x3a0` | `osal_free_msg` | 同上 |
| `+0x2f0a0` | `+0x3c8` | `osal_set_msg_src` | 同上 |

原头`+0x20`所指表基址为`V+0x1a4`，LIRO复制区起点是`V+0x1ec`，因此veneer位移不能直接当作LIRO重定位偏移。四个符号在此前固定的官方`osal_uipc.ko`中都有定义；本轮只核对定义及位置，**未加载、重定位或执行该模块**。

完整原单例构造`+0x22a680`还包含锁构造及上层dispatcher构造。本轮单独执行其管理对象和factory相关函数，不能将此写成完整单例、系统启动或真实OSAL服务已运行。

后续应核对原OSAL模块的重定位、初始化和内核依赖，定位能够执行的部分与必须停止的线程／消息／硬件边界；不编造调度器、当前任务、消息回复或物理缓冲区。Unicorn维护者也明确说明其CPU仿真范围及系统调用／中断处理需要额外环境，见[官方FAQ](https://github.com/unicorn-engine/unicorn/blob/master/docs/FAQ.md)（2026-10-26读取）。本项目没有把这些额外环境悄悄填成成功。
