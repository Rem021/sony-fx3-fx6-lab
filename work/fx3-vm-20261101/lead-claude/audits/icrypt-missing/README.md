# iCrypt 提供者、调用 ABI 与后续链接风险审计

结论：**原厂提供者存在，优先恢复加载，不建议实现替代密钥桩。** stage2/extraction/files 是精选提取子集；完整 AP projection 中 `/usr/lib/libInfraCrypt.so` 导出全部 9 个缺失 API。其原件来自 nflasha15 `/lib/libInfraCrypt.so`，inode 95147，22768 B，SHA256 `d3140522c90c0d1e5d75dca06f0f18f58b628d8f8dd6b29b808aaf205cfd842b`，与 full-v5 原始分区投影清单一致。不存在“已证明该 API 必来自 TEE 未提取分区”的结论。

仅静态只读审计；没有运行 QEMU、调用密钥 API、操作设备或修改 runtime。脚本只写相邻 `icrypt-proof.json`，README 为人工结论入口，未修改项目根入口以遵守独占写入范围。

## 原厂加载与最小修正候选

原 `libIMDB.so` 表第 86 项，VA `0x1e668`，order=4，target mask `0xffffff9f`，qemu_selected=true，field12=`0x2ec`；库名 `libInfraCrypt.so`，入口 `iCrypt_init`、`iCrypt_exit`、`iCrypt_sus`、`iCrypt_res`。entry+14=0，走具名库加载。`im.elf+0x405e9c` 读取 entry+14，`0x405ea8` 在库名和 NULL 间选择，`0x405eac` 调用 dlopen；flags 从对象+0x73c 取值。AP70 其他原厂模块实际记录 flags=`0x101`（LAZY|GLOBAL）。不是 appFw 或 im 的 DT_NEEDED 必然加载该库；原机通过 IMDB 的动态模块装载实现。

已检查投影中原 `/sbin/init2`、initrc 脚本和 manifest 的配置路径：init2 第64行直接 `/usr/bin/bootin.elf &`，未发现原厂 LD_PRELOAD 或 `/etc/ld.so.preload` 配置。完整文件系统 manifest 未提供 `/etc/profile`/systemd/preload 对应文件；这是一份已提取固件范围内的否定结果，不代表所有机型与可写配置均不存在。

AP70 终止前有其他库的 `FX3_GPE_LOAD`，没有 `libInfraCrypt.so`，因此该原库在所观测时段尚未走到具名装载。**为何 stock IMDB 第86项晚于 license_get_i 尚未证明**，不能称为 dlopen flags 错误。协调者已独立确认该库在 AP70 CPIO 中；本审计证明本机投影与原厂装载契约，不替代 guest namespace readback。

最小运行候选是仅在 `runtime/ap70-lcd-osd/init-reviewed.sh` 第149行现有 preload 列表末尾追加：

```text
LD_PRELOAD=/simulation/fx3-capid-v1.so:/simulation/fx3-hdmi-registration-v1.so:/simulation/fx3-gpe-observe-v7.so:/simulation/signal-observe-v2.so:/simulation/ioctl-trace.so:/usr/lib/libInfraCrypt.so
```

由 Lead 集成，**本工人未修改/执行**。不要新建 ld.so.preload 全局配置，也不要把 preload 当成已调用 iCrypt_init。库依赖链为 `libInfraCrypt.so -> libInfraCryptCore.so -> libsecvlt.so + libInfraSKD.so + libuuid.so.1`，另有 glibc/C++/pthread/dl/m/gcc/rt；脚本完整闭包中这些依赖均可定位。原厂 crypt Manager 在未初始化状态 HasPublicKey `+0x2664..0x26e8` 与 HasPrivateKey `+0x24a0..0x2524` 会记录未初始化并返回0，因此先恢复 API 符号可见性已有原代码的降级语义。

`iCrypt_init+0x1e74` 调 Manager_init `+0x289c`；后者创建服务/worker（服务ID `0x82ee0920`）并经 `+0x1f44` 发 Core 请求，成功才设 `+0x151f8=1`。Core 包含 `/dev/spidev0.0`、`/dev/urandom` 等字符串，顶层库含 `/dev/mem`，CertificateManager 含 `/dev/nflasha12`；这些字符串不是证明初始化必需打开这些节点。**设备节点、Core线程和初始化运行要求未证实**，不能通过预置初始化成功状态跳过。CertificateManager 和 InfraSKD 都不是9个 API 的提供者；两者依赖和 dlopen 导入信息见 proof。Core 的 libsecvlt 依赖提示安全存储实现，但没有证据支持独立缺失 TEE 库的猜测。

## 九个 API 的调用 ABI 和桩边界

按 AAPCS64 的 x0–x7 参数、w0/x0 返回约定推断（[Arm 官方 AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst)，本次核对）；未发现公开 Sony 原型，下面是调用边界的 ABI 推断，不是恢复的头文件。u32 id 是 get_icrypt_id 将 license enum 映射的值；`0x2e10048..0x2e1007c` 可见 `0x20300001/2/3` 常量构造及跳转表。输出 length 槽按64位传送，因此写作u64，具体 typedef 未证实。

## 启动路径与“无密钥”分支

可静态证明 `model::sequence_boot::license_get_i()`（函数字面量0x391a590，代码块从约0x2b61f00）有两处 HasPublicKey 路径：`0x2b62140`（已选择license）和 `0x2b62640`（遍历类型1..3），经 `0x2de2484 -> 0x2e101a0 -> iCrypt_HasPublicKey`。HasPrivateKey 经 `0x2b6217c` / `0x2b62684 -> 0x2de2444 -> 0x2e1014c`。

Has返回0会被wrapper变成missing=1,status=0。类型遍历路径 `0x2b62664..6a4` 在missing=1时可再查询私钥、将缺失状态交给 `0x2b5ffe4`，`0x2b626a8..6b0` 推进类型直至4，继续到 `0x2b621a8`。选定license路径也将missing存栈后继续。**license_get_i 内未调用任何Create函数，所以无密钥检测本身不会创建密钥或因“没有”报致命错误。** 这只证明本函数局部继续，不代表菜单已经可用或以后不会由其他sequence要求密钥。

`sequence_create_key_for_digital_signature::run()`（日志原型0x3920318）是另一条用户功能路径；它会调用CreatePrivate/CreatePublic，不允许把通用失败桩说成安全。`0x2b7c864`调用创建私钥，`0x2b7c86c`非零跳`0x2b7ce5c`，后者有 `SEQUENCE FATAL ERROR assert` 字面量及 `0x2b7cf38 -> 0x2ebf3b0`。替代方案为原库加载；如必须降级，只限启动检测Has返回无，禁用/明确不进入创建sequence，不能伪造创建成功。

AP70 serial.log 第20535行是链接器错误，紧邻前一条内核时间585.798531，距LCD越过约10秒；错误行没有TID和调用栈。静态启动最匹配 license_get_i，但**本次确切Has调用点、线程ID与sequence调度时刻未通过动态栈证实**；不能仅凭SeqQueueDispSwi越过就说错误由该线程发起。

## 全量链接风险

比较单位为 ELF `.dynsym` 可见 GLOBAL/WEAK 定义和未定义导入；基于 full-v5 manifest 的每个原始 regular payload、stage2精选文件、AP投影和原成员，包含 SONAME 归一与递归DT_NEEDED。不是只grep字符串。完整逐导入者记录、未绑定weak、observed命名空间与原厂IMDB保守超集分开保存，详见下面自动计数与清单。

“提供者在固件中存在”与“在当前动态命名空间可见”独立：iCrypt本次属于后者。`observed_plus_original_crypt_preload` 以AP70记录过的dlopen库+im/appFw+建议crypt preload为根；`not_in_this_namespace`保留命名空间仍缺但固件有定义的条目。动态日志是load尝试记录，并不保证每次成功；/tmp/shared.6TFiRY的内容身份未证明，appFw按已知日志错误加入。原厂IMDB全可定位库闭包是风险超集，不能称作AP70实际全部已装载。原厂未发现preload配置，不额外臆造原厂preload库。

风险排序：P0 iCrypt_HasPublicKey已发生（有原厂供应库，故不在固件缺失表）；P1 appFw中的强导入 adf_ext_type（call 0x2dd0e7c）与 remote::send_key_event_to_input_infra（call 0x2ddf49c），有直接可达包装调用，尚无本轮执行证据；P2其他已观测库强未定义；P3只在IMDB超集的强未定义；P4可选弱导入，通常受空指针门控、不能当成即将崩溃。下表按此规则排序，不把静态调用点冒充已调用。
