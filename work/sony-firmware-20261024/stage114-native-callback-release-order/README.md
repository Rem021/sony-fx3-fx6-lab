# FX3 7.02：消息释放与回调登记记录的不同寿命

2026-10-27。**MPR 原回调的公共返回出口会请求释放消息；用户 worker 随后进入下一次接收，驱动再处理上一条待结束的回调登记记录。登记记录留到下次接收，不代表消息数据也保持有效。** 本轮把两种对象分开，限制未来诊断只在释放前获取独立副本。

正式结果：[release-order-results.json](run-original-refcount-and-cleanup-20261027/release-order-results.json)。12 组原分配头与释放、2 组不同尾值控制、2 组缺客户端、8 组回调结束分支、2 组 MPR 用户释放封装、2 组下一次接收，合计 110 个有界阶段。Mac-only；没有 Windows、UU、相机接口、主机 ioctl、模块装载、真实锁、池释放或刷写。

## MPR 的公共释放出口

原 `_ZN3mpr5Codec17CallbackFromAvbbcEPvS1_` 位于 `0x28593c`，长度 400 字节。此符号内唯一普通 `RET` 在 `0x285a08`；其公共出口 `0x2859ec` 将原消息指针与队列 ID `0x80c70047` 交给 `osal_free_msg`。匹配回复的 48 字节复制在这段公共出口之前，但中间的状态清除、信号与锁仍未执行。

本轮从**独立声明的公共清理帧**开始，绑定同固件原用户 OSAL 函数。原封装生成操作 `0x8000000b` 及相同队列 ID、消息指针，然后停在 ioctl 之前。结合阶段 113 的原表，操作 11 对应原内核释放入口。没有把 ioctl 返回伪装成成功，也没有宣称此前回调已经完整运行。

因此，不能把回调收到的消息指针存下来，等回调结束后再读取。安全诊断设计需要在确认可读范围和所有权的前提下，于释放前复制所需数据，随后只传递独立副本。原外部 raw98 参数还有其独立寿命，不能因为复制了回复头就认为参数体也已保留。

## 原引用计数与真正归还池的边界

沿用阶段 47 的官方 `osal_uipc.ko`，SHA-256 `6aa0f5c8c72f5f6cf9aa9c905fc3f3f75b8bea0dfebaf13deb632b0de088eb38`。先执行阶段 112 的原分配片段，在声明客户端和 128 字节块下生成原头部、数据指针、引用计数与尾标记；再独立给定动态客户端查询结果，执行 `osal_free_msg` 的原引用更新片段。

| 声明条件 | 原消息引用结果 | 原客户端块计数 | 后续边界 |
| --- | --- | --- | --- |
| 消息引用 2 | 减到 1 | 保持 1 | 原函数返回 0，没有调用池释放 |
| 消息引用 1，普通客户端有私有池 | 减到 0 | 减到 0 | 私有池释放前停止，参数为原块起点、128 字节 |
| 消息引用 1，普通客户端无私有池 | 减到 0 | 减到 0 | 全局池释放前停止，参数为原块起点、128 字节 |
| 消息引用 1，flags bit3 设置 | 减到 0 | 减到 0 | 本轮所用非零块大小分支走全局池释放前停点 |

此处 bit3 的含义不扩展为实机当前配置。引用 2 是独立声明输入，不是证明本机当前真的持有两个引用。原头部的前缀标志使归还地址从消息头反算到 128 字节块起点，覆盖了额外 40 字节预留。

缺失客户端的独立结果返回 `-0x400`，不读取块。尾值从 `0x77777777` 换为声明控制值时，所执行释放片段仍到达相同池释放前停点；这段代码没有读取该尾区域。**尾标记不是这段代码的安全验证凭证，返回 0 也不等于所有引用和存储已释放。** 池服务本身、后续重用和并发原子竞争尚未执行，不能由单线程 guest 原子指令推断实机并发安全。

## 下次接收处理的是另一种对象

原用户 worker 从回调后的 `0x32f4` 再次准备操作 `0x8000000d`，停止于 ioctl。另一独立内核片段从待处理 slot 取出回调登记记录和消息头指针，先把登记记录 slot `+0x78` 清零；解锁保持为未执行间隙。其后原异步分支把记录和消息头作为 `finish_callback` 参数，停止在调用前。

本轮另执行 `finish_callback` 的声明客户端、锁后片段：

- 非 broadcast 声明客户端、空后续队列：登记记录待处理计数由 1 减到 0；所执行片段不读取声明消息块，然后停在解锁前。
- broadcast 声明分支、非空链单元而链头为空：另减消息引用。引用 2 减到 1，引用 1 则继续到池释放前停点。
- broadcast 声明分支、链单元本身为空：所执行片段不减消息引用。

这些差异依赖明确声明的客户端 flags、链结构和队列。**不能把一种分支的所有权规则套到所有客户端，也不能把保留登记记录理解为延长消息数据寿命。** 本轮没有让真正的回调、用户释放、下一次接收和内核 finish 在一条运行时事务中连起来。

## 公开故障案例复查

[A7CII 原故障帖 #31](https://github.com/QAQLeonard/a7c2-fl23-research/issues/31)在 10 月 27 日新增用户反馈：经仍可用的录像模式启动后，拍照模式也可恢复。此前还有两名用户确认通过录像模式进入后处理。它是用户自述的应用启动路径恢复，不能支持所有刷写故障、BootROM/eMMC 故障或 FX3 恢复保证。

**本项目推论：**目标改动作用于 FX3 MAIN 录像，不能把“未坏的录像路径”作为独立救援前提。[A7IV 原维护者仓库](https://github.com/DavidBuchanan314/ILCE-7M4-RE)另描述 BootROM/fastboot 备份恢复，但明确存在 boot0 加解密尚未实现的例外，且对象是 A7IV；不据此操作 FX3。REA 的 FX3 7.02 帖直接刷新失败，搜索索引仍是功能请求，不能把缓存评论数当成当前完整支持清单。

## 限制与下一步

新增两处原 ABS64 数据指针只在 guest 副本中解析到原 `.bss` 的 `vpool` 符号；原执行指令不变，运行前后映射镜像与允许区外内存不变。局部符号绑定不是 Sony 实际装载器的证明，核对由同一代理完成。

本轮 [诊断寿命约束](diagnostic-lifetime-refinement.json)仍为不可部署说明。消息映射和生命周期尚无实机证据；目标 1080p29.97 HEVC42010 约 16 Mbps、自然 MAIN 参数、FH/16M 资源匹配、硬件 Open/Start、文件音画、长录温控冷启动，以及同机健康备份、受限恢复回读与独立救援保持未验收。全部 16 项状态、授权及阶段 75 不可部署原型保持。

下一步回到自然 MAIN 参数生产者与质量/码率资源匹配，用现有传输边界约束筛选最小诊断点，不再仅因消息局部实验通过就推进刷写。Windows 继续延后；没有新增实机操作请求。
