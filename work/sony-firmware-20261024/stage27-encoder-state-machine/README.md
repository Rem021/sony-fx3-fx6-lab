# FX3 Open 状态机受理与待处理参数寿命

本阶段确认：普通Open参数复制之后的 `0x178aac` 主要输出诊断信息；后续请求进入内部状态机。12个受限原指令用例核对了数值状态、忙碌排队、返回值转换和动作选择。**这仍不是硬件Open成功，也没有形成可安全刷入或可靠救砖的方案。**

新增的安全相关证据是：一个忙碌分支复制0xd8字节事件时，保留了指向原参数区的内嵌指针。本阶段不能证明完整消费路径永远不重绑该指针，或实机存在悬空访问；但后续备份/受限修改/恢复流程必须继续追它的所有者与寿命，不能只覆盖应用层队列。

## 参数诊断与实际状态机分开

原av-cam的0x178aac–0x1798ec有912条指令，直接调用包括各45次0x27d528/0x27d568诊断入口，以及头部输出帮助函数0x17e528和名称查找0x17e8b8各一次。它和0x17e528的函数体中均未找到非栈存储指令。

调用者在0x177b98调用该函数后，两条后续路径分别在0x177ba4或0x1786a8覆盖X0，没有把该返回值拿来判断格式接受。本轮因此不再把这里当作待验证的核心格式转换函数。该结论只覆盖原函数体、直接调用和已核对的返回使用；诊断后台没有执行，也未声称它们完全没有其它副作用。

实际后续提交在0x1786b0调用0x17eb64。这个封装读取内部状态机指针，调用0x17eb80，然后将其原返回值与0比较，生成0/1。不能把这一封装结果当成编码器Open成功码。

## 原数值状态和动作表

Open处理表位于文件0x36c4f8，每行0x18字节，分别含guard、action和next指针。其数值状态0对应：

| 项目 | 原函数 | 本轮核对 |
|---|---|---|
| next | 0x184a4c | 返回数值状态1 |
| guard | 0x184a2c | 返回常量1，不读取视频参数 |
| action | 0x184a34 | 通过owner调用0x17b794 |

0x17b794还需读取owner+0x20处的接口，再取其虚表+0x10。本轮没有建立该实际接口对象与完整实现的绑定，没有执行Open动作。

目标HD MAIN、匹配proxy和非法codec/frame三个独立fixture，在数值状态0且busy=0时都走到状态退出钩子0x184cc0之前停止。另一个数值状态1的fixture，next得到0x16，停在无效事件诊断之前。它们说明原当前状态有影响，也说明这个局部guard/next选择没有验证目标视频参数。

两个独立的“状态转换之后”片段按old0/new1的明确前提执行原动作表选择，抵达owner的0x17b794入口即停止。前置退出/进入钩子、实际状态更新和真实动作均没有执行或被stub成成功，各独立片段不能拼成一次完整成功。

## 同一个封装值对应不同情况

| 明示数值状态/前提 | 0x17eb80原返回 | 0x17eb64封装的零值比较结果 |
|---|---:|---:|
| state=0x15 | 3，并写state=0x16 | 0 |
| state=0x16 | 4 | 0 |
| busy=1、pending=0的待处理路径 | 1 | 0 |

没有为3、4、1套用未经绑定的官方错误枚举名。这里确实存在不同情况得到同一封装值的现象；不能只看这个0就推断硬件失败，更不能凭请求进入本地处理流程就推断硬件成功。

## 忙碌分支的0xd8字节事件

当busy=1、pending=0时，原代码先执行0x27da84复制封装，后者调用映像内原copy例程0xd80。它将0xd8字节复制到状态机+0x368，然后设置pending，再检查队列计数。三个对照覆盖：

| fixture队列状态 | 原片段观察 |
|---|---|
| count0/write0 | 复制事件，设置pending，追加状态机+0x350的functor指针，count变1/write变1 |
| count9/write9 | 复制事件并追加，count变10/write回绕0 |
| count10/write0 | 仍复制事件并设置pending，但本次不追加functor，count/write不变 |

队列满这一片段不能单独证明运行时会丢请求或构成固件缺陷；还需上游调用约束、后续消费和错误回复证据。busy=1且pending已经置位的另一对照停在重入事件诊断之前，没有执行其后状态或错误处理。

客体事件由已确认的0x28头部、0x98视频参数和明确标成未知的0x18尾部fixture构成，不是真实抓取的机身事件。复制后的内嵌参数指针仍指向原事件+0x28，而不是新pending副本+0x28；本次原复制片段没有重定位它。源事件和参数保持不变。

由此可以提出一个必须继续闭合的寿命要求：恢复/替换时要覆盖下游MC状态机的pending、functor队列及它们仍引用的源参数区。是否有后续指针重绑、同一持有者长期保活、同步保护或其它消费约束，当前未验证。不能把本轮的合成排队用例当成真实并发、安全点或恢复器实现。
