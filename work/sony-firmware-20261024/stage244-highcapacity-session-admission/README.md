# FX3 首次程序试验的通信路径判定

2026年10月30日。对应实施路线第2项。本批不需要连接相机。**相关原厂命令的静态登记链已核对；现有GET_FILE2结果文件回传候选保持不放行。** 第2项没有完成，首刷前仍有5个里程碑未通过。没有重复此前模拟测试。

## 本批解决了什么

[静态核对器](audit_session_contract.py)只将两份已保存的官方7.02共享库当作文件解析。原件SHA固定，保存了12处完整函数或明确边界的代码范围、71处指令及3条命令表记录的逐字对应。没有运行Sony、Linux或glibc指令。

原厂1001类别的命令15、16、17登记在libsencore表中，分类分别为400f、4010、4011，指向队列016f0480。libJiritsu的jiritsu_init在6dbc登记回调b278；命令消息桥取命令低字节，回调通过原跳表接入发送或读取包装器。此前“原件是否确有相应类别与接收处理端”的静态连接已经补上。**这不证明当前机身实际加载/登记了它，也不证明已经通过认证。** [原件与全部核对](static-contract.json)

## 为什么当前结果回传不能直接上机

1. DMM管理对象保存在全局46bd0。新的阶段1请求会析构旧对象并更换它；阶段4处理命令，读取的阶段16负责释放。包装器中的16/17/18是内部阶段返回值，不是自写程序的成功状态。
2. 选定文件路径保存在另一全局467c8。选路径会释放和替换旧值，GET使用并释放当前值。自写模块的nonce、目录占位及主机自己的锁没有自动覆盖这两份原厂状态。
3. 即使队列逐条处理请求，也不意味着整组“选路径到读取”不可插入其它请求。若存在两个获准请求来源且底层没有整段租约，就可能出现A选自己的文件、B替换路径、A读到B路径的顺序。这是有明确前提的静态反例，未在真机观察或执行；也没有据此宣称原厂不存在其它排他机制。
4. 操作0的读取链先经过sys_mount、CFileAccess::mount、selection_mount。目标/tmp/jiritsu不匹配/mnt前缀，因此原分支到f7c0，再在f7d4调用libc mount；传入标志c0ed0490未请求MS_RDONLY。这不证明此次一定写了闪存，也不能证明它是无持久副作用的RAM读取。

所以，本批明确排除将第243阶段两条内层候选帧直接作为USB测试、用自有目录占位代替原厂状态排他、或将该GET描述为已经安全验证的RAM回传。**否决的是当前候选的放行依据，不是宣称FX3所有入口都不可能。** [可读取的判定](decision.json)

主机审查器首次把sys_mount尾跳的符号预期为libc mount，实际先进入CFileAccess包装器，断言当场停止。原审查器和[失败记录](initial-audit-failure.json)已保留；补齐两级包装器和实际非/mnt分支后，静态核对才通过。这是主机审查修正，没有相机故障或设备操作。

## 下一批如何决定是否需要连接

只定义最小通信诊断：以当前MSC为条件，明确主机控制端与身份前置、具体命令白名单、预期响应、全局时间预算和退出/归还判据；排除上传、选路径、文件GET及模式切换。认证引起的状态或持久副作用必须单独说明，不能把“未写固件”扩大成“零副作用”。195号主机对照方案仍保持未批准、未启动，本批不重新申请。

在固定程序和边界齐全之前，不让用户为本批接线。如果仍不能形成这样的方案，应交付缺少的具体证据或条件，停止追加相同模型案例，不自动回到现有文件回传路线。
