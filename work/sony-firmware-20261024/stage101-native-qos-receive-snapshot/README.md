# FX3：原接收副本与上层命令转换边界

**原接收片段先把码率参数复制到上下文，再把该副本的指针交给状态机；上一阶段的指针队列不能直接解释为借用外部消息。另一个新限制是：目前核对的原库命令转换表没有下层码率命令0x10a的映射，不能直接通过此前已验证的转换入口发出它。** 仍未找到自然产生16Mbps请求的实际MAIN策略，没有硬件实录、恢复或可刷入版本。

地址、命令号与字段偏移为十六进制，状态数字与统计计数为十进制。本阶段仅Mac离线，所有原文件和既有stage75客体原型保持，没有访问Windows/UU或相机。

## 从原MID分派到上下文副本

原`177934`序言建立真实保存帧；任务hook的查找/调用未执行。独立进入原`177960`后，原表`36b970`分别把MID`107/108/109/10a`送到`177980/177bfc/177c8c/177d28`，均先停在各自日志入口。没有用宿主分支代替MID选择。

在`10a`分支的日志之后，原`177d98`及复制函数`d80`执行以下操作：

| 原字段与动作 | 本轮观察 |
| --- | --- |
| 输入消息`+8`的48字节 | 原样复制到状态上下文`+358` |
| 原调用参数W2 | 保存到上下文`+3a0`，即副本后紧接的4字节；原诊断文字称为reply_id |
| 副本与回复字段合计4c字节 | 后续原尾声把上下文`+358`的指针交给`17effc`状态事件分派 |

这里的输入头CID2003、长度50、W2和对象图均是明确fixture；本层MID分派不等于外层CID、完整长度、来源、传输或当前通道已经验证。它也不是下层CID2103、长度54、带4字节通道的同一封套。没有因为两个位置均使用MID10a就复用结构布局。

参数打印helper `17a9a4`未执行，不补它的返回值或副作用；之后从原尾声独立进入，使用前段原代码已产生的指针和保存帧。任务hook、日志及打印间隙使这些片段不能作为“正常接收已完成”的证据。

## 外部缓冲、上下文副本与重复交付

两种旧值背景A5/C3下，先由原复制生成16M上下文副本，再由宿主明确把外部消息目标改成20M。上下文副本仍为16M。在声明状态3中，它沿原ROM选择的动作进入时序码率入口；另在较低的独立栈调用原下层转发，生成的54字节封套仍包含16M，所有暂停的原调用帧保持。

在声明状态1中，原尾声及状态机选择排队动作。明确的日志间隙后，原队列体及其调用者尾声返回，队列指向上下文`+358`，不是外部输入地址。返回值只是该局部事件结果，不是编码器已应用或完成确认。

另对同一客体明确交付第二个20M请求和不同回复字段。原接收复制先重写同一个上下文缓冲，然后才到下游非空队列检查；队列计数和指针保持，但该指针现在指向20M及新的回复字段。第二次执行停在忙碌日志入口，未把它当作成功应用。

这个顺序试验没有执行任务hook、真实上游串行约束或状态生产者，不能证明相机允许连续这样交付，也不构成固件竞态/缺陷结论。它改变的是后续方案的核对方向：先确认上下文副本的合法代次、重复请求约束及回复关联，不能仅用外部消息寿命或队列计数来判断。stage100已经证明的“队列只存指针/出队不擦槽”仍成立，其指向对象的来源在本轮得到了更具体的限定。

## 现有上层转换入口的限制

原`libInfraAvbbc.so`的`ObjAvbbcCmn::ConvertCmdMidToMc(unsigned short)`位于ELF VA`140eac`，64字节。它通过`1b2678`符号重定位槽读取`ObjAvbbcCmnTable::midConvTableToMc`，原表位于`16aff8`，176字节，包含43条映射和1条FFFF终止记录。

| 输入 | 原函数输出 |
| --- | --- |
| 520 | 201 |
| 529 / 530 / 531 | 107 / 108 / 109 |
| 532或直接传10a | FFFF |
| 50a | 0；不解释为应用成功 |
| 10529的寄存器输入 | 107；原函数首先取低16位 |

这张原表没有任何10a输出。8个原函数探针完整返回，没有原生写入，表及解析后的指针槽保持；只使用本地已定义符号绑定，没有返回适配器或日志替代。

**结论只限这份原表及本地符号绑定。** 尚未排查所有固件API、其它库、直接MC路径、运行时符号替换或真实策略，不能断言系统全局没有码率设置能力，也不能将缺映射解释为硬件不支持。现在应继续寻找原生的其它调用路径，而不是把相邻命令号或下层存在的处理函数当作上层已有入口。
