# FX3 MAIN FF 的16M私有数据候选与原参数封装

本轮形成一个更具体的**离线数据候选**：将已匹配的MAIN FF原预置复制到客体A的独立缓冲，仅改变目标系数，原HEVC参数封装片段便生成target=16,000,000；trace=25,999,360、CPB=26,000,000及其它已封装字段不变。另一个使用同一原FF预置的客体B仍得到24,498,176。

这不是已实现的原生写入钩子或可上传模块。候选指针与一个32位系数由**明确的客体fixture设置**产生，原固件只读，实际状态、配置代次、准入/生命周期、完整参数包和HAL/硬件仍未验证。当前不放行上机、刷写或恢复。

## 原代码确实消费了候选数据

原0x221fd0片段从common+0xe000取得选中预置，并读取目标、trace与CPB系数。原指令分别把它们打包到下游参数块+0x2c、+0x30与+0x34。本轮在0x22211c继续读取其它参数之前停止，未执行整个构造器、后续固件命令或HAL。

这比只调用默认值解码器多了一项证据：候选16M已经被原参数封装指令读取并写成对应字段。它仍不是完整有效硬件请求，更不是编码器已接受或生成了16Mbps码流。

## 副本如何建立

原资源公共对象为另一类streaming模式保留了common+0xe010开始的0x100字节预置副本区。原0x226364分支复制的是不同模板，并有不同的模式/质量条件；**不能直接把该分支当作MAIN FF复制实现**。

本轮在隔离客体中：

1. 运行原描述符复制前缀与原MAIN FF行386/preset0x19450选择，之后的构造和运行时清零未执行。
2. 调用原通用memcpy，把原0x3c5798的0x100字节FF记录复制到A+0xe010。副本结束位置恰为A+0xe110，未覆盖其描述符。
3. 由显式fixture把A+0xe000指向副本。原解码/封装结果与复制前完全相同。
4. 仅将副本+0xb0的目标value_minus_one改为249,999；原scale0不变，对应`(249999+1)×64=16,000,000`。trace、CPB、MAIN类型、preset身份与其它字节均保留。

原记录实际发生差异的字节均位于+0xb0…+0xb3这个32位字段内；原封装输出的差异则仅在+0x2c…+0x2f目标字内。原静态记录与整份映像的哈希保持不变。

fixture设置前核对了A的MAIN流类型、FF质量、HD/29.97/逐行/42010描述符、行ID和原指针。这是保护**离线实验**的检查，不是原生固件准入、线程安全点、身份认证或恢复策略。

## 复选原指针后，旧参数仍然存在

最后执行的是**原预置选择器**，它让A重新指向原FF记录，原默认查询和新生成参数均回到24,498,176。

但之前已经生成的参数块仍包含16,000,000，A的私有副本也仍保留候选数据。原选择器没有替此前准备的数据建立退出/销毁证明。

因此，“原指针恢复了”或“新查询回到默认了”不能证明所有待消费参数、缓冲与硬件状态都恢复。这是客体参数复制层的具体证据，不是已完成的安全恢复。真正恢复必须覆盖已生成包、队列、消费者、HAL应用/反馈和代码/数据生命周期，仍需沿用此前准入与安全点要求。
