## 新证据与对备份的影响

| 声明输入与原指令结果 | 对备份的要求 |
| --- | --- |
| 32字节目标只读到31或0字节：原函数返回0，内部回复为 `0x1000000a`，有效回复长度只有4 | 必须分别检查传输、内部状态和完整长度；返回0不是文件备份成功 |
| stat大小为0：原路径实际准备 `read(...,0)`，可正常回4字节成功状态 | 零长度不能单独证明目标内容已经备份，尤其不能代替分区容量测量 |
| 声明stat为4GiB+16：原stat方法保留64位大小，但调用者只读取16字节并回20字节、状态0 | 接口没有通用大文件完整性保障；必须限制类型和大小，并独立验证完整目标 |
| 声明大小为4GiB减4：`N+4` 回绕成0，原大小分类接受最小档，后续准备极大读取 | 主机输出上限不能约束设备分配/读取，不能将它作为泛用原始分区读器 |
| 官方appFw参考79,015,712字节：普通分支分类输入79,015,716，选单位0x307；variant1输入158,031,432，返回未接受单位 `0xffffffff` | 普通/variant1资源要求不同，不能套同一容量判断；分类通过也不证明当前可分配内存 |
| 待处理日志分支完整或短写后都改用日志路径进行后续stat；短写时待处理字节数仍保留 | 读命令可走到日志处理，并非每个selector都会读取最初声明的系统文件 |

这些尺寸是**声明条件下的原代码行为**。4GiB边界没有在用户机身或实际文件上触发；不将它声称为已确认的实机漏洞。当前appFw参考远低于4GiB，但通用备份接口仍需排除这些语义。

原长度链是：FILE_INFO `+0x820` 保存64位N；普通分配使用32位 `(N+4)`，variant1再做32位二倍运算；read参数取low32(N)，完成比较也只比较32位。按已查原分类上界，在不回绕且只讨论分类数学范围时，普通N最多 `0x63ffffb`，variant1最多 `0x31ffffb`。这不等于设备端有可配置范围读取，也不保证DMM空闲/容量/所有权。

## 正常退出与异常仍需分开

跨函数正常/短读guest中，原程序以flags0准备一次POSIX open、一次read、两次fsync和一次POSIX close。GET_FILE2虽两次调用CFileAccess::close，第二次原方法看到关闭标志后直接返回；不能把两个包装方法调用误数为两个实际close。

负的stat/open/read/fsync提供者结果会进入C++异常准备。本轮停在异常申请前，没有伪造展开/处理完成，因此这些跨函数例没有“服务完成”结论。较早16组中声明FileAccess直接返回-1的分支，只证明该返回值下调用者如何处理；其中4GiB减1与-1低32位相等的反例，不证明真实POSIX异常一定以该方式返回。实际异常选择、清理与最终回复还需追踪。

Linux `read`本身允许短读，成功时应按实际字节数解释；Linux单次读取上限也不能修复调用者的32位长度运算。[read(2)](https://man7.org/linux/man-pages/man2/read.2.html)。`st_size`对普通文件/符号链接有明确长度语义，不能替代原始设备容量接口。[stat(3type)](https://man7.org/linux/man-pages/man3/stat.3type.html)。这些是通用规则，未测量用户机身的实际VFS行为。
