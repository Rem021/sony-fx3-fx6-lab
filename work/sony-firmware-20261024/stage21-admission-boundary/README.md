# FX3 构造、入队与停止路径边界

本阶段补上了退出观察中的一个缺口：**已捕获实验配置的对象可以尚未出现在队列或当前对象槽中；只检查这两处不够。** 17个受限阶段用例及3个复制状态的原wait判断通过。这是合成观察范围反例，尚未证明真实相机存在竞争问题，也没有实现可上机的禁止入队或恢复方案。

## 原入口和构造范围

来源固定为官方7.02提取的 `appFw.so`，SHA256 `545c5053a74e04ffbf2bbaaf80f558092dd545ed2298b2395ca547dbba58290f`。内部类型113（0x71）仍绑定 `sequence_get_media_remain`、pool0，不是remote格式或PTP属性。

原member调用表GOT0x4714100指向0x4a41278，类型113的16字节表项在0x4a41988，函数为0x2c3e01c、this调整为0。通用两任务调用函数0x2bd1940先取得manager+0x2b90的锁，再按表调用工厂。原指令分派片段在实际工厂入口停止，参数没有用stub填写。

另一条确认路径是数据表0x4029600引用的typed wrapper 0x271760c。它通过原getter取得全局manager，再把类型113、参数地址和原始option传给0x2c3de38。本阶段没有追到该wrapper所有外层调用者，不能据此断言外层有没有model_lock。

扫描全部可执行PT_LOAD的直接B/BL，找到该类构造函数0x2c3d618的5个调用点：

| 工厂入口 / 构造调用 | 本函数可见的动作与锁 |
|---|---|
| 0x2c3dbd0 / 0x2c3dc70 | 先取manager锁及pool锁，找到排队目标，再构造新对象并插在目标之前，还会调整相关token登记 |
| 0x2c3dd34 / 0x2c3ddc4 | 从后向前查找排队对象并替换；函数内部没有取得pool锁，外层契约未闭合 |
| 0x2c3de38 / 0x2c3de6c | 先构造，再调用公共入队函数；registry-lock控制值为1 |
| 0x2c3deec / 0x2c3df8c | 持有pool锁向后查找并替换；未找到时，解锁后回到普通typed工厂 |
| 0x2c3e01c / 0x2c3e054 | member表工厂，先构造、可选连接依赖，再调用公共入队函数；控制值为0，已确认的外层分派持有manager锁 |

另有0x2c3de98先做原查找，未找到才进入普通typed工厂。这里的清单覆盖固定构造函数的直接调用，不代表所有间接调用、运行中可达性、外层锁或其它补丁消费者均已闭合。

公共入队函数0x2c0d628有1490个直接B/BL引用。本阶段据此保留通用基础设施边界，没有提出全局禁用它来充当实验模式退出开关。

## 构造到入队的区间

普通工厂在构造返回后才进入0x2c0d628。该构造函数的内层model_lock守卫在0x2c3dbbc退出；外层可能仍持有逻辑所有权，这一点未验证。

公共入队路径的静态正常顺序为：

1. 取得请求token，写入对象的类型、token、名称及manager指针。
2. 查询依赖关系、处理登记；是否在本函数内取得manager锁由控制值决定。
3. 按类型映射pool，取得pool+0x18的锁。
4. 分配列表节点，调用原列表hook插入，增加排队计数，解锁。
5. 对pool+0x48的条件变量调用notify_one，唤醒该pool工作线程。

typed正常路径在登记后释放本函数取得的manager锁，再去取得pool锁。member分派的外层manager锁则可能仍覆盖这段过程。控制值0因此不能简单标为“无锁”；必须连同调用者解释。

本阶段构造两个新观察对照：使用原87个getter读和此前已封存的客体标记代码，分别捕获原厂标记0、实验标记2；随后在另一个合成客体中，把对象放在队列之外，设置当前槽和队列为空，将后续实验开关设为0。公共入队入口执行到原token帮助函数就停止，没有产生token返回值或队列节点。原单pool wait谓词对这两种状态都放行，标记2的对象字节仍然存在。

另一个独立片段从“token帮助函数已返回”的前提出发，执行原元数据写入后停在依赖表查找入口。即使对象已有类型、名称、token和manager指针，只要它还未加入队列，原pool判断仍看不到它。

这些结果证明的是**该pool谓词不覆盖队列外的生产过程**。它们没有执行完整构造、调度或外层锁，不能证明这种状态在真实退出时一定可同时被观察，也不能证明原厂有缺陷。构造前后入口、生产者生命周期和外层所有权必须加入后续方案的证明范围。

## 通知和整组停止的区别

入队通知是pool+0x48的notify_one；上阶段确认的任务完成通知是manager+0x2bc0的notify_all。两者不是同一个条件变量。原wait仍应复查条件；通知本身不能当作退出凭据。[C++条件变量工作草案](https://eel.is/c++draft/thread.condition.condvar)（2026-10-25核对；只解释通用语义，不是Sony运行库验收）。

原0x2c0d570包含向29个pool加入空对象节点并通知的代码，随后遍历29个线程handle，调用0x2f71e60，后者直接转到 `osal_wait_thread_exit` PLT。空对象在原worker 0x2bd76bc选择返回分支，区别于正常任务发布路径。

本阶段只运行空对象分支到解锁入口，以及一个等待调用的传参片段到PLT；没有插入空节点、等待真实线程退出、运行后续线程池停止帮助函数或重启。该函数的实际调用者、适用应用状态和可逆重启条件均未建立。因此这段应用级生命周期代码不能直接拿来作补丁卸载按钮，更不是故障时的独立救援入口。

由原控制流还可推得：仅持有manager锁并要求旧worker完成，存在相互等待风险，因为worker收尾也要取得它；原wait通过条件变量释放并重新取得该锁。禁止新实验请求的状态必须能跨越等待保留，不能把“持有这把锁”本身当作完整方案。这是设计约束，未作原生死锁或竞争实验。
