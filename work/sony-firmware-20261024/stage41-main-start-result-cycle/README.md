# FX3：MAIN START结果读取与同对象START→STOP周期

本轮接上了原START_DONE读取函数，并在**同一个客体owner**内串起原消息发布、START结果读取、再次借用消息缓冲、STOP发布与四类参数清理。79段原代码片段、6次客体原型调用和5类对照通过。

START读取只归还消息缓冲，四类编码参数仍保留；后续STOP_DONE消费才在本对照中归还它们。这比在不同初始对象中分别测试更进一步，仍不代表实际相机已经启动、停止或恢复。

## 原START读取入口

原0x2249d0读取当前队列项，消息+2为0时取出消息+3、+4的16位字段和+0xa字节，写入输出+0、+2与+4。它弹出消息，并在条件允许时归还消息缓冲；没有调用四类参数索引的归还函数。

正式正例通过原0x2304a0进入：先执行+0x390对象调整，再经0x228b64和0x227870查找owner，最后运行上述读取函数。注册树、对象及原消息仍为fixture，真实上层调用者未执行。

未命名字段只按偏移记录，不把消息+3的任意非零值命名为某种编码错误，也不把返回0当成硬件成功。

## 查看队列也不能只看返回值

原0x22c528无论队列是否有项都返回0；它通过输出标志指示是否有消息。队列有项时另写出消息类型，队列为空时类型输出保持原内容。

本轮原执行覆盖：空队列→标志0；START发布→标志1/类型0；START消费→标志0；STOP发布→标志1/类型3；STOP消费→标志0。空队列不能继续把遗留的类型字节当作有效新消息。

## 同对象周期的状态

| 阶段 | 待处理消息数 | 消息池可用数 | 参数池可用数 | 四类参数索引 |
|---|---:|---:|---:|---|
| 初始化 | 0 | 1 | 0 | 均保留 |
| 原START发布 | 1 | 0 | 0 | 均保留 |
| 原START结果读取 | 0 | 1 | 0 | 均保留 |
| 原STOP发布 | 1 | 0 | 0 | 均保留 |
| 原STOP消费 | 0 | 1 | 4 | 均移除 |

两次发布均执行了上一阶段的原owner查找/借缓冲前缀，再以明确捕获的输入运行诊断后的独立片段，执行原RTTI、消息复制与排队。必经诊断未执行，没有伪造返回值，因此不是完整接收函数的连续执行。

第二次发布确实通过原池操作重新借到了第一次原START读取归还的消息缓冲，未由宿主重置池或待处理索引。消息队列读写位置最终均为2；消息池读取位置2、写入位置3。

四类参数副本在START后仍保持原字节，编码副本target=16M；STOP归还也不擦除它们。这里证明的是本地消息/参数生命周期，不证明实际HAL所有读者已经退出。

## 五类边界

| 明确的人工条件 | 原执行观察 |
|---|---|
| 把STOP_DONE交给低层START读取函数 | 返回0，输出未变，消息和四类参数仍保留 |
| START消息+0xa改成1 | 原样输出该字节，四类参数保持；低层读者不比较期望键或epoch |
| START消息+3改成7 | 原样输出7，函数仍返回0；字段正式错误语义未绑定 |
| 消息归还队列计数设为满 | START仍被取出、输出写入，但没有追加归还消息项；此人工边界不证明实际机身泄漏或池配置 |
| 待处理计数设0，并显式提供fallback槽指针 | peek报告无待处理项；刻意调用低层读者仍可从fallback取值并归还消息 |

fallback对照中的脱离队列和指针由fixture提供，未验证这是MAIN正常接收顺序或允许的调用条件。它不能用来认定原程序会错误地处理旧消息。需要核对实际调用者如何约束这些槽位、请求身份和代次。
