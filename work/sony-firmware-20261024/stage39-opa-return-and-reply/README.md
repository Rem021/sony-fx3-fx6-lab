# FX3：原参数缓冲归还、索引移除与消息清理

本轮接上了上一阶段保留副本的**原代码归还路径**：在明确的离线消息/池/对象输入下，原函数把四类参数缓冲交回池、移除各自索引节点，并归还消息缓冲。正式运行通过74段原代码片段、17次客体原型调用及5类负例，另验证了池最后一格的归还与再次取用。

这使下一步可以定位真正需要接入的归还观察点。**真实消息生产者、请求关联、配置代次与HAL完成尚未绑定，不能据此认定安全恢复或实际主录可用。** 本轮仍没有连接或写入相机。

## 原代码链路

上一阶段原复制函数0x21a3b8把参数保存到独立池缓冲，并登记在owner+0x1160、+0x11e8、+0x1270、+0x12f8对应的四个索引。其请求复制长度分别为0x40、0x1c0、0x80、0x300。

本轮先用这些原函数创建四个实际客体副本/索引，再运行：

- **0x225934**读取人工准备的待处理消息。仅当消息+2为3时，按消息+0xa的8位键依次清理四个索引。
- **0x21c114**查找匹配键，调用0x22c6f8归还缓冲，成功后调用0x21d704移除节点并将节点放回其内部可用槽。
- **0x22c6f8**向owner+0x1038对应池追加缓冲地址/容量，增加可用计数，写入位置在0x2a8个槽位间回绕。
- 完成后0x225934还把原消息缓冲放回owner+0x10对应队列。

另一个正例执行了原0x228bbc包装函数，经0x227870的键控owner查找，再尾调用上述清理函数。包装层对象与owner索引仍是人工构造；真实接口注册及上层调用者未确认。

## 实际观察到的归还

四个池块容量均为1024字节，原复制分别写入上述请求长度。清理前池可用计数0，四个索引各保留一个节点；匹配消息清理后：

- 池可用计数变为4，返回的四组地址/容量与原取用值一致。
- 四个索引根均为空，四个节点均回到各自可用槽。
- 待处理消息计数由1变0，消息归还队列增加到1。
- **归还不擦除内容**：四个缓冲与消息字节保持，编码副本仍包含先前16M参数。归还、改写数据和擦除数据是不同动作。

独立回绕对照从有效的空池末尾索引0x2a7开始，执行原归还，再执行原取用/复制；写、读位置分别回到0，目标缓冲收到新数据。它证明该局部环形队列操作，不证明实际机身全局池状态。

## 返回0不能单独作为放行依据

匹配消息的清理函数返回0。但把消息+2改为2时，它同样返回0，同时不弹出待处理消息、不清理四个索引、不归还参数或消息缓冲。

另一个对照把消息+3从0改为7，清理行为与返回值保持，原函数把该字节复制到输出。**目前没有绑定消息+3、+4、+0xa、+0xb的正式字段名称或真实生产者**，因此不能把7命名为某种编码器错误；它只说明这个字节与局部清理结果不同。首次记录曾用`status`作为测试标签，正式复核已更正为`byte3`，旧记录保留，不作为错误码语义证据。

## 部分清理与负例

| 人工条件 | 原执行结果 |
|---|---|
| 消息类型不符 | 返回0，无处理，四个索引和待处理消息保持 |
| 消息键不符 | 到达原诊断入口，四个索引仍保留，无参数归还 |
| 第二个索引的键不符 | 第一类已经归还并移除，其余三类仍保留，然后到达原诊断入口 |
| 参数池已满 | 到达原诊断入口，池计数与索引保持 |
| 包装层owner索引为空 | 原查找到达诊断入口，清理函数未执行 |

除“类型不符”的正常返回外，错误对照都在原诊断入口前停止，未执行完整错误返回或收尾。它们不证明机身存在故障或泄漏；它们明确了受限恢复需要复核的中间状态，不能假设一次清理必然全部完成。

## 客体登记与真实完成仍分开

在一组正例中，测试者给准备源和已复制编码缓冲各提供一个原型登记。归还生产者和源登记后，复制缓冲继续阻止数据复原。

随后原函数已完成上述本地索引/池清理，**原型仍拒绝复原**，因为实际完成钩子尚未接入。只有测试者显式通知“副本完成”后，原型才重新选择原预置。该通知不是实际HAL回调，亦不是相机恢复证据。

实际接入必须保证登记在发布前完成，并验证消息的真实来源、当前请求/代次、全部消费者及失败路径；还要单独证明代码执行者已退出。本轮没有卸载代码或擦除旧缓冲。
