## 原代码实际处理了什么

原 `+0x27d528` 在初始化guard置位时返回固定日志对象地址；guard未置位则进入原构造路径，本轮对此明确停止。原 `+0x27d898` 将静音输入最低位写入日志对象 `+0x1908`。本轮运行该原setter写静音位，不用宿主伪造日志函数返回。

原匹配器的诊断依次调用原名称helper，然后真正进入 `+0x27d568` 的可变参数包装和 `+0x27d5c8` 正文：

- 静音位为1时，原 `+0x27d604` 分支进入原尾声并返回。
- 静音位为0、类别2的启用位为0时，原 `+0x27d634` 分支进入原尾声并返回。
- 两个类别启用位为1时，原代码准备256字节输出区，经原CAPI绑定调用官方内核 `memset`，再进入格式化函数 `+0x27d7d0`；本轮在该函数入口前停止，不伪造格式化／输出结果。

因此，前两种**条件状态**下，上一轮“诊断可能改变寄存器或中性未知”的独立片段假设被原执行替代；本轮原getter实际返回的日志对象、helper实际返回的字符串、原日志早退及原寄存器保存／恢复都已执行。它不证明真实相机当前采用这些状态，更不要求将相机日志关闭来完成目标。

## 这一次诊断的实际参数

目标匹配诊断的原字符串参数为：`HEVC_MP4`、`29_97`、`PROGRESSIVE`、`FF`、`CHROMA_420`、`BIT_DEPTH_10`，地址均位于原映像的只读字符串中。`FF`是临时匹配视图的资源质量名称；原source和common仍保持FH，不能把日志中的FF名称当作上层模式已改变或实际码率。

其余三个原32位标量为源 `+0x1c` 的内部值0及宽高1920／1080。格式文字称前者为 `input_frame_rate`，**内部值0不等于0fps**，也不替代真实时间戳或硬件帧率；编码帧率名称为原helper输出的29_97。

在这个实际调用点，X0…X7和10个溢出参数槽中，没有匹配器原输入或临时视图的地址。格式字符串和六个文本参数是原映像字面量，数值字段来自原指令提取的标量。这个直接观察缩小了“该诊断把临时匹配视图指针传给后端”的疑虑；**不是所有诊断、全局指针不逃逸或异步后端寿命证明**。启用分支的格式化／输出仍要继续核对。

标量槽按原 `STR W` 的32位宽度解码。A5／C3旧值会留在8字节槽的上半部；原始64位槽值完整保留在结果中，但不能把未写上半部拼入32位宽高，亦不能据此宣称实机未初始化缺陷。这里是观察器类型解释，不修改客体内存来“修”结果。
