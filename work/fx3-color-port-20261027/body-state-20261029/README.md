## 下一项服务是 UPM 电源状态查询

从已提取的原 FX3 7.02 AP 分区只读取得 `/kmod/upm.ko`，453,896 字节；来源、inode、整文件哈希和上一阶段 40 项封存核验见[来源记录](service-inspection-results.json)。它是 ET_REL 文件，报告中的内核地址均为 `.text` 节内偏移，不能当作运行中的绝对地址。

原 `k_upm_framework_core_start` 的线程入口重定位指向 `.text+0x13de8`。该循环接收 `0x80920871` 消息，从原 `.rodata+0x9d0` 表分派 command 0–6。command 3 指向 `.text+0x13cf8`，按 factor 索引 `g_upm_fp_factor_func`；factor 7 的读取回调重定位到 `.text+0x1ba18`。

回调从 UPM framework 缓存的电源状态复制 40 字节，原回复 wrapper 再构造 156 字节回复。AP 原 `0x2498` 函数发出的恰是 command 3／factor 7／208 字节请求，回复目标从请求 `+0xa4` 取得。接收器、原重定位表、回调与回复代码相互对应，不再把常量搜索命中直接当作接收端。

## 三端原代码怎样执行

沿用上一阶段的原 AP 镜头准备和原 CP 元数据回复；随后由原 AP 构造 UPM 查询，内存通道交给独立 AArch64 guest，执行原内核接收循环、分派表、command 3、factor 7 回调和回复包装。真实模块中原本需由加载器修正的 ABS64 指针，在 guest 中按原重定位记录解析；外部 branch relocation 只在 guest 中转向对应原函数或严格 RAM 适配器。

CP 镜头身份、UPM 电源缓存、AP 发送 ID、动态消息通道及分配成功，仍是明确的合成输入。UPM 线程入口从声明状态启动，未执行真实内核初始化或读取物理电源。线程启动通知仅进入内存接收槽，没有伪造另一服务的执行或回复。

| 合成条件 | 原 AP 镜头准备结果 |
|---|---|
| 镜头机型／地区／版本通过，电源 type 1、jack 1 | 原电源分支设置 `0x151f0=1`，准备函数经原错误转换返回 0 |
| 电源 type 2、jack 2 | 停在 `Backup_read(0x00920017)` 前，未提供备份数据 |
| 电源 type 1、jack 2 | 同样进入备份查询边界；不能仅凭 type 1 宣称放行 |
| 镜头机型不匹配 | 原前端错误 7；没有进入 UPM 查询 |

三端桥接四组的原请求／回复字节、寄存器分支、全局写入和动态通道释放见[执行记录](ap-upm-bridge-results.json)。新增全局写入只允许原 AP `0x2588` 对 `0x151f0` 写入 4 字节的值 1，其他新写入仍拒绝。

另四组单独执行 UPM 接收／回复：外接电源、电池、插口异常以及非法 factor 24。前三组均由原回调复制状态；非法 factor 走原 `-1018` 回复，未进入电源回调。[UPM 执行记录](upm-peer-results.json)

## 数值含义由原诊断函数复核

没有依据裸数值给电源状态命名。执行原 `k_upm_dump_power_status`，仅捕获其 `printk` 请求，三组结果确认：

| 字段 | 原值 | 原字符串 |
|---|---:|---|
| type | 1 | `PS_TYPE_ACV` |
| type | 2 | `PS_TYPE_BATTERY` |
| jack | 1 | `PS_AC_CONNECT_OK` |
| jack | 2 | `PS_AC_CONNECT_NG` |
| type／jack | `0xffffffff` | 对应 `UNKNOWN` 枚举 |

这说明所查 AP 直接放行分支要求“ACV 且插口连接正常”的缓存状态，不是绕过固件签名的机制。字符串与状态都是原代码的输出关系；当前机身的实际状态仍未读回。[原诊断执行](power-enum-results.json)

## 对完整目标的实际影响

本轮移除了离线链中“下一项服务回复是什么”的未知项，没有移除真实入口、动态装载或固件签名的门槛。原 FX3 机身 model 字段仍会在镜头类别检查处被拒；本轮使用的镜头类别与身份是合成夹具。这个准备成功码也没有验证整个 UFU 容器，更没有执行后续解包、启动或持久写入。

此前三份官方正常更新包的完整尾签名验证和改动反例继续有效；CRC、AES 重编码、准备成功、临时程序执行各自不能替代正常修改包的准入。用户要求的完整 FX5 专有菜单／功能、VENICE 私有实时 ISP、FX3 MAIN 像素绑定和可正常刷入的目标包，仍需各自独立证明。

本轮只读刷新了 [A7C II preload 作者研究](https://github.com/YuuLuo/a7c2-service-preload)：其说明仍将临时子进程执行与修改固件准入分开，适用范围为 ILCE-7CM2 2.01。没有执行其中的设备步骤，也不把它作为 FX3 回执。

接下来优先回到尚未恢复的正常拍摄 MAIN 色彩绑定和可取得的供体专有内容；这里的电源准备分支无需再靠扩大合成状态矩阵充当进展。真实设备会话与恢复证据继续由已有负责 agent 的独立材料约束，不在本任务中触碰设备。
