## 同一原调用现场继续到哪里

先运行原管理对象构造，明确提供主描述符与引用计数1的缓存记录。句柄和缓冲指针均为离线输入，**没有经过真实分配，不证明这些数值在机身上有效**。A5／C3两组旧存储填充值，各跑两种句柄标志。

原代码将最后引用减到0、清理缓存记录，暂停在`+0x27c1a8`释放函数入口。然后保留同一个Unicorn实例、寄存器、栈及RAM，从实际停点继续，没有补返回值、跳过服务或制造回复。

原函数首次运行原资源元数据构造，生成202条记录。它们的条目标志为0，只是元数据，不是202块已分配的硬件内存。随后原代码构造216字节请求、原内联消息、消息来源，进入原LIRO绑定的OSAL提供者：

| 本轮原请求字段 | 值或位置 |
| --- | --- |
| 首16位字段 | `0x23`，与此前申请请求的`0x20`区分 |
| 句柄 | 请求`+0x08`，保留声明的句柄数值 |
| 后部字段 | `+0x14`为`0x1111`，`+0x16`为2 |
| 内联消息 | 状态2、大小216、来源`0x806800f3` |

没有完成消息缓冲区申请、同步发送、回复、物理释放或外层返回。主描述符仍保留在暂停现场；源码、原Sony调用指令及模块节字节均核对，自编译适配器没有执行。

## 标志分支带来的额外依赖

原句柄bit15会设置通用命令的bit28，本轮观察如下。这里的地址和ID均属于离线模型，不能作为机身地址使用。

| 声明的句柄 | 原通用命令 | 最先进入的OSAL申请 |
| --- | --- | --- |
| `0x123a3cde`，bit15=0 | `0x8061003c` | 本请求216字节，client ID `0x3c`，等待参数1 |
| `0x123abcde`，bit15=1 | `0x9061003c` | 先走原诊断记录路径，申请52字节，命令`0x8f013a`，client ID `0x13a`，等待参数0 |

第二条路径在主释放消息发送前就依赖诊断消息申请。其client ID大于`0x3f`，原模块调用了另一段只读的稀疏查找代码，再进入另一把锁；本轮两把锁的模型对象相差`0x210`。因此，不能只覆盖低ID的直接缓存与主释放消息，便声称退出流程完整。

两条路径都在原内核`_raw_spin_lock_irqsave`第一条指令前停止。低ID缓存／高ID查找返回的空值来自未运行初始化的ELF零BSS；这不是机身故障证据，也不是可继续编造线程、锁或消息池的理由。原驱动初始化、IRQ／当前任务、分配器、诊断发送及主消息回复仍未通过。

## 独立通用回复检查

另起明确的独立片段输入，用原内联消息构造／设置函数提供本地数据，从原`+0x27bf28`执行到`+0x27bf68`，停在包装器清理和最终返回之前。**这些数据没有注入前面暂停的任何请求，也没有冒充真实同步回复。** 表中的结果是片段形成的W19状态，不是一次真实释放返回。

| 明确提供的本地内联数据 | 片段结果 |
| --- | --- |
| 216字节，标记`0x1111`、状态0 | 0 |
| 216字节，标记相同、正状态1 | 2 |
| 216字节，负状态`FFFF` | 1 |
| 216字节，标记改为`0x2222` | 1 |
| 仅8字节，标记`0x1111`、状态0，首字段为无关数值`BEEF` | 0 |
| 仅6字节，或状态2的空内联数据 | 1 |

原读取函数按实际内联长度与216的较小值复制，随后清理该消息的内联数据及状态／大小／来源；本地输出尾部沿用本轮明确提供的零值。原通用检查随后检查输出`+6`的标记与`+2`的有符号状态。它不是本轮已验证的请求关联、句柄回收或消费者完成通知。

**8字节确认可能正是协议允许的形式。** 本轮没有证明协议要求回复必须216字节，也没有证明端到端关联检查缺失、机身有漏洞或短回复有问题。下一步应查清各类确认的合法格式、关联和完成语义；不能仅为让检查更严格，就自行把请求长度当成回复长度要求。
