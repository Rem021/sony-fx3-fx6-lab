# FX3 原编码输入几何生成与通道选择

2026-10-25（本地日期）。本轮为离线原指令研究，未连接或修改相机。

**已在声明的通道记录输入上，接通原编码侧的几何生成步骤、原 builder 片段和原 VCD 基带/配置谓词。** 三个正向场景由原代码生成 1920×1080 几何，基带校验与配置校验均返回 0，不再直接补写 COMMON 来通过检查。真实通道记录的建立、当前 MAIN 通道、完整启动和硬件编码仍未验收。

## 新确认的原数据链

| 原步骤 | 字段/地址 | 本轮范围 |
|---|---|---|
| 元数据保存 | `0x246138` 复制 0x88 字节到组件 `+0x7a8` | 原 setter 完整返回 |
| 元数据取回 | `0x246144/0x24614c` 返回配置/元数据地址 | 原 getter 执行 |
| 数组与索引 | 元数据 `+0x18` 为数组指针；启动事件 `+0x14` 为索引 | 数组和索引值是明确的 RAM 输入 |
| 选择记录 | `0x24cf34` 按 `index * 0xd18` 计算地址 | 原计算及记录读取执行 |
| 几何打包 | 记录 `+0x3e/+0x40` → start-input `+0xe8/+0xea` | 原 `0x24cfb8..0x24d020` 打包执行 |
| 几何消费 | start-input `+0xe8/+0xea` → COMMON `+0xc/+0x10` | 原 builder 复制执行 |
| 消费端检查 | VCD `0x1a81cc` / `0x1a8594` | 原纯谓词完整返回 |

入口所属原源码文字为 `enc/imola_enc_state.cpp`。搜索中另找到同样写 `+0x3e/+0x40` 的 `0x23d964`，但它属于 `dec/imola_dec_state.cpp`；没有把该解码器片段用于主录输入。相似偏移本身不能证明同一对象或生产者。

初始 start-input 的两段 0x88 字节内容由原代码从描述符和元数据复制，几何与格式字段由选中记录的原打包器生成。元数据 `+0x6c=1`、两条通道记录、索引、对象身份等仍是声明的实验输入；没有把它们说成当前相机读回。质量仍沿用人工 quality24/FF 行 386，原 quality22/FH 未命中资源表的缺口保留。

COMMON 输入像素格式号 13/14 与 MAIN 流类型 14 是不同枚举。本轮只按原分支、数值与 pitch 描述格式输入号 5/6，没有据此验收实际传感器像素格式或编码位深。

合计 **76 段 A64 原片段和 6 次 MIPS 原谓词运行**。记录读取轨迹确认每个场景只读取选中的记录。正向结果保留私有数据预置的 target 字段 16,000,000；该私有副本仍是明确的主机数据输入，不是本轮新实现的相机原生补丁。stage49 已证明配置谓词不读取码率字，因此这些返回 0 仍不是 16 Mbps 硬件能力证明。

## 哪些环节还没有执行

原动作开头、几何转储和 builder 中仍有未执行的诊断；原默认查询 `0x22ba98`、标志/附加参数准备 `0x246274` 以及真正加锁的启动包装器 `0x22b358` 也未执行。后诊断片段在另一客体使用明确复制的内存、栈和保存寄存器作为输入，没有伪造日志/锁返回，也没有将分段结果合称完整启动动作。

本轮闭合的是“给定元数据图时，原编码侧怎样选择记录并生产几何，以及这些字节怎样进入消费端纯检查”。尚未闭合的内容包括：真实记录数组的生产与登记、MAIN 的当前索引、记录生命周期/配置代次、全部标志/默认值/额外参数、资源质量对齐、日志/共享锁、完整 VCD 启动、实际缓冲映射/通知/完成与异步引用归还。

原文件零槽只用于有限 owner 输入，本轮没有重新运行完整通用编码器构造；其构造与零初值证据沿用 stage48。三个正向场景也不能证明整组 start-input、完整请求或真实图像链已经有效。旧的最小输入及其 `0x3006` 结果保持不变。
