# FX3 缓存替换、等待集合与退出观察边界

本阶段明确了三项退出条件：刷新路径的一次虚函数调用不是完成凭据，刷新会保留旧请求token，原厂wait集合也不能直接解释成“要等待的任务”。原指令的局部对照已通过；**真实禁止入队、线程停止、完整wait、卸载和恢复均未实施。**

## 缓存刷新不等于旧对象已经退出

`sequence_get_media_remain` 的原虚表0x46e8000中，偏移0x20的目标是0x275d3d4，只有一条RET。两处原刷新片段实际经过此虚调用后返回，合成旧对象的标记、token和其它字节完全不变，客体没有内存写入。

后续路径还会分配新缓存、转移一个内部三指针容器、调用旧对象删除析构，再重绑列表节点。本阶段没有执行这些原生分配、完整转移、析构或并发流程，因此没有断言整个原厂替换机制不安全；仅确认该虚调用本身不提供取消、join或完成确认。

## 请求token不能当作配置代次

原token生成函数把任务类型放在高32位，将计数器的旧值放在低32位，并递增32位计数器。8个原算术片段对照覆盖两个类型值及计数边界；真实全局计数器、互斥锁和完整token API未运行，实验从原ADRP之后以合成计数页为前提进入。

实际刷新路径在删除旧对象前读取旧token，随后把同一token写入新对象。3组原元数据片段对照显示，新旧缓存标记即使不同，token仍可相同。两段之间的分配、构造、转移和删除未执行，不能将分段测试当成完整刷新验收。

因此它适合继续研究请求身份或关联关系，不能直接用作profile配置版本。新对象0x18字段来自原名称表，是任务名称指针，不是代码回调地址；这一绑定在片段结果中也核对了。

这里的内部任务类型113（0x71）由名称表绑定为 `sequence_get_media_remain`，映射到pool0。它与先前remote格式值113属于不同空间，也不是PTP属性或设备命令。

## 原查找和wait的判断范围

原查找函数先检查pool中的独立对象槽，再遍历排队列表。6个对照覆盖独立槽、空列表、单/多节点和二者同时存在；仅检查列表长度会漏掉独立槽中的对象。测试从假定已持有pool锁的位置开始，停在解锁前，没有执行真实锁或取得活体快照。

原 `sequence_manager::wait` 的判断也检查这两处。输入集合通过原32位hash-set查找函数解释；另用12组查找对照核对了合成容器，包括同bucket碰撞，没有用查找stub。

9个单pool原谓词对照包括：

| 独立槽 / 排队列表 | 输入集合 | 观察 |
|---|---|---|
| 均为空 | 空 | 该pool放行 |
| 媒体剩余时间对象 / 空列表 | 空 | 进入需要等待的分支 |
| 媒体剩余时间对象 / 空列表 | 包含该类型 | 该pool放行 |
| 空 / 仅一个媒体剩余时间对象 | 包含该类型 | 该pool放行 |
| 空 / 仅一个媒体剩余时间对象 | 空 | 进入需要等待的分支 |
| 媒体剩余时间对象 / 仍有排队对象 | 包含独立槽类型 | 进入原断言入口 |

因此不能把集合参数理解为“等待这些类型退出”。在上述条件下，命中集合反而允许该pool继续通过。摘要中的 `running_kind` 只是合成独立槽场景的命名；本阶段尚未把该槽与真实工作线程PC完整绑定，没有实际运行任何任务。

原wait循环覆盖29个pool，但本阶段只运行各自锁之间的判断片段，停在放行、准备等待或断言处。**单pool放行不代表完整wait返回，更不代表全应用、编码器或所有补丁调用点空闲。** 完整wait入口另作负例，在未建模的模型所有权帮助函数处停止，没有补原生锁/等待输出。

## 模型所有权与退出条件仍需统一

完整wait在前后调用模型所有权交接/重新取得帮助函数；原帮助函数包含交接或清除所有者、随后重新取得所有者的路径，期间还可能等待条件变量。因此退出流程不能仅依赖一次model_lock捕获结果，还要验证禁止新实验对象进入、等待期间配置是否改变，以及返回后对象/代次是否仍满足撤除消费者的条件。

原基础析构还会销毁条件变量。C++工作草案把“没有线程仍阻塞于该条件变量”作为析构前提，不能把析构本身当作任务全部结束的保证。[C++工作草案原文](https://eel.is/c++draft/thread.condition.condvar)（2026-10-25读取）。这用于解释通用约束，不代替Sony实际线程和运行库验收。

当前可复核的退出要求是：

1. 找到并封闭所有新profile请求/缓存生成入口，确认实际录制处于允许退出的状态。
2. 在相应同步条件下观察相关独立槽、排队对象、标记缓存、局部输入包和实际调用点，确认它们均不再依赖实验消费者。
3. 使用经过验证的等待集合与范围，等待后重新核对配置身份和对象状态；不能用请求token相同代替配置一致。
4. 重新生成合法原厂副本后，才通过受限恢复器恢复原代码，并完成原字节回读、WBI/冷启动和对应录制验证。

这些是由本阶段证据收紧的条件，尚无实机执行器或验收。独立槽与工作线程的关系、全体补丁消费者、原生wait、异常/锁竞争路径和在途观察器均未闭合。同机健康备份、模块加载/退出、独立恢复入口以及实际MAIN成片/音画同步/长录目标保持未完成。
