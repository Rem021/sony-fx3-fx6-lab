2026-10-27。**本轮将阶段108的独立 `SetGlobalMsg` 试验细化为原 `ReceiveASync` 接收后路径：它直接读取 OSAL 元数据、复制并分类消息，不调用该 setter。同步回复还需要事件匹配，释放消息本身不证明外部 Open 参数区可以复用。** 全程只在 Mac 上分析已保存的官方固件样本，没有 Windows、UU、相机或卡内文件操作。

正式结果：[osal-envelope-results.json](run-native-callback-boundary-20261027/osal-envelope-results.json)。12组接收条件、4组发送期待参数、12组声明回复，共74个有界阶段。目标仍是 MAIN 1920×1080、30000/1001 fps、HEVC 4:2:0 10-bit约16 Mbps；精确30.000 fps单独验证。未达到实机主录或安全刷入标准。

## 接收端原路径

从既有并重新校验的 `nflasha15.img` 只读提取原用户态 `libosal_uipc.so`，SHA-256 `09ebf5980237fc473077dc844763dcb00cba423f431646e3be7c0ca49ea70ff3`。这份用户态库与阶段64使用的内核 `.ko` 是不同对象；本轮没有装载它们，也没有执行接收、发送、释放或内核服务。

原用户态导出函数给出：消息数据指针`P`之前，`P-0x0c`是来源u32、`P-8`是长度u32。原 `osal_set_msg_src`、`osal_get_msg_src`、`osal_msg_size` 在 guest 中执行了真实读写指令。导入按原符号名称绑定到该同固件库候选，不能据此确认活动进程的实际符号解析。声明封装其余字段不被当作实际分配器输出。

MPR原发送代码显式设置来源`0x80c70047`，目的队列`0x8055001f`。这两个代码常量用于本轮条件，不等于已经注册或连接到相机队列。

原 Dataflow `ReceiveASync` 从完整入口执行到 OSAL接收前停止；下一阶段独立声明封装指针和错误输入0，再执行原错误翻译、来源／长度读取、`memcpy`和分类，停止于消息释放前。没有伪造接收成功返回。之后的 `GetMsg` 也是独立阶段，未把未执行的释放及栈展开视为已经完成。

| 声明条件 | 原代码结果 | 使用范围 |
| --- | --- | --- |
| 阶段108完整48字节头，原发送来源 | 复制48字节，raw状态2，存储长度48；原GetMsg取出完整头并清理消息对象 | 4组；未建立真实队列接收与释放 |
| 长度16 | 复制16字节，状态2；GetMsg请求48仍只复制16、返回0，目的尾部保持旧填充值 | 2组人工完整性对照，不交给AV解引用 |
| 长度400 | 原代码将复制及raw存储长度限制到384 | 2组容量对照，未交给GetMsg或编码消费者 |
| 人工`0xa0a0a0a0`标记、非public来源`0x00550001` | 走结构化状态1 | 2组分类对照，不当成合法的结构化消息或送往后续消费者 |
| 同标记、特殊来源`0x00c00695` | 特殊来源分支优先，仍走raw状态2 | 2组人工来源分类对照，不归因于真实FX3消息流 |

本轮未调用 `SetGlobalMsg`。阶段108的该函数结果仍在其原范围内有效，但不能再把它当作已验证的真实接收入口。消息对象清理的是其内联消息头；外部raw98参数区仍通过头内指针引用。

## 发送期待与同步回复

原发送函数在复制消息头后，有两种期待参数分支。本轮使用原头的消息ID`0x210`、子码0：调用者给出回复存储指针时，原 `GetExpEvt` 生成事件`0x1001`；未给出指针时选择事件1及发送栈内存储。执行停止于原期待事件全局写入前，没有提交或发送任何消息，也没有认定当前真实调用者采用其中哪一支。

回复实验独立声明期待事件全局值及回复存储地址，再执行原 `ConvertAvconEvent`、`GetExpectedCodecEvent` 和 `CallbackFromAvbbc`。回复包是人工模板，未证明实际AV会产生这些包。

| 声明回复与期待 | 原路径观察 |
| --- | --- |
| 回复ID`0x4e0`、子码1；期待`0x1001` | 原事件匹配后走同步互斥锁；独立锁后段将原48字节回复复制到声明期待存储，再停止于把期待改为2／指针置空的原调用前 |
| 回复ID`0x4e0`、子码2；期待1 | 同样进入同步回复复制 |
| 子码1但期待`0x1003`，或期待保留值2 | 此声明格式下走录像回调分支，停止在未绑定的间接调用之前，不当成完成的同步回复 |
| 人工格式字段`0x44`且期待不匹配 | 走另一事件队列分支，停止在其互斥锁前；不执行队列操作 |
| 人工未知回复ID | 原转换为2，直接走消息释放分支，释放本身仍未执行 |

初次运行未把录像回调的间接调用设为停止边界，错误地预期所有不匹配事件都走队列；该声明回调指针为零，仿真在PC0结束且没有通过结果。失败回执和当时源码保留。核对原格式分支后，正式运行在`0x2859e8`调用之前停止，没有补写回调目标或返回值。

## 固定参数区的寿命仍未闭合

原发送函数设置期待后取互斥锁、发送，再调用 `pthread_cond_wait`；该函数内没有显式定时等待参数，外层watchdog／取消尚未核对。[Linux man-pages](https://man7.org/linux/man-pages/man3/pthread_cond_wait.3.html)说明条件等待会在等待期间释放互斥锁、返回前重新取得。这里仅引用通用接口语义，未执行Sony的线程库或验证真实调度。

原回调匹配段在复制回复后准备清除期待并发条件信号。不能因此把“某个消息释放”“函数返回”或“出现信号”当作完整的编码配置确认。仍需核对实际事件身份、内容、实例／代次、外层串行化、调用者等待状态和固定raw98区的有效期。当前证据不足以指称相机存在竞态，也不足以保证跨等待期间可安全复用该区。
