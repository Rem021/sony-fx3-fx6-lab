# FX3 DMM 默认参数、BK4 双记录与原换算入口（2026-10-29）

**仍无可正常刷入的 FX5/VENICE 整套替换固件。** 本轮从官方模板取得此前缺失的参数 `0xfa0182` 原值，并让原 CP 查询／换算代码导出配置源的候选地址 `0x09a08e00`。没有真实配置复制、缓冲分配、MAIN 像素、完整供体 ISP 或修改整包准入。

上轮 [CP 配置解析封存](../dmm-config-20261029/README.md) 的 27 个文件逐项校验通过，属于有新证据的 progress。外盘 UUID 核对为 `F9404A58-A1C4-409F-8E78-9A6B7EEB3F7B`；原件、旧封存及另一 agent 的 HEVC／USB／恢复工作不变。全程只读官方原件和有界 Unicorn RAM，不操作机身、USB、手机、真实 IPC 或原生 Sony 程序。

## 官方模板中的两段 BK4

输入为已固定 SHA 的 `fx3-7.02-decrypted.fdat`（808,704,512 字节，SHA `694c4e9ea53bce6785521078bcb5728068e6ef3da8f0f052ff5ce23b1cb2b768`）。核对所选 tar 头的名称、类型、长度及校验和，并按原 `backup.sum` 复核全部 **22 份默认模板的大小及 CRC32**。

每份模板包含两段 `BK4` 记录，两段各自的数据边界和按字节求和校验均成立，共 **44 段**。该格式另与[维护者的 BK4 解析实现](https://raw.githubusercontent.com/ma1co/Sony-PMCA-RE/master/pmca/backup/__init__.py)交叉参考：六字节属性项、数据边界、跳过头部 `0x20..0x23` 的校验计算。核心依据仍为官方字节和原 CP 解析指令；没有运行 PMCA、社区设备程序或签名工具。

22 份模板中，本轮三个目标参数的原值均一致：

| 模板内记录 | `0xfa0182`，8 字节 | `0xfa0183`，8 字节 | `0xfa0184`，4 字节 |
| --- | --- | --- | --- |
| 第一段，文件偏移 `0` | `0x4110c4000` | `0x19000` | `0` |
| 第二段，文件偏移 `0xd2000` | `0x809a08e00` | `0x19000` | `0` |

因此仅取模板的第一段会丢失一个重要候选，不能把第一段查到的地址当作 CP 实机值。第二段与 CP 地址域相符仍不能单凭这一点给两段定为 AP／CP，或证明正常启动选择了第二段。

为原指令实验保存了 `CX95900_ALLLANG.bin` 的两段原记录，分别为 857,900 和 1,369,580 字节，原头、数据和校验不改。这个选取只是统一实验输入，**不是确认用户机身地区、型号变体或启动选择**。本轮没有读取或修改用户机身备份，也未搜索／提取私有签名密钥。

## 原查询与换算：不再使用文件读取适配器

CP 原件 SHA 为 `c90d00d807874a5309dc1b65b203287e83608ceee513cc57b53409333fb6bcba`；以下 CP VA = 文件偏移 + `0x108000`。

分别把两段原 `BK4` 记录作为明确输入放到模拟 RAM `0x04000000`。原 `0x4985c4` 建立参数表；原 `0xa85174/0xa8520a/0xa8523e` 查到原属性项、长度 8 和数据指针，全部与独立宿主解析吻合。属性值来自原记录，不由钩子提供。

随后进入原 `dmm_module_GetConfigData`（`0x4d7a84`）：

- **严格路径，各记录一例**：均停在原 `0x52ee34` 备份互斥锁第一条指令前。没有提供内核、CPU 上下文或锁返回，也未完成 DMM 参数查询。
- **明确互斥锁环境适配，各记录一例**：仅把原备份互斥锁进入／退出声明为返回 0，原 `0xa84be8` 内的参数查询、8 字节载入及 `0xb54930` 区间换算执行。第一段没有匹配区间，停在原诊断 `0x1500c0` 前；第二段得到 `R0=0x09a08e00`，停在原内存属性校验 `0x53894c` 前。

共 **4 组**。与上轮不同，这里没有进入顺序文件读取适配器，也没有在候选地址放入 `DmmCfg.bin` 或为内存属性返回“成功”。正例仅走到原指针校验入口，不能称为已读到正常配置或已发出一次成功申请。

## 布局对应与独立缺口

从同一官方 FAT 分区读取的原 `tomco.txt` 包含：

```
snapshotdbg_addr=0x09A21E00
memcfg=0x7000000@0x09000000:uc
```

原第二段参数换算得到的候选地址加相邻值满足：

```
0x09a08e00 + 0x19000 = 0x09a21e00
```

该范围也落在上述未缓存区域声明内。这支持它是一处预留配置区的**布局推断**；本轮未找到 `0xfa0183` 的专门消费者，容量含义尚待证实。上轮 43,320 字节 CP 文件可以放入该范围，但“能放下”不能证明文件来源或装载；另一份 AP 配置也能放下。

原 `0x53894c → 0x54bbd0 → 0x554ebc` 会查询 `0x14007c8` 指向的软件 MMU 表和属性后才接受指针。该路径已静态封存，但没有当前表内容、正常初始化或映射成功结果。

重核原 WBI 的 SHA 和 1,399 条保存记录，两段默认参数地址都没有被任何记录覆盖；没有用 AP WBI 补造 CP 配置内存。两段模板如何选取／复制到 CP 主备份、`DmmCfg.bin` 如何装入候选区，以及机身当前参数仍未证明。
