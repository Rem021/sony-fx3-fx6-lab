# FX3 存活会话全局监管：离线入口原型

2026-10-30；经典ILME-FX3 7.02；Mac普通用户进程、自写ARM64与假Linux内核，不操作相机。

**实现并验证了一个串行启动读取工作器的存活监管入口：10项主测试与2项结果边界测试通过。通过该入口的不同采集请求不能重叠，阻塞、超时或不完整完成证据会保留UNKNOWN。** 同一个正常存活会话仍可完成boot0和boot1各四个窗口，未缩成只读第一个窗口。

这是后续机内监管的离线原型；**第219轮ARM64模块本体未修改，直接调用它时的全局并发缺口仍在。** 当前没有相机传输、上传、认证、安装或机内监管后端。不能将本原型当成已经修好的可刷固件。

## 为什么采用存活监管

复核了[第194轮全局占用实现](../stage194-supervised-fixed-launch/global_guard.c)：它已明确进程死亡不能充归还回执，`flock`之外还要保留未完成状态。[Linux flock说明](https://man7.org/linux/man-pages/man2/flock.2.html)也说明锁可随最后一个相关描述符关闭而释放。因此本轮沿用“存活所有者、私有完成、异常保持占用”的原则；没有把Mac C／CommonCrypto实现直接当作相机Linux组件。

[live_arbiter.py](live_arbiter.py)只在新的离线目录中原子建立会话目录与独占占用文件。文件始终保留，不删除、不解析为重启授权；即使上一次成功，退出后的新监管器也拒绝接替原目录。文件不冒充可信持久恢复检查点。

一次正常存活会话在内存中维护`IDLE → RUNNING → IDLE`；异常进入不可自动恢复的`HELD_UNKNOWN`。新任务只由原监管器的私有状态放行，须同时满足：

1. 工作器来自本轮明确的离线启动路径，实际`Popen`句柄正常退出0。
2. 直接继承的私有socket收到唯一、完整、匹配会话／nonce／请求SHA／模块SHA／PID的完成消息，并到达干净EOF。
3. 工作器实际返回0，假内核文件描述符检查通过，没有额外或重复消息。
4. 既有独立启动区解码器核对输出的请求、容量、窗口、CRC／SHA及本轮合成源的全部预期字节。
5. 占用文件身份及内容未改变，当前检查仍在期限内。

stdout、公开完成JSON、磁盘记录、“PID已不存在”以及完成消息单独到达，都不能恢复IDLE。超时不强杀、重置或重启；人工测试接口只释放本轮自建阻塞。迟到的正常退出不会解除已进入的UNKNOWN。

## 实测范围与结果

[主测试](runs-final/receipt/results.json)10项通过，20个真实普通Mac子进程各运行自写ARM64模块与假Linux环境；另2个真实进程争抢同一会话目录，仅一个成功，结束后新所有者仍被拒绝。

- 正常存活会话依次完成boot0、boot1各4窗口，每个启动区33,423,360字节，块数均为128／128／128／126。两份完整组装SHA均为`0bf7d4c932dc8a583aa5101bad7c8e7a8d6191c15c54479847c83b62434cc625`。这是同一人工源用于两种启动区角色的测试，不是两份真实相机备份。
- 已确认第一个实际子进程仍活着且自建源读取阻塞时，不同采集ID的新任务被拒绝，第二个工作器没有创建。协作释放后第一个返回23，监管状态继续UNKNOWN。
- 完成消息已经到达但子进程仍活着时，继续拒绝新任务；正常退出并通过独立输出验证后才可顺序启动不同采集请求。
- 非0退出、退出0却没有私有完成、收到完成后再非0退出、错误nonce／模块SHA、重复完成帧、超时和占用文件改动，均保持UNKNOWN。
- 部分会话记录及监管器退出后的原目录不可自动恢复；实际两个所有者进程的竞争与退出已检查，不用文件里记录的PID代替句柄观察。

[追加边界测试](runs-boundaries/receipt/results.json)2项通过，另3个真实普通Mac工作器：同窗口重放返回51且零源读取，监管器保持UNKNOWN；成功私有消息到达后改坏一块输出，再正常退出，也被独立CRC核对拒绝。最终验收共12项、23个ARM64模型子进程及2个所有者竞争进程；不重计第219轮50案例或旧0.5测试。

首轮10项中9项通过，占用文件改动案例发现观察逻辑提前返回，未继续收取已退出原子进程的EOF。修正为“保持UNKNOWN，同时继续观察同一句柄和私有通道”，并去重错误记录。首轮失败回执与4份当时源码保留，未删除或重启那个工作器；最终主测试及追加检查均通过。

## 尚未证明的部分

实际文件独占创建、私有socket继承、子进程启动／退出与竞争发生在Mac普通用户环境。root／proc／设备路径、Linux syscall、时钟、驱动配置及源读取均由第219轮假内核提供；Sony原件只参与数据哈希，没有执行Sony程序、Linux内核、glibc或Sony装载器。

本轮没有证明root跨UID隔离、可信程序装载、相机实际父im、机内IPC或受保护固定路径。可写测试目录在对抗性删除／替换下不构成可信全局资源域；相机root私有路径与同机身份仍需实现和验证。模块文件SHA和私有测试子进程握手不能替代完整代码／权限认证。[fsync说明](https://man7.org/linux/man-pages/man2/fsync.2.html)也不能使RAM记录跨重启持久保留。

下一步把本轮状态机、私有完成条件和失败保持占用语义移植为自写Linux ARM64候选，并在假内核中强制所有受控读取经同一入口；目标模块的直接旁路必须关闭，不能仅依赖用户手工选择监管器。仍先离线构建，不上传或触发原日期命令。

正式0.4／0.5包与23源码、全部16项需求和既有授权保持；195仅主机root01仍未具体批准、未启动。真实同机备份、数据视图／访问归还、独立AP救砖、逆写／冷启动及MAIN1080p29.97 HEVC／长录尚未验收，exact30单列。目标active，持久刷写未放行。
