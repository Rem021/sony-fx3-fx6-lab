**本轮把原生owner查找、码率查询结果和完整的启动参数准备函数接到同一离线客体。** 结果进一步说明：只核对预置中的16M还不够，启动时还会准备独立的QoS调整块。实际下游怎样合并、硬件最终采用什么值仍未验证。

这轮没有修改C原型，也没有生成可刷固件或机身装载模块。原Open请求保持挂起；独立调用使用另一块栈。组件状态和可选设置是明确的试验输入，不是当前相机状态或真实MAIN对象读回。相机、Windows和UU均未操作。

## 八组结果

以下四种输入各用A5／C3两种旧值运行，共44段有界执行：

| 明确的组件/设置输入 | 原启动头前5字节 | 原QoS输出 |
| --- | --- | --- |
| 可选参数未启用 | `00 01 00 02 00` | 更新掩码0，无目标调整 |
| 启用目标16M | `00 01 01 02 00` | 掩码`80`，编码目标16,000,000 |
| 启用目标20M对照 | `00 01 01 02 00` | 掩码`80`，编码目标20,000,000；所选预置仍16M |
| 只启用尾部字段复制选项 | `00 01 01 02 00` | 掩码`100`；查询`+2c/+30`复制到QoS块`+1e/+20`，值8008／240000 |

上述掩码是十六进制。函数返回1仅说明这个参数准备helper的本次执行结果，不能当作硬件Start成功。20M是用于区分两条参数来源的控制输入，不是拟采用的目标值，也未证明它在真实相机上覆盖预置。

`240000 / 8008 = 30000 / 1001`是精确数值关系。因此这组字段与目标29.97相符；字段正式语义、下游单位/缩放以及硬件时序仍须继续核对，不能据此验收29.97成片，更没有证明精确30.000支持。

## 实际启动链中的位置

原`24ce04`准备栈上start-input，并清零独立的128字节QoS块和768字节另一参数块。`24ce94..24cebc`调用带锁查询`22ba98`及本轮已运行的`246274`。原查询结果存放于栈`+80`，start-input从`+b8`开始，两者间有56字节空间；未把旧自写适配器的24字节错误套在这个原调用者上。

`22ba98`本身需要原同步守卫，本轮没有执行或替代其锁。运行的是其下层查询入口，属于独立试验，不是一次自然的完整启动动作或已证明合法的重入。

静态原分支继续为`22b358 → 230470 → 228abc → 21f7f4`。原Start主体先生成/复制64字节公共块与448字节codec块，再分别复制128字节和768字节其它参数块。由此不能把QoS块直接说成448字节codec块已经被改写；它们是不同来源/大小的提交参数，后续实际消费和优先顺序仍未闭合。此链和复制顺序仅作原字节静态证据，本轮未执行完整Start、这些池复制或发送。

完整QoS helper还执行了待处理区的清理调用；没有因此宣称实际申请成功、提交完成、重试安全或所有消费者退出。真实配置代次、策略消息与启动间的共享同步仍是缺口。
