## 修改包准入不能由重打包替代

本轮对三份原 FX3 包重新计算完整 SHA，与既有签名实验的输入一致；官方公钥文件摘要也一致，因而复用已封存的原验证结果，没有重复运行已通过的原指令实验。

有效的后续证据是 `input-20261028/official-key-rsa-verification-results.json`：原7.02／2.04／2.05均对应 RSA2048/SHA256，覆盖密文主体加16字节 IV；保留旧签名的12个单字节修改对照均未通过。另有独立 OpenSSL 原7.02结果：包含 IV 通过，去掉 IV 失败。更早 tail 阶段用候选快照公钥／SHA512 的未命中结果已被后续正确公钥结果取代，不用旧阴性结果推导签名机制。

这证明已检查的真实性条件，**不证明已经发现适用于7.02的全部准入分支，也不证明任何可能方案都不成立**。当前事实是：解密、改字节、重算 CRC 或重新加密，没有给出新的有效签名或一条已验证的修改包准入路径。本任务不搜索／推导签名私钥，不生成签名，也不借另一 agent 的设备后端试探。

- [fwtool](https://github.com/ma1co/fwtool.py)：当前入口有 PE、DAT、FDAT、Msfirm、ASH、DSLR、分区表、bootloader、WBI 分支；没有取得专门处理本地 VENICE `DATA23213` type3/type4 的已核验读取器。只检查了所列入口，不据此声称整个仓库或全网绝无相关代码。

此前实际提取的 SNC 工具仍只验证了它自己的 SVU 头分支；五份 VENICE 前缀在该特定分支拒绝，不能把这个局部结果扩大为所有专业更新工具都不支持。原 VENICE V2.01/V6.30 内层未解开的结果也保持不变。
