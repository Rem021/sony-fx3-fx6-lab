# FX3 原厂im子进程回收与加载ABI核对

2026-10-30；经典ILME-FX3 7.02；Mac静态原件分析及自写ARM64模型探针。无相机操作。

**找到了第224轮不能直接当作机内可用方案的具体原因：参考im有自己的普通子进程回收器，而且原厂加载入口没有建立我们所需的四参数调用合同。** 本轮补6段原始字节、8处独立BL/PLT核对和2组新的自写ARM64时序探针。它们改变下一步架构，不构成真机启动、备份、救砖或首次刷写通过。

## 原厂回收器会竞争退出状态

[原始字节记录](im-loader-and-reaper-audit.json)重新核对参考`im.elf`的完整40,920字节SHA256 `5171f576d8b76cfbf15581389183b390c445bd6ff9dd97fd6668c5f64e77dc91`，与第183和218轮保存原件一致。来源是已保存官方7.02镜像nflasha15/inode80972，不是本机相机当前内存或文件读回。

| 原件地址 | 原始行为 |
|---|---|
| `0x4024cc–0x4024d8` | main准备signal=17、处理器地址`0x402f4c`，调用signal PLT |
| `0x402f54–0x402f60` | 准备状态指针、options=1、PID=-1，调用waitpid PLT |
| `0x402f64–0x402f68` | 返回PID大于0时跳回继续回收 |

即参考main注册SIGCHLD处理器，处理器循环`waitpid(-1, &status, WNOHANG)`。对完整.text按4字节扫描指向waitpid PLT的BL形态字，只有`0x402f60`一处；这不排除依赖库、间接调用或运行时替换。实际机内是否仍安装该处理器、执行时序和竞争概率没有观察。

第224轮创建的是SIGCHLD普通子进程，自己的父端通过`wait4(指定PID, …, WNOHANG)`取得退出证明。若原厂回收器先取得这个状态，后一次wait4不能重新取得它。PID消失、公开文件或DONE消息不能替代被取走的退出证明。

[新反例探针](probe-first/receipt/reaper-probe.json)重新使用第224轮相同的父端二进制SHA `c3e1d45b55fb8c4c228e7fe4b78cbe702ef81fcd2406f882fe374310198c93dd`及未改的第223轮子端：

| 明确模型时序 | 子端返回/原退出状态 | 父端wait结果 | 最后状态 |
|---|---|---|---|
| 无其它回收者的基线 | 0 / 0 | 指定子PID | IDLE |
| 模型原厂回收器先取走状态 | 0 / 0 | -10，ECHILD | HELD/UNKNOWN |

两组均实际执行自己的ARM64父端、clone后的自写子分支及静态工作程序；源读取都是两块人工数据，READY/DONE都到达。第二组不会重新放行原父端，也不能由新的父实例接替固定会话。所有自写线程终止。原厂处理器本身和Linux内核没有执行；抢先回收是依据原件建立的显式模型时序，不是实机发生记录。

这是**可用性缺口且保持拒绝的反例**，没有发现该候选错误释放。第224轮20组正常模型场景仍保留，其覆盖范围不能推广到真实im回收行为。

## 不能只改clone信号或换等待标志

[Linux4.9原始源码](source-reference/exit.c)的`eligible_child`按`exit_signal`与`__WCLONE`选择普通/clone子进程，`__WALL`或ptrace另行放宽。`wait.h`定义`__WCLONE=0x80000000`。但[exec.c](source-reference/exec.c)的`de_thread`在`no_thread_group`处明确把`tsk->exit_signal`重置为SIGCHLD，普通单线程exec也经过该处。

因此，clone时信号设为0，再exec静态工作程序，并不能使它持续避开im的普通回收器；若自己的wait4还坚持`__WCLONE`，反而不再匹配exec后的普通子进程。[Linux execve手册](https://man7.org/linux/man-pages/man2/execve.2.html)也明确列出该重置。这不是一个可直接采用的修复，本轮没有修改clone标志、原厂信号处理或机内代码。

源码来自Linux维护者的v4.9参考树，保存长度/SHA和行范围；不假定Sony4.9.337没有任何修改，更不替代真实内核观察。[源码捕获](kernel-source-capture.json)

## 原厂加载器仍需要入口适配

原`im`的`0x405e24`路线从描述符取文件及符号，dlopen/dlsym后，在`0x405f34–0x405f44`从描述符`+0x38/+0x40`选择一个值放入x0，再间接调用符号。另一条`0x405f5c`路线可选择`/usr/lib/libObj.so`或描述符路径，`0x40602c`间接调用符号前，也没有构造我们所需的handoff、request、child、fd四参数合同。

这些指令证明存在描述符驱动的库/符号调用，不能证明USB请求可指定任意RAM路径、任意符号及完整参数，也不能证明调用发生在主线程。新的父端submit四参数需要明确适配；只把其函数名交给dlsym不够。构造函数仍只写内存，不能自动替代submit/poll。

已排除的固定Jiritsu路径、TERM_MODE和日期shell触发结论不变；不为进入本模块而改IMDB、替换原厂信号处理器、忽略加载错误或放宽身份检查。

## 后续实现方向

下一项是自写的独立看护进程：原厂im只负责一个经明确适配的启动交接；看护进程在自己的地址空间中设置并核对自己的子进程/信号政策，再创建和等待工作程序，持有原全局会话及私有完成通道。原厂waitpid默认只回收其直接子进程，不会在看护进程正常存活时直接回收其工作子进程；孤儿收养、ptrace和其他特殊等待仍需明确处理。

这尚未实现，不能只增加一层fork就宣称完成。特别是第223轮工作程序仍固定核对父执行文件为40,920字节im；若新看护进程exec自己的ELF，该条件会拒绝。必须版本化父身份与镜像绑定合同、绑定主机固定任务/程序哈希和私有通道，防止简单删除旧检查或引入父子镜像互相内嵌SHA的循环依赖。新的入口适配也必须保持显式调用与初始化无设备动作，不能由dlopen成功推断获准工作。

看护进程异常退出、完成通道缺项、退出被其它waiter取走或读调用阻塞，均继续保留UNKNOWN；不得通过公开JSON、PID消失或超时回收来恢复授权。下一阶段先实现这些自写组件与假对象联测，不包含实际认证/上传/加载或相机程序执行。
