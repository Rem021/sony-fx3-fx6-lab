# FX3：原始失败分支与 Close 的条件（2026-10-26）

本轮在 Mac 上追完了原目标 FH 请求的“没有匹配行”分支，并补查显式 Close 的局部释放路径。**失败返回、消息回调、资源归还和可安全重试仍是不同的步骤。** 两组旧值输入都在 Close 时进入尚未执行的存储释放入口；与原文件静态区域初值一致的全零对照，才完成本轮局部 ID／handler／map-node 归还。这不是实机冷启动、修改后回退或救砖证明。

用户已明确 Windows 暂时不可用，先只用 Mac。该指令到达后没有再访问 UU／Windows；此前传好的参数审计任务保留为延后材料，未观察到提交或执行，不再要求当前代发。完整目标仍进行中，未暂停整个研究。

## 原始失败请求走到了哪里

本轮恢复了原 matcher 和通道准备两处 BL 的原指令；映射中的两个自编译适配器均未进入，私有16M写入器未执行。原函数仍使用已声明的局部 RAM、原管理对象／factory 构造、队列、外部请求和静音 logger 输入；没有把它当作真实 Linux 启动。

原请求匹配返回 −1，沿两次原诊断进入共同失败尾部。原代码写入通道 sentinel `FF`，经原 common 尾声返回到 factory；factory 的32位返回值为0，最后停在外部消息虚调用前。这里的0不直接命名为协议成功，`FF`也不代表所有资源已经归还。

在回调前，dispatcher 请求队列计数已是0，但原先8／6／6的 ID、MAIN handler、MAIN map-node 空闲数仍为7／5／5，注册树仍引用借出的 handler。外部消息头是已声明的部分输入，首虚表指针没有绑定；没有执行回调、确认通知、完整错误传播或合法重试，因而不能由“队列空了”推断请求生命周期结束。

原文件的诊断文字分别为 `not found CreateCh Table` 和 `expect enc_close`。其对应原字符串及调用分支已逐字节保存、核对。这支持“还存在显式 Close 路径”的分析方向；不能单凭日志判定真实相机泄漏。

## 显式 Close 的受限检查

在失败请求的暂停状态上，另用独立客体栈调用原 factory Close `+0x2277b4`，键来自原注册树。原 lookup 找到同一 common；原虚调用实际指向原 common Close `+0x21f048`。这是明确的独立入口试验，**不是已收到真实 Close 消息，也没有在独立释放后恢复原先暂停的 Open**。

| 初始存储条件 | 原 Close 实际结果 | 可支持的结论 |
| --- | --- | --- |
| A5旧值 | 五个资源ID均为 `FFFFFFFF`，仍带着A5形状的 `+0x1040/+0x1048` 字段到原 `+0x22da80`，在入口前停止 | 仅检查ID sentinel 不足以覆盖另一组缓冲区状态 |
| C3旧值 | 同样到存储释放入口，实参随C3输入变化；函数体未执行 | 未核实来源的指针没有被清零、释放或补成成功 |
| 与原文件对应静态区域相同的全零输入 | 原 Close 返回0，ID／handler／map-node 空闲数回到8／6／6，注册树为空；原再查询返回null | 在该明确初值及局部对象条件下，原归还路径可运行 |

全零输入下还检查了8个空闲ID、6个handler、6个map-node的唯一性，避免只看计数；没有执行第二次完整 Close。原 lookup 已返回null，后续调用是否具备检查仍需追踪。两个旧值输入均在原存储释放函数第一条指令前停止，未给它提供释放结果或替换指针。

## 零值的来源与适用范围

本轮重新核对原静态调用链的地址计算：`0x541b20 + 0x20a80 + 0x390 = 0x562930`。原 av-cam 文件在该 factory 区域的668,848字节全部为零，六个 common 槽的 `+0x1040..+0x104f` 也全部为零；每段长度、偏移和SHA256独立复核。原文件初值与本轮零输入一致。

这提供了**文件初始存储**的证据，尚未证明实际 LIRO 文件装载、WBI保留／重载、真实当前槽位、复用对象、所有缓冲区生产者或共享同步。不能用零输入的通过结果覆盖旧值分支，更不能把它当作已修改16M运行时的恢复。两个旧值输入也不是从相机采集的内存，不构成实机缺陷报告。
