## 原调用者比null回复指针试验更具体

原 `ExecEncOpen` 在`0xd18d8`建立栈帧，以原指令取`FP+0x60`作为48字节回复区，并在日志后将其清零。单流调用块`0xd1ba4..0xd1bbc`原指令传给 `Codec::EncOpen` 的参数为：

| 参数 | 本轮原指令结果 |
| --- | --- |
| Open参数指针 | `FP+0x90` |
| CodecType | `0x20` |
| FileFormat | 从exec`+0x77c`读取；本轮声明为15 |
| count／ViewId | 1／0 |
| 回复区 | `FP+0x60`，非空 |

这将阶段110的“有回复指针”分支落实到单流原调用者：在此前原消息ID`0x210`／子码0条件下，原期待为`0x1001`。旧目标fixture中显式给出的null回复指针并不是这个调用分支的证明；旧结果只保留其声明输入范围。

本轮没有执行实际日志、锁、DMM操作、参数构建器或 `Codec::EncOpen`。原代码在`0xd1b74`先调用normalLock解锁，再进入Open参数准备；该局部锁不能单独证明固定参数区在整个Open事务内串行。实际外层工作队列、同一调用者／实例及其它锁仍待核对。声明格式15也没有解决原上游自然MAIN缺VPC6的问题。

## 原回复生成与发送前封装

原 `InfraMovieEncoderSeqEncOpenAstra::ExecErrorCommand` 清零回复存储后，通过参数`0x100b`的Getter取状态。本轮在该未绑定虚调用之前停止；之后独立声明状态0／2，原指令生成：

- MID`0x4e0`、子码1、状态字段`+0x14`、CodecType字段`+0x18`。
- 传给 `InfraAvbbcMsgManager::OsalSndMsg` 的长度为`0x2c`，即44字节。
- 原Manager调用原 `SetGlobalMsg`，用同固件原libc复制44字节，建立Dataflow raw状态2、长度44。
- 原源ID转换和hook函数执行后，在日志入口停止；独立日志后段进入原 `SendASync`，请求向`0x80c70047`分配44字节，来源为声明Manager ID`0x8055001f`，再停止于OSAL分配之前。

上述0／2是独立状态输入，不能当作真实Getter返回、硬件结果或已执行的错误处理事务。Getter、日志、分配与发送没有被替换成成功。

## Ack与Comp的原字段处理

本轮用ErrorCommand原指令产出的44字节作为明确的独立模板，放进56字节AV存储（8字节前缀＋44字节数据＋4字节声明尾部），再执行原Ack／Comp方法。**这没有证明正常MC后端给这些方法生成输入的完整路径。**

原 `SetParameter` 的构造参数块确实把Ack对象配置为：等待子码`0x8502`、发送子码0、发送标志1。对象构造期间的日志键查找依赖尚未绑定的容器；本轮在查找前停止，构造器后段以独立日志键0输入运行，不伪造查找结果。Comp对象也采用同一明确边界。

| 原方法／输入 | 回复前字段 | 原MPR转换结果 |
| --- | --- | --- |
| Ack ExecCmd，模板MID`0x4e0`／子码1 | 原代码将子码改为构造字段0；发送44字节 | 事件1 |
| Comp ExecCmd，同模板 | 保留子码1；发送44字节 | 事件`0x1001` |
| ErrorCommand，状态0或2 | 原生成MID`0x4e0`／子码1；发送44字节 | 都是事件`0x1001` |

Ack／Comp还运行了原类别5错误转换；本轮输入0／2在这些声明条件下分别仍为0／2。未据此定义完整错误枚举。非零状态也能具有同一个期待事件身份，因此诊断必须检查内容及后续编码结果，不能把匹配或唤醒当作硬件成功。

原Ack `ResCmd` 对构造子码`0x8502`进行比较，匹配后还会转换状态并走日志；其完整后端消息来源、状态机推进和实际响应尚未执行。本轮没有以类名推导“MC已经打开”。
