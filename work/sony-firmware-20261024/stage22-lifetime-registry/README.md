# FX3 实验对象登记与代码退出边界

本阶段形成了一个**串行化登记协议的参考实现**，补上队列外生产者和对象的观察范围。它没有安装到相机，也不产生恢复原代码或释放补丁内存的许可。数据依赖退出与代码无人执行是两个条件，不能用一个对象计数替代。

参考协议在2个生产者、1个FIFO worker、1次关闭操作的1194个模型状态内，没有出现登记表误报已清空；两个刻意错误的候选协议均找到反例。另有7组身份/故障控制和4个原固件析构边界片段通过。模型范围、原指令片段和实机验收保持分开。

## 原析构路径新增证据

原件仍是官方7.02提取的 `appFw.so`，SHA256 `545c5053a74e04ffbf2bbaaf80f558092dd545ed2298b2395ca547dbba58290f`。

原非删除析构0x2bb0390先写回该类虚表，再转到基础析构0x28443a0。基础析构在依赖容器清理、条件变量销毁和其它清理之前，就把虚表指针改成基础类的0x46e3198。2个原指令前缀对照中，原cache虚表0x46e8000均发生这个变化，cache+0x388的标记0或2保持不变。执行停在后续清理之前。

原删除析构0x2bb03a4调用上述路径，再以对象地址和0x4d8大小尾调用 `_ZdlPvm`。另2个片段只验证尾调用传参，停在原PLT，未执行free。这些证据说明：在通用free处临时读取虚表来识别原cache类型，可能已经太晚；对象释放后也不能再读取它的标记、token或虚表完成注销。

替换路径先构造新对象，随后处理旧对象和旧token；原请求token在捕获点尚未完成新身份赋值，之后又可能沿用旧token。因此登记身份不能只依赖该token，也不能等入队后才登记。这里没有执行完整替换、基础清理、条件变量销毁或真实释放。

## 参考协议

`lifetime_registry.py` 的 `Registry` 是Python参考模型。每个方法被当成同一串行化域中的一次完整操作；代码本身没有实现Sony原生锁、atomic、ABI、故障返回或线程调度。

| 操作 | 协议约束 |
|---|---|
| enter | 在读取并采用实验激活状态之前，预留生产者ticket；它与close必须使用同一已验证同步域 |
| register | ticket仍有效时登记对象，之后才允许它携带实验标记；即使先前ticket获准、随后入口关闭，该生产者仍保持可见 |
| finish_producer | 已登记输出，或明确没有实验输出，才结束生产者记账；对象即使先被worker销毁，尚未返回的生产者仍独立可见 |
| 对象阶段变更 | prepared、queued、running、retiring保持登记；替换/取消也必须保留准确对象身份 |
| complete_retire | 对应清理及释放调用已返回后，才能结束该代对象记账；实际回调位置仍未实现 |
| retain/release_input | 可能晚于源对象结束的局部包或其它消费者需单独持有依赖，不能随源对象一并清掉 |
| close | 阻止新的实验ticket，保留此前ticket和对象；本模型不重新开启会话或清除故障 |
| fault | 容量耗尽、身份错误、重复登记或编号耗尽会保持故障状态，即使已知对象随后全部清理，也不能报告干净退出 |

对象key由分配地址和私有ticket代号共同组成，配置epoch另存；请求token只作关联信息。一个控制用例让同一地址、同一请求token对应两代对象：完成旧代注销后，新代仍在登记表中。另一个控制让查询包晚于源对象销毁，直到包释放后登记依赖才为空。这是参考协议控制，不是Sony allocator重用、包所有权或回调已被实际验证。

编号使用Python整数和可配置上限表达“不允许回绕”的协议要求；没有证明原生uint64存储、原子指令、溢出分支或跨核可见性。容量不足时的实际相机行为也未设计完成：本模型只阻止错误的退出判断，没有提供可以直接抛入原厂代码的错误返回，更没有把某个消费者静默回退成原厂参数。

## 反例与有界检查

模型使用独立的生产者和对象生命周期作为观察真值，并枚举方法之间的交错。它没有枚举机器指令重排、真实锁、异常、无限生产者或所有功能消费者。

两个错误候选的最短反例为：

1. **先读开关，稍后才预留登记。** P0已获准进入，随后close看到空登记表；P0仍可能继续生成实验对象。改进协议在entry检查与ticket预留之间不留这个窗口，前提是原生实现确实提供所假定的同步。
2. **在析构入口立即注销。** 对象刚进入销毁阶段，登记表就已为空，但原析构后续清理尚未完成。该反例中原current槽仍非空，因此完整的原pool检查仍可能阻止退出；它证明的是登记子协议误报，不能写成完整的不安全卸载轨迹。

改进协议检查了1194个不同模型状态，登记表在该边界内没有误报。检查还记录了39个“登记及模拟队列/current均已清空，但模拟生产者或worker仍处在补丁尾部”的状态。这里的执行位置是模型中的阶段标签，**不是实机PC采样或Unicorn并发执行**。

这进一步区分三类条件：

- 被覆盖的实验数据已经退出，包括队列外生产者、对象、衍生输入和原队列/current。
- 所有相关补丁入口已按验证过的方案停止新代码进入，既有线程及返回地址不再依赖待回收代码和数据。
- 恢复原字节、指令可见性、回读、WBI/冷启动和对应录制回归完成。

当前只实现了第一类中一个受限参考登记协议；原生入口、所有消费者和实际同步仍缺。后两类没有由本模型放行。单纯在补丁末尾把计数减到0，仍可能留下尚未离开补丁代码的执行者。

Linux内核RCU文档把停止新引用与等待旧读者退出、随后回收分开。[原文](https://docs.kernel.org/RCU/whatisRCU.html)（2026-10-25核对）。这里仅借用通用回收约束，没有声称Sony应用具备相同RCU API。C++工作草案也区分同步关系与原子对象各自的修改顺序；分别读取开关和计数器不自动构成一个复合事务。[原文](https://eel.is/c++draft/intro.races)（同日核对）。实际ARM内存序和指令发布仍需单独验证。

## 未完成项和下一步

本阶段没有原生ticket存储、同步、登记hook、析构完成回调、全消费者覆盖、线程安全点或代码回收器。下一步应先核对所有衍生包/对象的真实所有权和析构调用者，确定可实现的注销位置与安全点来源，再设计原生ABI。不能把“模型方法是原子的”当作实现，也不能以墙钟等待替代线程退出证明。

完整目标不变：经典FX3 7.02的1920×1080、29.97fps、HEVC420 10bit约16Mbps实际MAIN主录，以及同机备份、受限恢复/回读、独立救援入口、冷启动、音画同步、长录和温度验收。精确30.000fps仍单列。以上实机目标均未由本阶段达成。
