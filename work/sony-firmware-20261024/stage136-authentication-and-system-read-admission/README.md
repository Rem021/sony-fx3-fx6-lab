**认证最终应答并不证明相机端的登记、日志和模式更新已经结束。** 本轮把原认证线程的虚调用与工作线程vtable连接，核对命令表发布和条件写入顺序；另审查出直接POSIX读取分支，生成两个固定库文件的离线请求草稿。没有执行认证、相机文件读取或发送这些草稿。

## 认证尾段的原始顺序

NinThread原函数与WorkerThreadManager vtable解析共同给出以下条件路径：

1. `0xbe6c`先序列化最终认证应答。
2. `0xbea4`调用vtable偏移20，对应 `registHaspId → Regist_HaspId`；阶段134已确认其有条件更新 `/setting/.hasp` 88字节。
3. `0xbf2c`调用vtable偏移28，对应 `onComplete`，发布命令表并调用所存完成回调。
4. 其后若日志存在，调用更新流程：读取4096字节、解码/更新/编码，以 `wb` 打开并写回 `/setting/.etools` 4096字节。
5. 线程返回前，等级3分支还准备创建/写入 `/ramdsk/dev/mode` 三字节；其他分支会移除该文件/目录。本轮没有证明 `/ramdsk` 的实际存储后端。

上述是静态条件顺序，不证明每次认证都写上述文件，也未证明用户机身文件存在。最终应答或完成回调不能单独作为所有文件操作结束、所有线程已退出、可立即停止/回收的凭据。实际握手、正常退出和取消/join边界仍待验证。[原函数与调用证据](authentication-publication-review.json)

## 命令表由完成等级选择

| onComplete等级参数 | 原函数选择 |
|---|---|
| 1 | pFunc_level_C |
| 2 | pFunc_level_B |
| 3 | pFunc_level_A |

该函数在其他等级下仍可调用完成回调，所以收到“完成事件”不等于已建立可用命令表。`terminal_change_function_is_disabled` 的等级判断也不能误作编码状态或同步锁。阶段131三个已查表缺ff01/ff03的结论仍限于这些表；本轮没有将其推广为所有动态服务均不存在。

## 临时目录名称不是RAM保证

同包官方启动配置列出 `/dev/nflasha2 → /setting`、`/dev/nflasha10 → /tmp`，均为可写vfat；`/dev/nflasha15 → /usr` 为只读ext2。它们是公开固件启动配置，不是本轮对用户机身挂载表的测量。

因此，涉及 `/tmp/jiritsu` 的挂载、目录或日志流程不能仅凭路径名字就归类为纯RAM副作用。阶段130的GET_FILE2挂载/日志审查保持有效；未来授权说明需要覆盖真实条件写入范围，不承诺整个服务过程零写入。

## 新的固定系统读取候选

已静态审查 `get_access_filename` 和CFileAccess的open/read/stat：非 `/mnt` 路径分支会把路径交给POSIX接口。原setpath字符检查不排除点字符。按[Linux路径解析规则](https://raw.githubusercontent.com/mkerrisk/man-pages/master/man7/path_resolution.7)，可形成走出服务挂载根后读取固定 `/usr/lib` 目标的候选。

本轮仅生成 `/usr/lib/libsencore.so`（官方参考377328字节）和 `/usr/lib/libJiritsu.so`（225200字节）的惰性帧草稿，记录原件SHA、候选路径和参数；没有通用路径输入、USB发送或认证实现。它不是此前阶段9保守编码器的放宽发布；原编码器保持原样。

原 `CheckUnitType` 根据大小选择四档DMM单位，上界分别为5/15/50/100MiB减1，再大的请求返回未接受的单位值。两份小库参考值属于首档；这不证明当前机身可分配的实际空间、DMM所有权或完整错误清理，也没有增加设备端的请求长度字段。

词法归一化与POSIX分支不能证明机身当前进程根、命名空间、挂载点和符号链接。当前还缺传输/回复实证、驱动归属、设备侧长度/分配和退出审查，**草稿未达到可发送状态**。主应用appFw.so官方参考为79015712字节，仍需完整同机备份和恢复；不以两个小库草稿缩减这个范围。[读取准入与草稿](system-read-admission-review.json)
