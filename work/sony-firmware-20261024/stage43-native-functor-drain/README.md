# FX3：原事件构造、虚调用出队与代码退出

本轮执行了原状态对象构造前缀，让它实际写出START/STOP嵌入事件的虚表，再通过原队列与虚调用执行待处理事件。11段原片段的正式复核通过。

最重要的观察是：**原队列计数、活动标志及两个待处理标志都可为0，而客体PC仍在待处理事件正文入口，原调用栈尚未返回。** 因此，这些数据状态不能单独证明代码已经退出或模块可卸载。

这是单个Unicorn实例中的确定顺序调度，真实线程、多核、锁、实例绑定、HAL及机身恢复未验证，没有连接或写入相机。

## 虚表由原构造代码写入

原0x253b38前缀在客体中执行，写入：

| 嵌入事件 | 对象位置 | 原虚表地址点 | 原事件编号 |
|---|---|---|---:|
| enc_sys_v_t | state+0x508 | 原映像+0x37f128 | 16 |
| enc_stop_done_t | state+0x550 | 原映像+0x37f188 | 18 |

本轮没有由宿主直接设置这两个虚表。原RTTI名称、类型信息及虚表项均逐字节核对。

构造执行在第一个未绑定运行时清零入口停止，后面的队列/活动区清零未执行。用0xa5预填对象的对照中，活动字节及待清零队列区仍为0xa5，说明构造前缀不是完整初始化。后续对照明确使用零填充和指定状态/owner作为输入，不宣称完整构造器或真实单例已经建立。

## 原出队调用链

原队列处理先减少计数，再通过嵌入事件虚表调用0x253db4。该通用分发器先清除嵌入对象+0xc的待处理标志，然后读取虚表+0x18并进入具体正文：

- START正文0x253ec4，从嵌入对象取owner和1字节数据，转入原0x252f54。
- STOP正文0x253ee4，取owner和6字节数据，转入原0x2533d4。

待处理标志位于具体事件正文执行之前就会清除，队列也在此之前已经取走该对象。

## 两段客体调用按确定顺序交错

本轮在原START状态帮助函数已经设置活动标志、尚未完成的一个原PC处暂停，保存客体CPU上下文。

随后用另一段客体栈调用原排队函数。它观察到活动状态，实际复制事件并入队，然后正常返回。再恢复先前保存的CPU上下文，保留刚产生的客体内存写入，让原调用继续出队与执行。

使用Unicorn的CPU上下文API；没有把PC设为LR、伪造函数成功返回或恢复旧内存。[Unicorn API声明](https://github.com/unicorn-engine/unicorn/blob/master/include/unicorn/unicorn.h)仅作为API概念参考，本轮以实际安装的2.1.4运行结果为证。

正式复核另外检查了所有X0–X30、Q0–Q31、SP/PC/LR及NZCV/FPCR/FPSR的恢复，并核对整个客体可写区域和栈的哈希，确认恢复CPU上下文时未回退排队操作的内存。

这只验证一条受控调度，不验证真实线程、弱内存、多核或原同步域。

## 数据已清，正文仍在执行

原调用继续到出队事件正文入口时，实际读取到：

- 队列计数0，活动标志0，START与STOP待处理标志均0。
- 客体PC为START的0x253ec4或STOP的0x253ee4。
- 原栈帧仍存在，SP尚未回到调用前位置，事件数据仍保留。

移除这个观察断点后，从**同一PC和寄存器/栈状态**继续执行：

- START正文完成原状态处理，经原外层栈正常返回，最终SP回到调用前位置。
- STOP对照刻意在ENC_READY状态安排STOP事件，属于不符合当前状态表的人工顺序；原正文到达错误诊断入口，本轮在诊断前停止，没有声称正常停止或错误恢复完成。

因此，本轮只对已观察的START调用证明其客体代码返回；它不是所有线程、消费者和实验模块的全局退出证明。错误顺序STOP也不能被计为成功收尾。
