# SERVICE获取子步骤回执组件

针对269实际失败中“只知道复合操作11返回独占错误、不知道具体方法”的缺口，已修改C流帧写入器与Python解码器。**这只是离线组件，没有native入口、启动器或可上机包；没有新的USB、管理员或相机操作。**

原backend已经维护`acquire_step`及`acquire_raw_return`，旧流帧却未输出。新格式保持672字节，在原保留区592／596加入步骤及其原始返回值，并同时升级为`FX3FLOW4`／schema4。后续帧必须保持已绑定的获取结果，不能在其他步骤改写它；旧格式拒绝进入新解码器。

步骤表分别标明device plugin、设备接口查询、device open、配置数量／当前配置／配置描述符、接口迭代器、interface plugin／query／open，以及接口属性和管道检查。收到错误时不再根据一个返回码猜测某个API；早于native步骤的拒绝也不能标成成功获取。

[组件核对](component-check.json)执行了实际C写入器、普通用户文件／fsync和Python解码；peer及获取结果是人工输入，不含IOKit。三个案例覆盖设备打开203与接口打开210返回相同独占错误、以及尚未进入native阶段的拒绝。七类反例拒绝，包括未知步骤、返回值混配、保留区修改、无步骤却宣称成功、调用前结果，以及269旧回执不能凭空补成新步骤。ASan／UBSan及编译检查通过。

这些检查不证明完整控制器、真实IOKit调用或退出已通过。后续需接入完整构建和fixture provider，并继续审查libusb的设备级独占错误处理与后续接口操作条件；当前没有放宽打开策略，也未重试已消费的268许可。269真实失败仍不具有子步骤证据，原记录不改写。
