# FX3 HEVC 静态预置与默认码率字段

本轮把MAIN FF的原匹配行386继续绑定到实际预置记录：**原选择器选中preset0x19450，原解码函数得到target=24,498,176、trace=25,999,360；不是16,000,000。** 匹配代理FH的preset0x1c26b则解码出target与trace均为16,000,000。

因此，原表存在HD29.97 HEVC42010 MAIN条目、FF人工对照能命中，仍不足以实现16Mbps主录。仅更换质量枚举不能满足目标，后续需要核对受限的码率调整与实际编码应用。实机、样片、受限恢复及独立救援没有验收，目标继续进行中。

## 原选择器闭合了哪一段

原CreateCh表每行+0x28存preset ID。原调用者0x21ee98进入0x2261a4；流类型14/HEVC_MP4及21/XAVC_PROXY_HEVC经0x22c3cc选择模块类别2，随后原选择器完整扫描0x3c4a98开始的HEVC预置表。

该表316条记录，每条0x100字节，在0x3d8698以类型25结束。找到ID时，原指令把对应记录地址保存到common+0xe000，并保存一个记录字段到common+0xe458。

本轮执行了原0x21edc8开始的“已匹配行之后”片段：原行字段复制、原模块选择、316条记录扫描和原指针保存均实际执行；在0x21dd54缓冲/通道准备入口停止。行号来自上阶段匹配证据，所需上下文、保存寄存器及非隔行字段仍是显式fixture。没有执行之前的完整构造、状态、日志、资源申请或硬件Open。

然后直接让原0x225b7c读取**原选择器产生的原文件内指针**，解码默认值；再独立执行0x246154，把这些值复制到Open完成载荷。全程未填造HAL参数、未修改原文件或原预置字节。

## 六组原预置对照

| 输入场景 | CreateCh行／preset | HEVC预置记录 | 原target整数 | 原trace整数 |
|---|---|---|---:|---:|
| MAIN HD29.97 FF | 386／0x19450 | 13，0x3c5798 | 24,498,176 | 25,999,360 |
| MAIN HD29.97 QT35M | 488／0x1944c | 115，0x3cbd98 | 33,000,000 | 34,996,224 |
| MAIN HD29.97 QT50M | 529／0x1944d | 156，0x3ce698 | 50,000,000 | 57,999,360 |
| MAIN HD29.97 QT9M | 583／0x19454 | 210，0x3d1c98 | 8,800,000 | 9,999,360 |
| 代理HD29.97 FH | 607／0x1c26b | 234，0x3d3498 | 16,000,000 | 16,000,000 |
| 原UHD59.94 QT150M控制 | 431／0x18da8 | 58，0x3c8498 | 150,000,000 | 159,989,760 |

六组都由原选择器、原解码器和原回复复制函数执行。其它MAIN质量对照仅改变独立描述符的质量字段，不是已实现的设置模型/菜单选项。各ID在本轮689条CreateCh表中各被一行引用；这不是完整间接引用或全运行时复用证明。

HEVC目标解码形式与[ITU-T H.265的HRD码率公式](https://www.itu.int/rec/dologin_pub.asp?id=T-REC-H.265-201304-S%21%21PDF-E&lang=e&type=items)一致：`(value_minus_one + 1) × 2^(6 + scale)`，标准对应bits/s。结合原target_bitrate名称、代理16M与UHD150M对照，**工程上可将FF目标字段解释为约24.50Mbps**；这是预置字段的解释，不是实测平均码率、封装码率或正式可用规格。请求生产者的单位和最终参数集/码流仍需分别闭合。

## 默认值查询不能充当实际码率回读

上阶段用合成缓存核对过0x225b7c和Open完成载荷的字段位置，没有声称观察到HAL返回。本轮找到了该分支的一个真实原生产者：0x2261a4直接让common+0xe000指向静态HEVC预置记录。

因此，这个解码器至少在当前已绑定分支上可以返回静态默认值。它不是已验证的“读取实际编码器当前目标码率”接口。之后代码是否克隆、改写或替换相关运行时对象仍需追查，也没有据此断言所有后续查询永远只读静态数据。

任何受限调整都必须检查实际用于初始化/更新的参数、对应错误与完成结果，并用真实HEVC参数集、文件/码率及连续录制验证。不能只比较Open完成字段或收到0x117确认，就宣布16Mbps已经应用。

## 收紧上阶段的策略线索

0x189c74/0x18cdd8的owner+0x278选择，以及0x18d7ac构建的MID0x1302，仍是原时序/同步路径线索。接收端实际进入`sync/sfmc_sync_mgr.cpp`。经典MAIN构造的低帧率逐行子接口则绑定`sfmc_enc_timing_i<8>`，原诊断源为`sfmc_enc_timing_i_normal_progressive_30p25p24p.cpp`，函数明确处理start/stop、mark与deadline。

这些名字和代码不足以把owner+0x278直接当作16M码率生产者。主线已改为：**有效MAIN质量／原静态预置 → 实际初始化/更新参数 → 编码应用和真实反馈**。时序/同步仍需验证，但不能用它的局部选择替代码率来源。

原运行时清零API仍未绑定：映像头+0x20指向原0x1a4，所用槽位0x85c在原文件中为0。本轮没有为它补实现，未把空槽认作运行时一定为空。
